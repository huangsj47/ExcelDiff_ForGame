# 正反例与验证矩阵

这些是审查训练用的抽象案例，不是任何项目当前仍存在漏洞的证据。数字为测试值。每次审查必须重新验证目标实现与配置。

## 统一测试口径

同一合法请求预期发 100，消耗 1 次资格（或扣款 10）。记录初始状态，再调用、观察失败、按真实重试路径调用一次，核对：
- 内存与持久化资产分别净增多少；
- 资格/次数/扣款分别变化多少；
- 邮件、库存等实际交付结果及唯一 ID；
- 发奖单/条目状态和接口返回。

不要把“接口 false”当作未交付，也不要把“接口 true”当作已全量交付。没有实际持久化测试时只断言内存结果。

## 验证矩阵

| 案例 | 关键执行过程 | 应得结论与禁止误报 |
|---|---|---|
| 写前失败 | 校验失败；资产 0、次数 0；重试仍失败 | 不存在多拿证据，不能因为允许重试而报告重复发放 |
| 写后失败、未记次 | 加 100 → 后续同步抛错 → 被判全败、次数 0；重试重复 | 可出现资产 +200、次数 0；注入异常复现只证明故障恢复隐患，不证明玩家能制造异常 |
| 正常成功对照 | 加 100 → 次数 +1；dailyLimit=1，第二次被拒 | 资产总计 +100、次数 1；正常限次有效，不应说所有连点均可绕过 |
| 部分失败但已记次 | A 成功、B 失败 → 返回部分成功并计次 | 不可报告“任一 handler 失败就不计次”；检查 B 的补发是否会重发 A |
| 通知在记次后失败 | 资产 +100、次数 +1 → 弹窗抛错 | 有限次/幂等保护时不能据此报告漏计次；若只有每日限次且允许多次，另查业务去重，不混为一谈 |
| 同一事务完整回滚 | 资产与资格在同一 DB 事务，提交前失败，全部回滚 | 不能只看到代码先改余额就说已永久到账；若事务中另发邮件，邮件不一定被 DB 回滚，另查实际边界 |
| 先占用无恢复 | 次数 +1 已提交 → 发放前失败，无处理中记录/恢复 | 是少发/吞资格问题；不能把先扣后发视为天然正确 |
| 未知结果直接退资格 | 下游已加 100，响应超时 → 上游退资格 → 重试新单再加 | 条件性重复发放；证明请求确实可能超时且副作用独立提交，不能仅假设“网络可能出错” |
| 稳定幂等单 | 同一业务键第二次命中完成记录，复用结果，无新增资产 | 重试不多发；还要检查首次处理中重复到达时的原子占用保护 |
| 仅复用日志 ID | sLogId 相同但没有去重查询/唯一写入；每次都加 100 | 接口不具备请求幂等；若它本来就是底层加钱原语，只有上层漏去重才是完整业务漏洞 |
| 邮件拆分开启 | 3 个附件条目、每封上限 1，生成 3 个新 ID；调用者只查旧 ID | 真实送达被误判失败；若全部交付均被排除、因此不计次，重试会重复交付 |
| 邮件拆分关闭 | 无上限/未超过上限，发送原 ID，原 ID 查找成功 | 不报告当前可达拆分漏洞；可单列开启拆分后的兼容风险 |
| 邮件部分拆分送达 | 仅部分新邮件成功，接口只有整体布尔值 | 不能认为全败可重发整单，也不能认为全成；检查逐封/逐条交付记录 |
| 仓库计划大于实发 | 计划 3 件、成功 1 件，结果仍报 3 件并计次 | 确认结果不实/少发；不能直接称为多发，除非补偿链确实整单再次发放 |
| 随机未命中不计次 | 每日抽取次数应为 1；未中记失败，允许反复重抽 | 若业务是限制抽取次数，则有免费重抽；若限制成功领取次数或配置有必中池，不能直接定性 |
| 单线程同步限次 | 检查次数 → 写资产 → 记次，无挂起/重入点 | 没有跨请求交错证据，不套用两线程同时通过的伪复现 |
| 有真实挂起的竞态 | 两请求在资格检查后 await，同一资源占用无条件写入 | 给出明确交错 A-check/B-check/A-write/B-write，核对唯一约束/锁是否已拦截 |
| 只有 GM 可调用 | 客户端玩法协议未接入；GM 路径有服务端权限 | 不能写普通玩家可直接刷；仍可报告内部重试的可靠性问题，标明权限范围 |

## 推荐的最小验证组合

针对一项风险至少选择：
1. 目标触发用例；
2. 正常成功或保护开启的对照用例；
3. 同一业务重复调用用例。

写后失败用例还要区分资产写入前/后的故障，并检查部分成功是否已计次。邮件用例要分别检查拆分开启/关闭，不以“计划发送数量”充当成功投递数量。

## 修复方案反向检查

提出方案时再问：
- 计次前移后，失败是否永久吞掉资格？
- 退款/退次数时，下游是否已经交付，或者结果还未知？
- 整单补发是否重复发放成功条目？
- 重试是否生成了新业务键或重新随机？
- 以 rewardId 去重是否误拦第二个合法任务奖励？
- 故障发生在“写资产成功、完成标记未写”之间，下次怎么确认？
- 原子性是否覆盖所有副作用，还是只覆盖一张表？
- 状态放在内存还是已经持久化，重启后谁恢复？

无法解释恢复路径的“先扣后发”，不是完整方案。
