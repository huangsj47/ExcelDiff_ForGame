# 资产发放安全审查

审查目标：以用户调用本技能时提供的文件、函数、模块或玩法为准；未指定时，按下方范围选择规则定位目标。不依赖宿主的参数占位符替换。

目标不是证明“应该先扣后发”，而是回答：**一次合法业务请求到底应产生多少资产与资格变化？失败、重试或重入后，会不会多发、少发或多扣？**

默认只读，不修代码、不写 TODO、不提交、不改变配置。使用中文报告，用户另有语言要求时遵循用户要求。

## 1. 确定范围与契约

- 有参数：优先定位给定玩法、函数或文件；沿相关调用链定向扩展，不扫全盘。
- 无参数：先用当前选中的函数/打开的文件，再看与资产流程有关的 diff。没有明确目标时询问。
- 先读适用的工程指令；使用项目要求的符号/调用链工具，不可用时才回退到文件搜索。Bash 遵守用户的 RTK 等约定。
- 以当前实现、真实注册的 handler、当前配置为准；历史文档与注释只作线索。记录当前配置来自何处，不能把本地配置当成线上已部署配置。
- 明确“同一次业务”的身份：角色、任务实例、订单、结算场次、领取阶段等。奖励配置 ID 不是天然的订单 ID；每日限次也不等于请求幂等。
- 明确额度的语义：成功领取次数、抽取次数、购买次数还是总交付数量。语义未知时保留条件，不自行定罪。

## 2. 从入口追到实际提交

必须追出以下节点（不存在的节点注明），不能只看某个 grant 函数：

```text
玩法入口 / 客户端 RPC / 内部任务 / GM
→ 身份权限、领取资格、参数来源
→ 请求去重、资格占用、次数记账或扣费
→ 构建发放计划与 handler 校验
→ 邮件 / 背包 / 货币 / 外部服务的实际写入
→ 完成状态与持久化提交
→ 日志、回调、通知、响应
→ 调用方的重试 / 补偿 / 退款
```

记录每个关键点的文件行号、返回值/异常处理、修改的状态及所属事务。

特别核实：
- 谁能调用，普通玩家能控制什么；只有 GM 调用时明确写“尚无玩法接入”。
- 检查的是内存还是数据库；置脏不是落盘，发起异步请求不是远端已提交。
- 是否存在数据库事务、唯一约束、条件更新、队列去重、状态机、outbox 或下游幂等。已有保护必须计入结论。
- 是否存在真实 yield/await、同步回调重入、多线程、多进程或多个消费者入口。不要见到“检查→写入”就假设中间可以插入另一请求。

## 3. 建立状态账本，检查故障边界

对疑似路径记录：

| 执行点 | 资产实际变化 | 资格/次数/扣费变化 | 完成记录 | 内存/持久化状态 | 返回/异常 | 重试行为 |
|---|---|---|---|---|---|---|

用同一业务请求执行一次、重试一次，计算最终变化。比较期望值与实际值，而不是仅判断返回 true/false。

### A. 写后失败与错误重试

- 资产已改，后续日志、功能钩子、同步或序列化失败，被整体判为“未发放”？
- `pcall/xpcall/try-catch` 只捕获异常，不自动撤销写入；检查实际回滚逻辑。
- 是否只在全部成功/存在成功条目后计次？部分成功到底会不会计次？从代码逐分支确认。
- 调用方会在什么条件下重试？是否复用同一业务单、稳定随机结果及已完成条目？不要臆造自动重试。
- 对某个普通库函数凭空假设抛错不足以定性现有漏洞。必须注明具体写后故障点、可达条件和恢复行为；只能故障注入验证的，归入条件性风险。

### B. 先扣后发与错误补偿

- 先扣钱/次数后失败，是否吞资格、不交付？是否有可恢复的处理中状态？
- 是否无条件退款/退次数，而下游其实已执行成功？网络超时属于结果未知，不等于失败。
- 补偿是否幂等，是否再次发放本单已成功部分，或让原单和补偿单同时完成？
- 不建议把所有失败一律退次数，也不建议把所有异常一律当成功。

### C. 去重、并发与重入

- 幂等键是否稳定且按业务正确划分；是否只是日志字段，或每次请求随机生成？
- 去重查询与占用是否原子；“处理中”重复请求如何响应；服务重启后去重是否仍有效？
- 只对实际存在的并发/重入窗口构造交错顺序。同步单消息流程没有挂起点，不按多线程模型报告竞态。
- 同奖励配置的两次合法业务不应被误拦；同一业务的重复请求不应多算一次。

### D. 发放结果与资产事实不一致

- 返回清单来自计划还是成功写入记录？部分入库失败有没有扣除失败数量？
- handler 可能部分写入再失败，框架是否误当零写入？
- 邮件是否拆分/改 ID/排队/异步投递；是否误用原 ID 或立即本地查找判断送达？检查配置是否真的启用。
- 溢出邮件与直接入账是否互斥，数量守恒？“未显示奖励弹窗”不等于没到账。
- 随机未命中是否是合法结果；重试是否免费重抽或换掉已确定的结果？

### E. 持久化与恢复

- 资产、扣费、领取记录是否同事务提交？真实跨存储/异步边界是什么？
- 崩溃后哪些状态可能保留？不得把内存已改直接说成重启后资产已持久化。
- 未完成单是否有人恢复；恢复能否确认已发部分；日志是否只是诊断信息而非可执行账本？

## 4. 反证与安全验证

形成发现前阅读 `references/scenarios.md`，检查是否存在反证。

- 优先静态核实真实调用者、配置、运行模型与现有保护。
- 需要动态验证时，仅做隔离本地测试：加载真实目标函数，mock 网络、数据库、邮件投递等外部副作用。不得连接真实服/数据库、执行 GM 发奖、改线上配置、发真实消息。
- 明确列出使用的真实代码、mock 层、故障注入点和测试配置。不要把手写的简化算法复现当成原代码复现。
- 断言资产净变化、次数/资格、已完成状态、邮件等交付记录和返回值，不能只断言抛错。
- 有异常测试必须有对应成功路径/保护开启的对照测试。
- 无运行环境时注明“仅静态验证”，不安装依赖或启动服务来凑复现；真实环境操作须另行授权。

## 5. 严格分类，避免夸大

每个发现分别给出 **触发类别** 与 **验证程度**：

触发类别：
1. **当前可达**：当前代码/本地配置存在完整入口与操作路径；说明是否普通玩家可触发。不能直接等同线上可利用。
2. **故障恢复隐患**：具体故障下，已经执行的副作用与恢复策略不一致；缺少正常操作触发故障的证据就明确说明。
3. **条件性兼容风险**：仅未启用配置、未来 handler 或未来接入满足前提时触发；与现存漏洞分开列。

验证程度：静态确认 / 隔离测试复现 / 故障注入复现 / 待验证。与触发类别正交，故障注入成功不升级成普通玩家可刷。

影响大小与触发可能性分开；不要仅因为假设“无限刷”就标最高优先级。同根因不同异常点合并。一般性“任何代码都可能抛错”不作为独立漏洞。

找不到真实玩法入口，写“未找到，目前仅某内部/GM 入口”；找不到具体异常来源，写“仅验证写后异常时的处理，未证明可主动触发”。没有确认问题可以直接说未发现，不凑数，也不承诺绝对安全。

## 6. 输出格式

先用一小段回答：**当前已检查路径能否多拿/少拿，结论依赖什么条件？** 随后给简短真实调用链和发现。

每项发现使用：

```text
标题：[触发类别] 缺陷及后果
位置：可点击的文件及行号
真实入口：玩法/内部任务/GM → ...；未找到时明确注明
前置条件：当前配置、角色状态、权限、具体故障、并发条件
执行过程：资产写入 → 资格/次数 → 返回结果 → 同一请求重试
预期 vs 实际：具体净增量/次数/交付差额（示例数字注明为测试值）
验证：静态/隔离/注入/待验证；列 mock 和尚未证明的条件
建议：最小充分修复，并指出会不会引入少发、多扣或补偿重复
```

最后说明覆盖范围、未检查/未运行的部分。输出保持聚焦，优先已确认问题，条件性项另列；若宿主明确要求结构化审查工具，遵循宿主格式，不重复输出两份发现。

## 修复建议底线

原则是 **先占资格、发奖幂等、失败可恢复**，不是“宁可玩家少拿”。

- 能用既有同库事务/条件更新解决时优先复用，不无条件引入分布式事务或新服务。
- 跨边界执行考虑稳定业务单号、处理中/已完成/结果待确认状态、条目级幂等、对账恢复。
- 只对确定未执行的副作用释放资格或安全重试；结果未知先确认，不能盲退/盲补。
- “把计次移到前面”“包一层 xpcall”“统一 return true”均不能单独作为完整修复。
