# 风险事实、影响假设与验证动作

填写 `report_items` 前读本文件。业务报告与 QA 待办使用同一份结构化数据，平台统一生成七章
Markdown；不要另写一遍完整报告，也不要从自由文本恢复风险。

## 一项发现对应一组行动

每项分别填写：

- `business_area`：知识包中的业务领域，不凭路径名猜玩法。
- `title`：短业务结论，前置对象与关键变化/矛盾（如某ID仍被引用、消耗由10改为空），不要抄长路径。用于速览，不截断事实；详细旧值与新值仍写 `change_fact`。
- `change_fact` / `change_fact_refs`：实际观察到的对象、字段、旧值→新值与业务坐标；缺失值写未确认。
- `impact_hypothesis`：什么触发条件下可能发生什么可观察后果。读到字段变化不等于验证了后果。
- `evidence_status`：`verified` / `partial` / `unverified`。模型声明只是判断；平台会校验地址，
  取回原文也不能代替人工核实需求和运行行为。
- `decision_question`：策划可以具体回答的问题。影响或需求未知时必填，不能把疑问改成缺陷。
- `test_actions`：每条包含 `conditions`、`steps` 数组、`expected`。未知预期留空并先确认需求，
  不自行补造。中低风险也不能漏；程序关联实际稳定 ID，模型不编造 R 编号。
- `evidence_refs`：照抄已取回的 `evidence_id`。坐标由平台绑定，不能猜路径、提交或证据地址。

每项要使 QA 知道构造什么条件、做什么操作、用什么结果判定；风险确认前同样要给取证和核实动作。
不要只写「注意测试」「可能有风险」「详见其它章节」。每项自己说清事实、假设与行动。

## 写给策划与 QA 的表达约束

每项围绕一件事：变化写对象/字段与值，影响用一句有条件的玩家后果，问题只问能改变判断的具体语义。
不要在每项重复完整文件路径、提交哈希或窗口统计；取证地址放 `evidence_refs`，覆盖数字全部由平台生成。
不要用「与设计一致」冒充未知判据。对象 ID/入口未知时，先给查清对象的动作；预期未知留空。
消耗类问题按已证实的收费规则覆盖不足、恰好、富余和重复进入；没有规则时先确认收费语义。

同族样本、备注、名字相似、常见玩法只提供对照，不能证明项目规则。删旧表行先查迁表与实际解析键，
不能直接断言引用悬空；备注数量不同先确认目标，不能直接推出玩家奖励错误。引用链写清各字段的 ID 类型。
这些证据边界同样约束摘要、影响面、回归和上线建议；不能在风险里写「若」，在其它章节却写成必然。
没有需求/实现证据，不擅定跨难度数值必须递增、同族 ID 必须相同、表与两端必须同时发布等规则；
不自行规定书面审批或整批回滚。发布与回滚建议先核对读取方、配置、存档兼容性及实际依赖。

## 四档是关注优先级，不等于人工阻断

| 档位 | 影响假设成立时的后果 |
| --- | --- |
| 严重 `critical` | 不可逆资产/存档损失、可重复获利、主要服务不可用 |
| 高 `high` | 核心业务链阻断、重要奖励或数值明显错误，玩家难以绕过 |
| 中 `medium` | 局部功能异常，有明确绕过方式或影响范围有限 |
| 低 `low` | 边缘流程、展示或轻微体验问题，需要验证但不直接推出阻断 |

四档条目都进入 `report_items`，不得因篇幅、模块或风险较低而省略。`anomalies` 仍然只接受
`critical` / `high` 且置信度至少 `high` 的处置项，两者职责不同。`anomalies=[]` 不表示没有
中低风险或待确认问题。
这不是要求每种严重度都凑一条。仅改普通说明或备注、且没有具体耦合依据时，记录变化即可；
不把「也许有人按文案匹配」这类无迹象的可能性单独报风险。未读结束日期只构成缺口，不能单凭未读再报一条时间错配。

没有需求依据时，允许保留高关注的假设，但依据状态必须明确待确认。严禁把配置中的 0 擅自解释
为关闭、默认或无限；应询问实际语义和预期，再设计能区分解释的验证。只取回差异并不证明了影响。
模型不声明「人工确认阻断」，流程完成也不等于可以上线。影响人数、资产数量等未知量不虚构评分。

排序和编号由程序执行：人工确认阻断状态→严重度→稳定 ID。模型沿用已有 `finding_fingerprint`，
新项可省略，由程序按领域、事实和影响生成 ID；不同发现不得复用同一指纹。

## 遗留条目、摘要和缺口

结构化清单覆盖截至当前仍成立的发现，包括上次遗留。本轮没有重新取证的遗留项，明确待确认，
不得补写本轮证据。已修复或推翻的写入 `baseline_updates` 并给提交/事实依据；人工忽略的默认不复活。
分片交付也保留全部四档，汇总不能仅取 `anomalies`，重复项合并必须保留动作与依据。

`overview` 简述业务目标和结论适用范围；`changes` 按玩家可感知变化归类；`impacts` 指出具体入口、
群体和耦合链路。`regressions` 只补跨功能场景，避免复写每条验证动作；`release_actions` 写上线确认、
联动顺序、观测和回滚条件，不代替人工放行。

`gaps` 写缺什么对象/提交/正文，平台给出的失败原因原话，以及挡住哪个判断和补充动作。
未取证部分不宣称安全，取证覆盖不称风险召回率或验证通过率。覆盖计数和单位由平台账本提供。
正文不写 token、字符水位、模型窗口、请求额度等技术预算参数。

## 历史自由 Markdown 兼容

旧 `report_markdown` 使用固定七章、每条独立分块、`R#` 编号整节唯一且模块间不重开；
写清变化与触发、影响、依据状态、处理或待确认。测试关联实际 R 编号，预期未知先确认需求。
新任务使用结构化协议，不同时输出旧长文。历史原文保留为存档，不据此补造结构化业务数据。
