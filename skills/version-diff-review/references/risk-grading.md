# 「风险评估」这一节怎么写

**写报告正文的「风险评估」之前读这一份。** 它是这一节的取材来源，不是可选补充。

这一节最常写坏的样子，是写成「这次改动有风险，建议关注 XX」——它读起来像风险提示，
但读者拿它做不了任何决定：不知道什么条件下会出事、出多大事、上线前该拦还是该放。
下面把「能用的风险评估」拆成可核对的几条。

## 1. 每一条都要答全四件事

| 要素 | 写什么 | 不算数 |
|---|---|---|
| **触发条件** | 什么情况下才会发生（例如「活动 ID 在 1000–1999 区间、且该玩家当天已领过」） | 「可能」「有一定概率」——没说条件就等于没说 |
| **后果** | 玩家或线上**看到什么**，能给可观测指标就给（多发的道具数量、报错文案、日志关键字） | 「影响体验」「可能异常」 |
| **证据** | 这一条建立在**哪次取证的什么**之上（哪个文件、哪一行、哪次 `file_diff` 的哪个字段） | 没有出处的推断 |
| **缓解** | 上线前**必须做什么**，或上线后**怎么观测**（看哪个面板/日志、多久内看到什么算正常） | 「建议关注」「注意验证」 |

四件事缺一件，这一条就是**没写完**——不是「写得简略」。缺 `证据` 的那条尤其要拿走：
它应当落到「待取证假设」里去（见第 3 节）。

**不要解释实现上为什么会出问题。** 读者是准备回归和发版的人，不是要改这段代码的人；
「因为这里少判了一个空」属于实现说明，不写。

### 这一节是**当前仍成立的全部问题**，不是本轮增量

增量分析时，正文的「风险评估」要覆盖**这个版本到现在为止仍然成立的每一条**：本轮新
报的、以及上一轮报过、现在仍然成立的。

**两种写法都可以**（真机两轮都跑过）：

```
# 风险评估

## 本次新确认（有原文证据）      ← 按来源分成两个二级小节（推荐，读起来最清楚）
R1（critical）…
R2（high）…

## 上次遗留（仍成立）
- [high] 【模块】标题（文件 @提交）
```

或者在同一个清单里**逐条标**「（本次新增）」/「（上次遗留，仍成立）」。
**两类混在同一节里就必须逐条标** —— 只靠位置区分，读者分不出哪几条是这轮新查的。

**旧结论只写「标题 + 等级 + （上次遗留，仍成立）」，不要为它补写证据。**
平台给旧结论的只有标题级摘要（标题、文件、提交、等级），你本轮并没有为它重新取证 ——
替它编一条「证据」「位置」，就是**印一个不存在的事实**，而这一节的所有可信度都建立在
「写出来的都查过」上。少写是信息不足，编证据是假事实：后者要严重得多。
要给旧结论补证据，就去真的取一次证（它涉及的文件本轮变了，或者你按它的文件与提交重新
索取过），取到了再按四要素写全。

**写完数一遍。** 这一节最容易出的错是**漏**：第一轮给你的清单里每组带着条数
（「仍待处理（26 条）」「需要重新确认（6 条）」），**把它们加起来、减去「已忽略」那一组，
就是这一节至少要出现的遗留条目数** —— 确认已修复 / 已被推翻的可以去掉，但要在正文里
交代是哪次提交修掉的。真机实测漏过 7 条（账上 47 条，正文只写了 40 条）：**写得简略是
风格问题，漏一条是那条问题从报告里消失**。

**篇幅不够时按这个次序省**：先省「中」那一档（整档不列，留一句计数），再省「上次遗留」
的细节（退回标题 + 等级一行），**不能省掉「本次新增」里的任何一条、也不能整条不写**。

## 2. 只在「已确认」的条目上分级

「已确认」= 你在本轮里**真的取得了支撑它的证据**：读过那段 diff、查过那张表的行、
跑过那个引用链路。**只是「看起来可疑」不算确认。**

分级判据（用不到的档位不必凑数，两档就写两档）：

| 档位 | 判据（满足其一即可） | 典型边界 |
|---|---|---|
| `critical` | 资金或数据的**不可逆**损失；或进程/服务起不来 | 多发少发付费道具、存档被写坏、启动即崩 |
| `high` | 玩家**可感知**的功能失效，且**没有自动兜底** | 活动入口打不开、奖励领不到且无法补领 |
| `medium` | 有兜底，但体验受损 | 需要玩家重启、需要人工补发、提示文案错 |
| `low` | 只影响可维护性 | 命名不一致、日志缺字段 |

**清单里只列前三档，`low` 一条都不列**（它不影响上线决策，列出来只会把清单拉长、
把真正要看的几条挤下去）。`low` 的发现仍要写进 `anomalies` 之外的地方就照旧处置，
只是不进「风险评估」这一节的清单。

**边界要就近靠严**：拿不准 `high` 还是 `medium`，问「玩家自己能不能绕过去」——能绕
（重开、重试、等下一轮）就是 `medium`，不能就是 `high`。

**`severity` 的四档只用于报告正文。** `anomalies[]` 里的 `severity` 仍然**只有
`critical` 与 `high` 两档**（达不到的不要进 `anomalies`）——两处口径不同，别把
`medium` 写进 `anomalies`，那一条会被服务端丢弃。

## 3. 「未取证的假设」单独成段，且不许定级

拿不到证据的判断**不是风险**，是**待办**。单独写一段「待取证假设」，每条写清：

- 假设的内容（你怀疑什么）；
- **要取得什么证据才能判断**（读哪张表、问谁、看哪份配置）；
- 在拿到证据之前，这一条**对上线决策意味着什么**（通常什么都不意味——这正是要说清的）。

**不要给它填一个等级。** 把「不知道」写成 `critical`，代价是**真正的 `critical` 失去
区分度**：读者分不清哪几条是已经查实的，于是要么全部当真（虚惊），要么全部打折
（漏掉真的那条）。假设段里出现的等级词，就是这一节写坏了的信号。

## 4. 清单怎么排：按系统模块归组，按严重度定序

清单**按系统模块分组**，形如：

```
【好友系统】
R1、【好友系统】好友申请列表在本轮改动后不刷新（严重）—— 位置：…；缓解：…
R2、【好友系统】好友赠送的每日次数在多端同时操作时会多发（高）—— 位置：…；缓解：…
【奖励发放】
R3、【奖励发放】领奖次数改为交付前记账，部分失败仍按成功返回（严重）—— …
```

四条规则，前两条是**硬约束**：

1. **每条以 `R#` 开头，编号在整节里连续且唯一，不按模块重开。** 平台要把复核裁决
   （`[F1]`…）落回正文的哪一条，唯一的锚点就是这个编号（服务端按 `R` + 数字去正文里
   找，再把裁决挂到它匹配上的那一条上）。写成「1、」「（1）」「第 1 条」都**不是**这个
   锚点：裁决会显示成「正文未编号」，读者再也对不上哪条被复核过。所以第二个模块的
   首条是 `R3` 而不是 `R1`。
2. **归组键是标题里的 `【系统或模块】`**，组标题就照原样写。标题里没有这个前缀的，
   按它点名的表 / 模块补一个（`【商城商品表】`、`【协议表】`）—— 不要为了凑组把不同
   系统的东西塞进「其它」。
3. **组内按严重度降序**（严重 → 高 → 中）；**组间按组内最高的那一条降序** ——
   哪个系统里有更重的，哪个系统排前面。
4. **篇幅不够时，「中」整档可以整体不列**，但必须留一句计数（「另有 3 条中等风险，
   未列在本节」）。**不能**按模块裁一半、也不能只裁中间那几条：裁了却不计数，读的人
   会以为那就是全部。

## 5. 排序与依据

条目**按后果从重到轻排**，并写出**为什么这一条排在最前**——排序依据本身要能被核对
（例如「排第一是因为它是唯一一条会造成不可逆损失的」）。

排序依据写在清单之前或之后都可以，但不能不写：不写的话，清单看起来就是一个平铺的
集合，读者无法判断「我只有时间验三条，该验哪三条」。

## 6. 写完之后自查

- 每条都能答全四件事吗？有没有哪条缺 `证据`（→ 挪进「待取证假设」）？
- 有没有哪条其实是**实现说明**（→ 删掉，或挪去「变更内容摘要」）？
- **编号是不是 `R#`、整节连续唯一**（模块之间**不重开**）？
- **有没有 `low` 混进清单**？裁掉「中」的时候留计数句了吗？
- 「待取证假设」是不是**真的没定级**？
- 用到的档位是不是都在这份文档的判据里？排序依据写了吗？
- 有没有把 `medium` / `low` 写进 `anomalies[].severity`（→ 那一条会被丢弃）？
