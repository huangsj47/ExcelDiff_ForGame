# 假阳性模式库

这份文件回答一个问题：**这个可疑的改动，究竟是真缺陷，还是合理设计？**

评审的输出会驱动真实的人工跟进与回归投入，所以「看起来像 bug」远不足以报出来。
下面先给处理原则，再给模式库。

## 处理原则：默认动作是「要上下文」，不是二选一

如果一个改动看起来像问题，但也可能属于下面任何一类情形：

- 阶段性屏蔽
- 半成品提交
- 联调保护
- 灰度开关
- 故意提前 return
- 故意注释掉的事件
- 故意保留的空实现
- 避免流程误入的临时护栏

那么正确的动作**既不是直接报错，也不是直接忽略**，而是**先去要能区分这两种解释的
上下文**：同提交的配套改动、开关状态、调用链、配置里的开关字段、注释说明。

只有在要到了这些上下文、且它们**共同证明这确实是缺陷**之后，才允许写进 `anomalies`。
要不到、也区分不了，就写进报告的「待确认」段落，并标 `confidence` 不足。

## 四类必须查调用链的经典模式

| 表面现象 | 为什么不能直接判 |
|---|---|
| 删除了函数，但仍有调用 | 可能是调用点也在同一提交里被删/被改，也可能是另一个同名重载；先看调用链 |
| 字段被删了，但消费方还在读 | 消费方可能已改为读新字段，或该字段本就有默认值兜底 |
| 事件被注释导致功能不触发 | 可能是**故意的阶段性屏蔽**，或该事件已由新机制接管 |
| 提前 return 导致后续清理不执行 | 可能是**故意跳过**某条路径；也可能清理逻辑已上移 |
| 「消费方读了某个常量/表/字段，而它不存在」 | **两侧可能不是同一时刻的状态** —— 定义与读取方常常在不同提交里落地。核对引用关系时两侧都要取**本批次内该文件的最新提交**（或干脆用同一条提交的 diff）。拿 A 提交的文件快照去比 B 提交的读取方，会把「中间那条提交刚把它补上」误判成悬空引用 |

这几类的共同点是：**只看一处代码永远判断不了**，必须看同提交的配套改动与运行入口。

### 「悬空引用」这一类为什么会误报（2026-09-20 实测）

那次周版本分析里报出一条 `high`：「`SeasonRankCfgMod.getInheritRank` 读取不存在的常量表
`SeasonRankConst.SeasonInheritRank`」。核对下来是**假阳性**，三条改动落在同一天、同一条
业务线上：

| 时刻 | 提交 | 发生了什么 |
|---|---|---|
| 14:21 | `226470e6` | `SeasonRankConst.lua`（245 行）—— **此时还没有** `SeasonInheritRank` |
| 16:01 | `91bcc3439` | **补上了** `SeasonInheritRank` 映射表 |
| 19:57 | `436fe64cdd56` | `getInheritRank` 出现，读的正是它 |

模型取文件快照时点了 14:21 那条提交（`file_diff 226470e6 …`），取读取方时点了 19:57 那条，
于是把一个**早已被补上**的常量判成不存在。定级 `high` 的结论会直接进人工跟进清单。

**动作**：核对「A 读 B，B 不存在」之前，先确认 B 的读取点与定义点取的是**同一个时刻**
（都用本批次内该文件的最新提交）；两边分属不同提交时，先把两次改动按时间排一遍 ——
定义晚于读取点，才是真悬空。

### 「凭印象补的名字」比空泛表述更危险（2026-09-20 实测）

同一次分析里另一条 `high` 报的是「【跨进程 ID】teamId 编码格式重写，但新旧守卫位同值，
旧格式 id 被解成伪属主」，证据写的是「`NEW_FORMAT_FLAG = 1 << 62` 被删除、
`TEAM_ID_MARKER = 1 << 62` 被新增，两者取值完全相同」。核对下来：

* `NEW_FORMAT_FLAG` **全树不存在**（任何提交里都没有过）；
* `TEAM_ID_MARKER = 1 << 62` 在**父提交里就逐字相同**，`decodeTeamId` 也一行没改；
* 那条提交真正改的是 **handoff 的版本号**（`TEAM_HANDOFF_FORMAT_VERSION 4→2`、
  `MATCH 5→3`、新增 `GAS_HANDOFF_FORMAT_VERSION = 4`）。

**「名字记不清」与「空泛表述」不一样**：空泛表述一看就知道不能跟进，而一个**具体但不存在**
的名字读起来和真证据一模一样，会直接把假阳性送进人工清单，还会让跟进的人去追一个不存在的
符号（排查成本反过来高于不报）。

**动作**：写进 `evidence` 的每个符号名、取值、行号，都要能在**你这一轮真的取回来的**
diff 或文件内容里逐字找到（不是「我记得有这么个常量」）。引用跨提交的对比时，
两边的取值都要分别指到具体提交。找不到原文，就把这一条降级成「待确认」，
不要给它 `high`。

## 领域假阳性模式

除了上面这些通用模式，本项目还有一批「看着危险其实是正常操作」的改法。**遇到它们
先要上下文，不要直接报**：

- **配置表里某个 ID 段整段被注释或清空**：可能是本期不外放，走的是分支表；先看是否
  存在对应的分支表文件，以及是否是阶段性屏蔽。
- **某个字段全表被填成同一个默认值**：可能是有意的临时兜底（等程序支持后再回填），
  不一定是填错。
- **活动时间被设成过去或很远的未来**：可能是**临时关闭**手段，也可能是灰度开关。
- **新增了一条看起来「无消耗且无限制」的奖励途径**：先确认它是否只对特定条件开放
  （新手、回流、首次），或是否由服务端另行限制。
- **删除了一个函数或类，但同名逻辑出现在别处**：可能是重命名或重构，不是删功能。
- **配置里出现了 `custom` 类型的字段**：这是**规范上不推荐**的写法（容易配错、不便
  检测），值得在报告里作为「建议」提出，但**它本身不是缺陷**，不要进异常清单。
- **数值看起来异常小或异常大**：先确认单位与量级（毫秒还是秒、基础值还是倍率），
  再判断是不是填错。
- **某个限制数值被放宽**：可能是策划有意调整体验，需要的是**回归其它限制是否仍然
  有效**，而不是断言这是个 bug。

## 归因护栏

下面这些推论都是**无效**的，项目复盘里被反复点名：

- 操作次数更多 **不等于** 互动更丰富——可能是重复触发或失败重试。
- 单次时长更短 **不等于** 操作更顺手——可能是被取消、截断或快速重开。
- 结果相近 **不等于** 排除了问题——可能只是问题被掩盖。
- 没有发生交互 **不等于** 玩家拒绝——可能是没看到、没进入范围或日志缺失。
- 缺少对象、阶段、完成度、奖励或前后状态时，**不要**把通用现象写成具体根因。
- **时间接近不等于因果**。两件事在时间上挨着，只说明它们是关联线索，不能写成
  「A 导致了 B」。
- **同名物件不等于同一实现**。同名美术物件可能因运行时组件不同走不同流程；没有
  实际配置、日志或复现证据时，不得仅凭名称断言技术实现或根因。

## 信息缺口下的降级话术

置信度不足时**不许伪造结论**。按下面的方式降级，并在报告里显式标注：

| 情况 | 该怎么写 |
|---|---|
| 需求描述或文档本身冲突、不清晰 | 输出「待确认问题清单」，并**降低结论强度**；不要替它选一个解释 |
| 只有需求、缺少实现 | 输出测试准备草案，并标注**「尚未结合最终实现验证」** |
| 需求文档或关联信息缺失 | 仍然给出分析结果，但必须标注**「信息缺口」**与**「谨慎使用」** |
| 对影响面判断的置信度不足 | 不得给出强结论，写成**「建议 + 待人工确认」** |
| 数据不足以支撑某个维度的判断 | 在 `dimensions` 里写 `hit: false`，并说明**是「不适用」还是「信息不足」**——两者含义不同，不要混为一谈 |

## 报出来之前再问自己三个问题

1. **证据能不能指向具体的东西？**（文件、字段、ID、行、提交）指不到就不要报。
2. **如果这是故意的，会是什么理由？** 想不出理由也不代表就是缺陷，只是说明还需要
   上下文。
3. **这条报出去之后，跟进的人会因为找不到问题而浪费时间吗？** 会的话，就降级成
   「建议」或「待确认」。
