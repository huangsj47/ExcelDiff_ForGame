# 测试范围与回归面

本文件回答的是**另一个问题**：不是「这个改动有没有缺陷」，而是「这份改动要安排多大
范围的测试、压测与回归」。

## 这份文件是干什么用的（先读这一段）

- 它喂给报告的 **`# 测试建议`**、**`# 回归建议`**、**`# 上线与回滚关注点`** 三节。
- **它不是异常清单。** 从这里得出的结论是「要测什么、要回归到什么程度」，**除非改动
  本身另有缺陷证据，否则不要写进 `anomalies`**。把「这个模块应该压测」当成异常报出来，
  正是本 skill 的精度优先原则要避免的那种噪音。
- 与 `incident-checklist.md` 的分工：那份是「看到什么改动 → 要警惕什么**事故**」（缺陷
  模式，进 `anomalies`）；这份是「看到什么改动 → 要安排什么**测试**」（范围，进报告
  正文）。两者都源自同一份项目事故清单，条目编号（`IDxx`）与事故计数可以互相引用。

## 数据来源与使用说明

- 规则反推自项目事故清单里**尚未被缺陷模式表覆盖**的那部分条目。括号里的 `IDxx` 是原始
  条目编号，`计数 N` 是那条对应的真实事故次数；计数按唯一项去重，计数为 0 的条目仍然
  有效，只是不作为优先级依据。
- 项目知识包提供**事实**（哪些模块算重要、压测参照哪套数据、有哪些平台与渠道）；
  本文件只提供**与项目无关的触发规则**。具体数值、模块清单、渠道列表以项目知识包为准。

## G. 回归范围触发规则

看到下面这些改动时，**回归面比改动面大得多**——改动只碰了一个函数或一个字段，但要回归
的是整条业务链。这是事故清单里踩得第二多的一类（发奖代码迭代，计数 12）。

| # | 看到这样的改动 | 要回归到什么程度 | 来源 |
|---|---|---|---|
| G1 | **发奖代码做了迭代** | 回归**所有限制**与**发奖主流程**——不是只回归这次改的那条奖励 | ID33（计数 12） |
| G2 | **老活动被复用或迭代** | 回归活动主流程 + **奖励相关的全部用例** | ID23（计数 8） |
| G3 | **单服活动改为跨服活动** | 全部用例回归（服务端与客户端两侧） | ID94 |
| G4 | **充值相关改动** | 全部用例回归，含各渠道包 | ID165 |
| G5 | **活动的基本模块**（组队、战斗、抽卡等）有修改 | 每个活动的**开启前 / 开启中 / 开启后**各回归一次这些基本模块 | ID160 |
| G6 | **修改了某个等价类** | 回归它的**并行等价类**仍然正常（只测改的那一类是常见漏测） | ID220 |
| G7 | **限制条件被修改** | 除了新条件本身，还要回归**其它限制仍然有效**，以及主流程 | ID219 |
| G8 | **修复了某个分支用例的 bug** | 覆盖主流程 + **其它并行逻辑分支**的用例 | ID206 |
| G9 | **客户端相关改动** | 需要覆盖项目支持的全部平台（Windows / 安卓 / iOS / 页游等），不能只测一个 | ID92 |
| G10 | **迭代了地图数据结构** | 回归**大批量创建与销毁**，以及所有复用该场景的用例 | ID267 |
| G11 | **修改了地图阻挡** | 按项目维护的常规路线列表回归一遍 | ID142 |
| G12 | **新增或迭代一个功能** | 先判断**跨服是否要禁止**这个功能；不禁止就要测跨服情况下使用它的表现 | ID16 |
| G13 | **任何功能改动** | 同时考虑**新服与老服**两种情况（新服的初始数据与老服的历史数据不同） | ID173 |
| G14 | **任何修改** | 先确认**当前运营中的分支**是否也需要同样的修改（只改主干是常见漏项） | ID291 |
| G15 | **内容从一端移植到另一端**（国服↔海外版） | 全回归 | ID70 |
| G16 | **系统迭代后** | 测**服务端开关**是否真的有效 | ID138 |
| G17 | **迭代或新增了重要模块** | 上线前至少压测过一次（见 H 节），有条件每周回归 | ID66（计数 19） |
| G18 | **原定外放的功能取消放出** | 把系统时间设到活动时间，到游戏中确认商品、日历、活动等**确实没有放出** | ID198 |
| G19 | **可以重复进行的活动、任务、副本** | 要测**多次完成**的情况，关注能否正常继续玩、奖励是否每次都正确 | ID98 |
| G20 | **充值相关的任何改动** | 除了功能回归，还要用**渠道下载的整包**再测一遍 | ID148 |
| G21 | **接入了外部充值或支付系统** | 要测被访问方**响应超时**的情况，确认扣的钱与到账的代币都对得上 | ID59 |
| G22 | **接入一个新的渠道或平台** | 要严格按渠道接入流程走，并用**新账号与老账号分别**登录与支付 | ID177 |

## H. 压测的触发条件与量级

「重要模块要压测」只是一半，另一半是**照着什么量级压、在什么环境压**——压测失败最常见
的原因不是没压，而是压的量级与线上不对应。

| # | 看到这样的改动 | 压测怎么做 | 来源 |
|---|---|---|---|
| H1 | 登陆、顶号、匹配、战斗、邮件、排行榜、全服推送、充值、好友、反外挂等模块新增或迭代 | 参照**外服的在线数、最大并发数、数据库条目数量、玩家数据**来确定量级 | ID64（计数 8） |
| H2 | 压测环境 | 软件配置尽量与外网一致；先确认外服的**最低硬件配置**，据此判断能否负荷 | ID67、ID62 |
| H3 | 每次压测 | 建立**历史数据对比机制**：CPU、内存等数值大幅增加就要追究原因 | ID221 |
| H4 | 存档类数据（邮件、排行榜、好友、申请列表） | 按**策划给出的最大值**压测 | ID65（计数 6） |
| H5 | 玩家数据以及其它存在大量对象的数据 | 做**大批量存档**压测 | ID231 |
| H6 | 新项目上线 | 通过数据读写压测数据库瓶颈（IO、内存、CPU、网卡流量），并保证**到达瓶颈值的 80% 时有报警** | ID256 |
| H7 | 用了缓存 + 持久库双存储的项目 | 必须测**删掉缓存后完全从持久库恢复**的压力 | ID238 |
| H8 | 服务端收发协议 | 收发缓存都要有上限：客户端**只发包不收包**测发送缓存，**频繁发包**测接收缓存 | ID111 |
| H9 | 每个集群 | 要有在线玩家上限，达到上限后玩家**排队等待**进入 | ID275 |
| H10 | 登陆压测 | 混入退出登录、顶号登陆、服务器踢人等**异常路径**，不只有平稳登陆 | ID277 |
| H11 | 匹配压测 | 统计匹配时长；按外服的**分数段分布**构造压测数据 | ID63、ID149 |
| H12 | 无法按线上角色比例等比缩小压测服 | 对相对富余的角色，调用特殊接口给到与线上同等的输出压力 | ID287 |
| H13 | 全服 GM 指令 | 要压**大量玩家离线**情况下的表现 | ID145 |

## I. 特定领域的测试条件

这些条目的共同点是：**条件不满足就根本测不出问题**——用例写了、执行了、都是绿的，但
因为环境或角色配置不对，缺陷根本没有被触发。

**多人条件**

- 可以组队（多人）进行的任务、战斗、副本、比赛，**至少要两个人**去测，并分别关注**队长与
  队员各自的限制与表现**。（ID22，计数 4）
- 多人并发挑战的 boss，要测**被不同人同时击杀**的情况。（ID103）
- 可有多支队伍参与的玩法，确保每个细分角色**至少 2 支队伍**；发奖相关要验证到**每一个**
  参与者。（ID273）
- 会产生多个虚拟场景的任务 / 活动 / 副本，场景销毁测试要**至少有 2 个场景**同时参与。
  （ID278）

**时间条件**

- 通过修改游戏内时间偏移来测**每个流程的触发**，而不只是测一个时间点。（ID96）
- 活动开启、阶段跳转、结束时间，都要测时间偏移 **-1 / 0 / +1**。（ID104）
- 跨越多个阶段的玩法，**每个阶段都要测**。（ID159）

**跨服与跨进程**

- 多进程之间切换玩法，要考虑**数据迁移的完整性**。（ID99）
- 跨服活动要测：携带领奖标志或满足领奖条件时，会不会**在跨服场景下错误发奖**。（ID257）

**包裹与物品**

- 发放奖励（主动领取或被动发放）以及任何会获得物品的操作，都要考虑**包裹满**的情况。
  （ID199）

**客户端与平台**

- 手游相关用例**一定要用真机**测试过。（ID91）
- 客户端模型要在**各个画质档位**下都测过。（ID141）
- 商品热更新要在**不退出客户端**的情况下测。（ID139）
- 有网页端的项目，相关改动要考虑**清除缓存**之后的表现。（ID68）

**海外版**

- 确认海外服是否访问国内接口，并确认其网络延迟是否合理。（ID71）
- 夏令时切换前，把系统时间设到切换前后，回归主要系统。（ID163）

**比赛与排行榜**

- 参赛人数为 0，或人数不足无法开战。（ID147）
- 参赛者资格被 GM 取消的情况。（ID35）
- 轮空。（ID188）
- 一方或双方缺席。（ID189）
- 平局。（ID207）
- 全部参赛者同分。（ID109、ID214）

**战斗与技能**

- 从 debuff 中回复的情况。（ID143）
- buff / debuff 附加属性的**下限与上限**。（ID144）
- 回合制游戏同时切入两场战斗。（ID137）

**GM 指令与工具**

- 踢人指令要测**登陆尚未完成**时踢人。（ID146）
- 需要能在**不重启服务器**的前提下设置游戏时间的 GM 指令来辅助测试。（ID282）

**活动**

- 重要活动场景的离开操作要加**二次确认**。（ID25）
- 有期限的活动，其**流程触发接口与领奖接口**都要加时间限制。（ID265）

## J. 奖励内容的核对方式

「发奖」类的漏测很少是没测，而是**测错了对象**——看了客户端的奖励提示就认为发对了。

- 核对**包裹中实际获得的类型与数量**，不要只看奖励提示或客户端提示。（ID81 计数 5、
  ID86）
- 宝箱之类的**奖励组合**，要真的**使用并确认**内容。（ID34）
- **限量奖励**要多次达到获奖条件，确认不会**超过限制领取**。（ID84 计数 3）
- 商城物品要**多次购买**，确保**每一次都扣费**。（ID274）
- 同时发给多人的奖励，要划分等价类：准备多个**无法领取**的号和多个**可获取各阶奖励**的
  号，确保一次发奖中**每个号**都拿到正确的奖励。（ID271）
- 消耗材料都是**绑定**物品时，一般只能产出绑定物品。（ID51）
- 新手期的珍贵奖励要**绑定**或**提高获得门槛**。（ID85）
- 删除邮件后**顶号**，确认不会重复收到邮件。（ID210）
- 新增贵重物品时，记得加入**投放报警**检测。（对应 `incident-checklist.md` B19）

## K. 外放与维护流程的用例

外放环节的检查项大多是**一次性的动作**，漏了就没有第二次机会。

- 服务器对外开放后，确认**外部玩家可以登录所有服务器**（不是只登录成功一台）。（ID78）
- 自己负责的内容外放后，**第一时间在外服跟进**。（ID93）
- 开服后建议回归**充值**等重要系统。（ID224）
- 开服后一段时间内观察 CPU 与内存，出现异常繁忙或异常增长要及时跟进。（ID184）
- 确认本周要用的**客户端资源都已放出**。（ID73）
- 验证服务端同步脚本的**版本号**。（ID46）
- 用外服客户端下载外服补丁，验证**服务器列表**正确。（ID154）
- 验证至少一个**本周维护新增的内容**。（ID48）
- 新服开服后，通过排行榜等手段确认服务器**确实清过档**。（ID136）

**热更（hotfix）专项**

- 全服推送后，**逐台**验证每个服务器都更新成功。（ID74）
- 服务端与客户端的 hotfix 都要**查 log 确认生效**之后，再做外服验证。（ID77）
- 外放补丁要用**外网客户端**测试，不要用内网客户端。（ID75）
- hotfix 过程中发现 bug，修完要**再次测试通过**才能外放。（ID182）
- hotfix 需要 QA 测试并同意才可外放。（ID54 计数 5）
- 无法黑盒验证的 hotfix 配置，要选外服的一个进程验证**内存数据**，并验证指令输入与返回
  结果。（ID230）
- hotfix 修 bug 要**取回外服数据**做兼容测试。（ID172 计数 2）
- 测试完成后要及时**删除动态代码**。（ID222）
- 与开发确认版本库里**新同步的文件**与预期相符。（ID41）

## L. 可以直接提给开发的左移建议

下面这些在评审代码 diff 时可以直接作为建议提出（**它们是改进方向，不是本次改动的缺陷**，
所以放报告正文，不要进 `anomalies`）。

- 引擎侧要做好兼容：坐标被设置到边界外时，不应导致内存越界或宕机。（ID247）
- 文档型数据库存档要覆盖 key 含 `.` 或为整数的情况。（ID236）
- RPC 协议接口做好兼容，**超过一定大小自动分包发送**。（ID179）
- 周期变量的设置与读取**调用统一接口**，减少开发与测试难度。（ID258）
- 延迟执行类组件要支持**「不可被打断」**选项，减少配置填写失误。（ID227）
- 客户端增加**每秒接收协议超量**的报警，便于定位问题。（ID229）
- 重要玩法要有**容灾措施**：用定时检测去补上未完成的操作。（ID87 计数 3）
- 重要系统与不重要系统**分库存储**。（ID126）
- 搭建外服监控与报警体系（函数耗时火焰图、CPU 与内存），并定期确认。（ID295）
- 使用**代码覆盖率工具**，防止回归覆盖不全。（ID248 计数 3）
- 容器化部署的外服环境要注意**自动缩容**可能杀掉正在生成补丁清单的服务。（ID293）
- 与外部平台合作的项目，要确认**平台侧的 QA 已跟进**并加入沟通群，老活动每次新开发都要
  重新确认一遍。（ID276）

## 刻意没有收录的条目

原始清单里有少数条目**不适合放进变更评审**，列在这里是为了让覆盖率的缺口是**已知的**，
而不是被误当成漏项：

| 条目 | 为什么没收 |
|---|---|
| ID80、ID169 | 依赖项目内部的**具体工具与产品名**。这类事实属于项目知识包，不该写进项目无关的通用 skill |
| ID89（关注测试过程中的 traceback）、ID135（备份分批低频进行）、ID156（服务 reload/restart 后确认进程重启成功）、ID255（运维变更配置要提前邮件通知）、ID266（不同级别代币的购买订单分队列处理） | **纯运维动作或测试执行习惯**，与「看一份 diff 判断风险」没有可判定的关系。写进来只会稀释真正可执行的规则 |
| ID286（多端 patch 测试环境） | 语义已被 `SKILL.md` 的 `version_branch` 维度覆盖（多端发布要**分端**验证补丁下载与生效），只是没有逐字引用编号 |
