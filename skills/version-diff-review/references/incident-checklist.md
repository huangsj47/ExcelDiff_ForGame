# 事故清单对照表

本文件把项目历史事故复盘**反推成「看到什么改动 → 要警惕什么事故」的规则**，供评审
变更时逐条对照。

这些规则是**通用的**——它们描述的是「配置驱动的游戏项目里，什么样的改动会出事」，
不依赖任何单个项目的目录结构或编号方案。**项目专属的事实**（配表 ID 怎么编、表怎么
命名、系统怎么划分）由项目知识包提供，会在分析时一并注入。

## 数据来源与使用说明

规则反推自项目的事故清单表（273 条唯一检查项，**去重后合计 518 次事故命中**）。使用时
有几点必须知道：

- **括号里的 `IDxx` 是原始条目编号，`计数 N` 是该条对应的真实事故次数。** 计数越高，
  说明这条踩得越多，越该优先检查。计数最高的几条是：表格 diff 确认（22）、重要模块
  压测（19）、协议测试（16）、边界测试（15）、协议防刷（14）、发奖代码迭代要全回归（12）、
  不要只信表（11）、服务器内存与存档（11）。
- **不要把这些计数加总当成「总事故数」之外的另一个指标**：原始表的 `总事故数` 列在同一个
  ID 重复出现时是同一个值，按行求和会把高频条目重复加权（408 行直接求和得 776，去重后
  是 518）。**本文件一律用去重后的口径。**
- **计数为 0 的条目仍然有效**。它们的语义不明确（可能是「高风险但侥幸没发生」，也可能是
  「未统计」），所以**不作为优先级依据**，但规则本身该查还是要查。
- 原始清单只有「研发期 / 运营期」两档时期，**没有更细的发现阶段**（测试/灰度/线上）。
  不要假设有。
- 原始清单里的「预防措施」列**整列为空**，不存在可引用的预防措施文本。
- **本文件只收录「看到什么改动 → 要警惕什么事故」的缺陷模式。** 清单里另一半是
  「要安排什么测试与回归」（回归范围、压测、领域测试条件、奖励内容核对、外放流程），
  在 `test-scope-and-regression.md`，**那些是测试范围而不是缺陷，不要写进 `anomalies`**。

## A. 数值与边界

| # | 看到这样的改动 | 要警惕的事故 | 来源 |
|---|---|---|---|
| A1 | 出现**等级 / 时间 / 积分 / 次数**等限制数值 | 边界测试缺失。要测**临界值减一、临界值、临界值加一**；如果是新引入的变量，还要测**该值未被初始化**的情况 | ID15（计数 15） |
| A2 | 出现**分级 / 分段公式**（不同等级段有不同处理） | 只测了一段，其它等价类没覆盖 | ID15 |
| A3 | 出现**时间点**配置（例如阶段切换写死在 12:00:00） | 定时器可能几十毫秒到几秒才 tick 一次，**错过精确那一秒阶段就切不过去**。看有没有越点后的补救措施 | ID101 |
| A4 | 出现**除法**或**先乘后除** | 除数为零；以及本来不会溢出的数据，因为先乘后除而溢出 | ID12、ID254 |
| A5 | 数值可能取**负数或特别大** | 玩家改协议把消耗改成负数刷奖励；数值特别大导致服务端运算溢出 | ID21（计数 2） |
| A6 | **多期活动**（充值返利、回流、节日） | 往期数据影响本期领奖。样本要覆盖：无往期数据 / 有往期数据未领奖 / 有往期数据已领奖；若活动中途迭代或修 bug 不完全导致存储结构不同，还要覆盖**修改前与修改后的数据** | ID170（计数 4） |
| A7 | **限次奖励 / 限次玩法** | 奖励限制的刷新时间与任务自身的刷新时间不一致（任务非零点刷新、奖励限制零点刷新）时，限制需要**加大**；要测刷新点减一/零点/加一 | ID95、ID240、ID241 |
| A8 | **限时领取**（领取时间限时或领取代币限期） | 要测过期时间减一、当天、加一 | ID243 |
| A9 | **积分 / 代币 / 奖励 ID 的兑换与过期时间** | 必须**晚于活动结束时间**，否则活动还没结束奖励就过期 | ID100（计数 2） |
| A10 | **次数限制被调整** | 任务、副本、活动的次数调整后，**奖励限制次数也要相应调整**（容易漏） | ID203 |
| A11 | 活动有次数限制，且**失败也给奖励** | 失败不累计次数时，若失败很容易，玩家可以刷失败奖励 | ID102 |
| A12 | **领取限制被设成等于获取限制**（礼包类） | 礼包可以累积多日一次使用，简单等同会导致触发限制反而领不到奖励 | ID208 |
| A13 | 出现**无消耗且无限制次数的奖励获取途径** | 原则上不允许，除非是非常低效的纯经验奖励 | ID237（计数 2） |
| A14 | 数据出现**先加后减**或**叠加语义** | 有历史数据时容易出现「叠加变替换」；无历史数据时容易遗漏初始化，极端情况是排序死循环 | ID284 |
| A15 | **存档类数据**（邮件、排行榜、好友、申请列表） | 存档数据要有上限，否则占用越来越大，消耗过多存储与内存 | ID53（计数 2） |
| A16 | **单条数据体积变大** | mysql / mongodb 有强制的单条记录存储限制；文档存档虽无限制，但过大会让读写都很耗时 | ID178、ID226（计数 2） |
| A17 | **奖励发放的版本与数量** | 要用正常流程验证每一条奖励，**奖励发放内容不可抽样验证** | ID32（计数 6） |
| A18 | 奖励物品在商城有售 | 要根据售价核对奖励发放是否符合策划估值 | ID193 |
| A19 | 涉及**真实货币购买**的接口迭代 | 需要在**每个渠道包**分别测试 | ID289 |
| A20 | 购买逻辑改动 | 要测身上货币为「价格减一 / 价格 / 价格加一」三种情况，关注包裹内商品与剩余货币正确；折扣品每个折扣都要重复这些用例 | ID228 |
| A21 | 奖励可以领取 | **奖励要有合理的领取限制**。「能领」和「能无限领」之间往往只差一个判断 | ID36（计数 6） |
| A22 | **场景内会刷出活动怪物或大量对象** | 要有数量上限，否则场景性能与产出都会被拖垮 | ID119 |

## B. 代码：奖励、协议、存档

| # | 看到这样的改动 | 要警惕的事故 | 来源 |
|---|---|---|---|
| B1 | **发奖代码里，给奖励在前、扣代币或置领奖标志在后** | **无限刷奖励**——中间代码一旦抛异常，扣除代码不会执行。原则是**先扣后给** | ID37（计数 9） |
| B2 | **领奖标志或已领取状态没有落盘** | 重登后限制失效，可重复领取。要用指令核对服务端内存与数据库数据 | ID157（计数 2）、ID260 |
| B3 | **发奖 / 扣费逻辑是异步的** | 检测虽然做了，但标记要「成功之后」才写，异步期间玩家可以**无间隔连发多次**，全部成功。必须用无间隔连发同一协议来测 | ID19（计数 14）、ID190 |
| B4 | **客户端触发的重要操作**（奖励、商城、充值、改属性） | 很多逻辑只在客户端做了预判、服务端没做限制，玩家可以绕过客户端非法牟利。要测：无间隔连发、把协议里的值改成不合理数值（如花费改成 -1、物品不存在）、不满足条件时发送领奖协议 | ID10（计数 16）、ID150（计数 4）、ID20 |
| B5 | **条件检测 + 异步操作** | 条件检测必须在**异步操作的最后一步再全部做一遍** | ID292 |
| B6 | **改动了已有接口的签名或返回** | 上层老调用拿不到同样的输出，需要兼容现有上层调用 | ID290（计数 4） |
| B7 | **数据库查询条件** | 针对个人或某个群体的查询，容易**漏掉用户维度限制** | ID272 |
| B8 | **分批处理函数**（例如全服发邮件） | 只测了第一批是常见漏测，**第一批与第二批的逻辑可能不同**。要测 x-1、x、x+1、2x-1、2x、2x+1 | ID88 |
| B9 | **新增数据库表或新增查询字段** | 没有加索引 | ID106（计数 5） |
| B10 | **RPC / 协议打包解包**改动 | 数据量超过 MTU 要分包，而部分网络节点禁止分片重组，导致发包失败；解包函数遇到截断字节会 crash。健壮性做法：造一个正常包，然后从末尾逐字节截断 | ID180、ID270（计数 2）、ID269（计数 2）、ID285 |
| B11 | **客户端发往服务端的协议缺少频率限制** | 全服广播、数据库查询等被高频调用会压垮服务器 | ID234、ID294 |
| B12 | **访问公司外部接口**（邮箱、HTTP、FTP、SMTP） | 没有用异步会阻塞；没处理错误返回与长时间不返回会造成雪崩。可以通过搜索代码里的 http、ftp、smtp 关键字发现这类调用 | ID18、ID217 |
| B13 | **公司内部公共 API 调用** | 要有 QPS 限制、超量返回错误码，并与接入方商定合理的超时返回时间 | ID218 |
| B14 | **新增外部合作方发奖** | 完全信任合作方、内部零限制会导致刷奖励。**必须加自检验（单人 + 总量）** | ID176（计数 3） |
| B15 | **抽奖结果异步 / 分步揭露中奖特征** | 期间玩家可以修改抽奖属性，导致符合特征的人数超出预期，出现刷奖励或该中奖的没中 | ID168 |
| B16 | 出现**使用限制的物品** | 限制要在**使用的最后一步**做好，只控制获取不够；还要测使用条件不满足时物品没有被错误扣除 | ID155、ID114、ID116 |
| B17 | 获取**可叠加物品** | 要考虑新物品与已有物品叠加后超出叠加上限、且物品栏已满、没有空格子存放多出部分的情况 | ID251 |
| B18 | 修改了**物品使用时间** | 要确认客户端描述也改了 | ID115 |
| B19 | 新增**贵重物品** | 记得加入每日物品投放报警检测 | ID82 |
| B20 | 新增物品 | 要测试它的用途 | ID38 |
| B21 | **热更时用函数赋值的方式修改服务器函数** | 部分脚本引擎的函数赋值改的是函数内部的字节码，而不是替换函数本身，**所有子类都会跟着受影响**。热更方案要确认用的是替换还是改写 | ID195 |
| B22 | 提交里出现**临时硬编码或本地调试代码** | 上线后仍会生效。硬编码需求要限制生效时间；调试代码提交要提单备忘 | ID281、ID122（计数 5） |
| B23 | 引擎版本修改 | 需要找引擎团队做兼容性回归 | ID120 |
| B24 | 出现**热更新支持**问题 | 要测一个系统的代码和配置文件是否支持热更 | ID288 |
| B25 | **删除或修改老接口** | 程序员应 grep 后告知 QA 回归范围（回归范围指要回归的系统或模块，详细用例设计是 QA 的责任） | ID123（计数 4） |
| B26 | 开发了**需求单以外的功能** | 需要通知 QA 测试 | ID213 |
| B27 | 关键流程的**日志与自检** | 重要系统的自检有误要记录 error log；要做好 log 分级 | ID216 |
| B28 | 逻辑代码与数据**没有分离** | 开发时应做到逻辑代码和数据分离 | ID164 |
| B29 | 新活动**用了旧变量或旧表 ID** | 玩家旧数据残留会导致新活动逻辑异常 | ID57（计数 4） |
| B30 | **多步确认流程**（先选、再确认、最后提交） | 所有的限制要**在最后一次确认之前**全部再判一遍；只在前面的步骤判过，中间状态一变就绕过去了 | ID90 |
| B31 | **非核心协议**的收发 | 非核心不等于可以不校验：**每个值都要判合理上限与下限** | ID245 |
| B32 | **GM 指令、调试入口或内部工具**的界面 | 环境校验（只允许内服）**必须在服务端做**，不能只靠客户端不弹出界面 | ID50 |
| B33 | 计费允许**负点或欠费** | 要有措施保证负点不会过大（同一账号多服登录会放大这个问题） | ID201 |

## C. 版本、分支、hotfix、外放

| # | 看到这样的改动 | 要警惕的事故 | 来源 |
|---|---|---|---|
| C1 | **hotfix 只打在主干、没打 release**（或反向） | 「hotfix 不能只在 trunk 做测试，还需要在 release 分支做测试」 | ID40 |
| C2 | **同一个文件被多次 hotfix** | 最新的 hotfix 可能**改坏之前的 hotfix**，要回归之前 hotfix 的内容 | ID194 |
| C3 | **hotfix 同时更新配置和代码** | 两者之间有时间差。要么同时完成，要么定好顺序并保证兼容：先代码后配置则新代码要兼容老配置，先配置后代码则新配置要考虑老代码兼容 | ID158 |
| C4 | **未外放的内容提前合回主干** | 版本污染 | ID127（计数 2） |
| C5 | **release 分支的协议与开发中的协议混在一起** | 需要分分支管理 | ID181 |
| C6 | **全服同步代码** | 多次同步会相互覆盖——历史真实事故：值班人员更新全部代码（版本 1）的过程中 SA 正在逐台更新，此时程序提交了版本 2 并要求更新，机器 S 被更新为版本 2，随后版本 1 的更新又覆盖了它。要求**在同一台服务器上同步** | ID204、ID42（计数 3） |
| C7 | **同步脚本没有过滤测试代码或测试脚本** | 测试代码被同步到外服 | ID196、ID197 |
| C8 | **大版本一次性推全服** | 「非服务器组的架构先同步一个服务器，线上测试并观察一下再同步所有服务器」 | ID43（计数 9） |
| C9 | **补丁上传后直接发布** | 上传的补丁可能不等于之前测试通过的那个。要用内部环境把补丁下载下来复验，并校验 MD5 | ID45（计数 4）、ID47 |
| C10 | **资源被删除** | 要测「重新在 app 下载整包后打补丁」的完整链路 | ID140 |
| C11 | **新手阶段用到的新增资源及其依赖资源** | 必须存在于**首包**而不是后续补丁里。可以通过扫描相关表格、解压首包资源来自动检测 | ID283 |
| C12 | **客户端资源或客户端 bug 修复** | 补丁打出后客户端相关内容要做主流程回归——平时用桌面版调用编译后文件测试，无法保证补丁内容与测过的一致 | ID174 |
| C13 | **有补丁更新** | 要测下载全新客户端再更新补丁的情况；并根据用户覆盖机型选内存最小的那台做补丁回归 | ID242、ID211（计数 2） |
| C14 | **正式服发布前的最后修改** | 开服前拉出 gray 或 release 分支后的修改，需要在**主干和该分支都测试过** | ID235、ID187 |
| C15 | **新增或迭代重要模块** | 登陆、顶号、AOI、充值、匹配、战斗、邮件、排行榜、交友、全服推送、反外挂等，上线前至少要压测过一次，有条件每周回归 | ID66（计数 19） |
| C16 | 出**整包** | 要回归历史账户是否存在、服务器列表是否正确 | ID121、ID162 |
| C17 | 静态扫描发现 diff 里**引用了高风险函数** | 这通常意味着有压测需求 | ID250 |

## D. 环境、存档与数据迁移

| # | 看到这样的改动 | 要警惕的事故 | 来源 |
|---|---|---|---|
| D1 | **系统迭代 / 老系统改造** | 必须**取回外服的老数据**（存盘数据或老配置文件）回内服测试；等价类要覆盖「有该系统数据」与「无该系统数据」 | ID17（计数 4）、ID186 |
| D2 | **hotfix 修复外服 bug** | 外服数据会**兼有「未初始化过」和「初始化过」两种**，内服要同时覆盖 | ID17 |
| D3 | **活动相关代码热更新后** | 要测热更后活动能否正常继续 | ID268 |
| D4 | **关键永久数据**（任务状态、活动进程、玩家属性改动、领奖标志） | 是否被正确存盘；引擎应该有关机前检测未存档关键数据并自动存档的功能 | ID260、ID261 |
| D5 | **活动、任务、副本可以重复进行** | 要关注**需要清除的数据是否清除了**（内存中和存档中） | ID185（计数 2） |
| D6 | **任务或副本超时结束** | 要给玩家增加的专用 buff、专用消耗减免等关键变量是否被清除和重置，否则玩家获利 | ID24 |
| D7 | **跨进程或多进程操作** | 内服只布单进程会导致跨进程逻辑永远测不到，**至少要布 2 个进程**；操作可能涉及多个进程的，要覆盖同进程与跨进程两种情况 | ID191、ID192、ID130（计数 4） |
| D8 | **跨服 / 中心服活动** | 需要**同时**更改本服、跨服、中心服等相关服务器的时间来测流程触发 | ID215 |
| D9 | **活动首次放出时间晚于活动周期起始时间** | 要保证数据初始化能完成 | ID223 |
| D10 | **服务器重启** | 某个玩法的**非玩家数据**是否被正确 load 到内存中 | ID252 |
| D11 | **玩家离线时发放非主动领取的奖励** | 要确保离线玩家能获取正确的奖励 | ID202 |
| D12 | **任务中玩家大退重登或顶号** | 大退重登可以测数据是否正确存档并重新导入；顶号可以测对内存中数据的影响 | ID105、ID244（计数 2） |
| D13 | **玩家在做批处理任务时发生数据迁移** | 可能发生数据复制和回档，需要禁止或确保不会发生 | ID117 |
| D14 | **数据迁移** | 确保迁移前未存档的数据在迁移后能被存档 | ID118 |
| D15 | **测试或压测机器** | 不能用正式运营的 DNS（检查 `/etc/resolv.conf`） | ID280 |
| D16 | **扫档操作** | 不要在正式运营环境扫档，要访问备份数据库或接入 SA 的备份扫档工具 | ID239、ID134、ID108 |
| D17 | **未开放的新服** | 不应该和正式运营环境产生通讯 | ID125 |
| D18 | **内服测试环境** | 尽量和外服一致。多进程环境可以缩减为 2 进程，但**不能是单进程**；尽量少针对内服做硬编码，有硬编码的模块每周要在正常环境回归一次 | ID130、ID131 |
| D19 | **数据库或相关组件升级** | 需要找 DB 中心做评估并拿到书面评估结果 | ID279 |
| D20 | **内存相关改动** | 内存泄露测试要看趋势，还要测玩家退出后内存是否正常回收 | ID110（计数 3） |
| D21 | **有已知压力上限的功能** | 要在服务端做好限制，而不是依赖执行人员的自觉 | ID151（计数 4） |
| D22 | **登陆、重连、断线重连** | 服务端对玩家数据应该有缓存上限；断线重连 QPS 超过一定数值应让玩家重新排队 | ID183、ID262 |

## E. 流程规范与可追溯性

- 发现 bug 要提单跟踪；上线期测试完成的单进入回归区，维护前回归完成后才关单。（ID14、ID175）
- 多周外测内容要建单跟踪，下周回归主流程。（ID69）
- 开服后 release 分支的修改要建单跟踪，下周回归主流程；已同步到主干的立马验证。（ID55）
- 需要后期修改的内容要提单备忘，例如外测服设置。（ID152）
- 每周维护一个回归 checklist，包括充值、战斗、核心玩法。**计数 10，是很高频的一条。**（ID44）
- 开服测试维护一个 checklist，包括战斗、多平台登录、核心玩法。（ID79）
- 商城、商会交易、奖励表等核心系统定期做全回归，**尤其是防作弊用例**。（ID72，计数 3）
- 计划在外部平台（如运营后台）执行发奖指令前，应该先让 QA 测试再发奖。（ID212）
- 运维修改游戏相关配置应该通知 QA 测试（包括屏蔽字库等）。这类修改往往监控不到。（ID167）
- 提交开发内容要写对单号；写错了可以用工具修复。（ID124）
- GM 指令、补偿发放等周边系统也要建单跟踪。（ID153）
- 需求描述如果只有「更快、更早、更多」这类说法，需要把它转换成可验证的规则，**不能自动写成体验改善**。

## F. 配置表变更的通用风险模式

配置表错误引发的事故占很大比重——历史复盘里的原话是「**配置表变更确认是 QA 工作的
基础业务**」，对应的条目计数 22，是全清单最高的一条。配置驱动的项目几乎都适用。

具体的 ID 编号规则、号段划分、表清单以**项目知识包**为准；下面是与项目无关的风险模式。

### F1. ID 的语义风险（最高优先）

| # | 看到这样的改动 | 要警惕的事故 | 来源 |
|---|---|---|---|
| F1.1 | **删除了已经放出的 ID 行**（尤其道具、物品、怪物、任务） | 玩家存档里可能已经有这个 ID，登录会数据异常，导致玩家身上数据错乱 | ID27（计数 6） |
| F1.2 | **改动了已经放出的 ID**（ID 没变但指向的内容变了） | 多半是**分支表或海外表 ID 冲突**，玩家手里的物品可能从 A 变成 B——**从不值钱变成值钱就是重大损失** | ID27 |
| F1.3 | 新增 ID **越出了本系统该占的号段**，或与海外版号段重叠 | 同上：ID 冲突 | ID27、ID56（计数 2） |
| F1.4 | 改动落在**本次需求不负责的系统**上 | 可能是误改其它系统，也可能只是**单号填错**——两种都要在报告里点出来，并给出该系统的跟进方向 | ID27 |
| F1.5 | **拿新变量或新 ID 替换旧的** | 表格、代码、其它配置里可能仍有旧引用；若这次改动本就由 ID 冲突引起，还要警惕**替换错了对象** | ID263（计数 3） |
| F1.6 | 替换之后 | 要查线上数据：如果仍有地方在用旧变量或旧 ID，就要做兼容 | ID264 |
| F1.7 | 表里**引用了其它表的 ID** | 确认被引用的 ID **存在且没有过期**（悬空引用） | ID28 |
| F1.8 | **新活动复用了旧变量或旧表 ID** | 线上玩家存档里可能残留上一期的数据，会导致玩家无法正常参与，**或者不参加就直接获利** | ID57（计数 4）、ID26 |

### F2. 单表改动的连锁影响

| # | 看到这样的改动 | 要警惕的事故 | 来源 |
|---|---|---|---|
| F2.1 | **客户端与服务端共用的表**被改动 | 两端主流程都要回归，**不能改动者说改了哪一端就只测哪一端** | ID205 |
| F2.2 | **时间类字段**（活动时间、开放时间）被改动 | 玩法、成就、网页、推荐、日历、道具、积分的**服务端过期时间**与**客户端显示过期时间**都要同步改；老日期可能还留在表格和代码里，需要全局搜索 | ID97（计数 3） |
| F2.3 | **奖励相关的填表或配置** | 至少要取一条奖励，验证限制条件的**判定接口**是对的，不能只看表 | ID249 |
| F2.4 | **价格类字段**新增或调整 | 交易类系统常模拟真实市场，填的只是初始定价，线上价格会随玩家行为波动，内服静态数据测不出问题 | ID171 |
| F2.5 | **会在外部交易平台展示**的商品所属表被改动 | 要去该外部界面核对属性，不能只信表 | ID253 |
| F2.6 | **活动屏蔽 / 下架** | 屏蔽是否完全：该活动及其全部关联单所涉及的表格修改是否都覆盖到了 | ID232（计数 1） |

### F3. 导表链路

| # | 看到这样的改动 | 要警惕的事故 | 来源 |
|---|---|---|---|
| F3.1 | **导表报错** | 报错必须是**阻断式**的，否则程序员发现不了 | ID112（计数 2） |
| F3.2 | 有条目被删除 | 该条对应的**生成文件（代码）也要一起删掉**，否则残留旧逻辑 | ID113 |
| F3.3 | **生成的代码文件** | 要提交进版本库，否则无法 diff、无法追溯 | ID246 |
| F3.4 | 导表工具链本身有改动 | 会影响所有表的产物，回归面比单表大得多 | —— |

### F4. 版本对齐与流程

| # | 看到这样的改动 | 要警惕的事故 | 来源 |
|---|---|---|---|
| F4.1 | 任何配表改动 | **确认「确认的 diff」与「测试过的 diff」是同一个版本**。生成物可能不是由最新表格导出的；在 diff 网站确认了、实际测的却是另一个版本，最后没测过的版本被放出去 | ID29 |
| F4.2 | 同上 | 要求「代码版本号 **不早于** 表格修改版本号」，并请开发在生成时记录版本号 | ID29 |
| F4.3 | 表经过 **merge** | 要对比两个分支的 diff，确认合并正确 | ID225 |
| F4.4 | 改动里**混入了非本周外放的条目** | 未外放内容可能污染线上数据。等待代码调用的表可以直接填主干，一填就影响线上的表必须走分支表 | ID31（计数 3） |
| F4.5 | 分支表与主干表 | 要做 release 与主干的 diff 确认，确认分支的修改回了主干 | ID30 |
| F4.6 | **表格与代码需要一起回退** | 只回退了一边会导致语义不匹配；除非能确证表格对线上无影响 | ID39（计数 2） |
| F4.7 | 配表改动完成 | **要立马在 diff 网站做 diff 确认**，拖延会让 diff 被后续提交污染 | ID233 |
| F4.8 | 配表改动 | **不要只验证表格或配置文件，要在游戏中实际执行用例** | ID83（计数 11）、ID166（计数 2） |
| F4.9 | 策划填表的内容 | 文档里要有详细描述，并标明对应的 ID | ID128、ID200 |

## 附录二：原始清单的字段说明

原始表是**单 sheet、408 数据行、14 列**。它不是事故档案，而是**祈使句式的检查项**
（按条目 ID 去重后 273 条），事故信息被压缩成计数列。几个容易误读的字段：

- **`条目ID`**：文本型数字（`'260'` 而不是 `260`）。同一个 ID 会在多个分类下重复出现
  （408 行里有 100 个 ID 重复），**必须先去重**再统计，否则高频条目被重复加权。
- **`关联三级分类`**：**是一个计数（取值 1–5），不是分类名称**。字段名极易误导。
- **`总事故数`** = 一级事故数 + 二级事故数。**只取总事故数作为权重**，三个都取会重复加权。
- **`一级事故数` / `二级事故数`**：原始表里没有任何说明解释「一级/二级」的含义，
  **不要编造它的语义**。
- **`预防措施`**：整列 408 行**全空**。
- **`条目背景` 与 `测试方法`** 是稀疏列（分别约 22%、20% 有值），且内部用换行分成
  「1. 2. 3.」编号段。**不要当成必填**。
- **`清单条目` 里的顿号是并列的检查对象**（例如「等级限制、时间触发、分段公式」），
  不是分隔的多个条目，**不要拆开**。
