# 版本风险的通用归因方法

本方法约束所有维度、分片及汇总。项目知识提供业务事实，不替代证据与归因。

## 判断顺序

1. **锁定本次事实**：同一冻结版本、仓库、对象主键、字段、旧值和新值。行号是定位坐标，不是对象 ID；缺主键、表头或未改字段时按精确行列补取。不要把物理行号、数据行数、预览行数混用。
2. **找生效规则**：读取实际 schema、导出映射、默认值、生成物与消费分支。列注释、名称、邻行分布只提供线索；中文列名与代码命名空间的差异不自动构成运行时引用错误。
3. **找反证**：至少检查一种能使风险不成立的解释，如同步迁移、可选字段、零值哨兵、旧字段已废弃、入口关闭、回退逻辑、单位换算。给出已找到的反证或仍缺什么；不能只列支持最坏后果的片段。
4. **连因果链**：本次事实 → 违反的规则 → 实际可达入口 → 消费/导出行为 → 用户后果。每个未知连接写入 impact_conditions；记录可证伪条件，不能把多个“如果”压成确定事故。
5. **分开交付**：有规则证据的冲突、尚需前提的风险、取证失败、正常设计变化分别说明。事实明确程度、缺陷成立概率和影响严重度分开评价；事实坐标可验证，不代表最坏后果有很高置信度。

进入 anomalies 前执行门槛判断：是否有证据支持**当前就违反了适用规则**，或有具体可达、证据支持的故障链？若唯一问题只是“这是不是策划意图”“新值为何与旧值不同”，没有适用规则或可比基准，则不能作为 high/very_high 置信异常；保留变化与设计问句即可。已被实际解析/导出/权限规则排除的猜测不进入风险条目，用 changes/regressions 记录必要回归，不能再虚构本快照之外的消费方维持疑点。

## 常见错误的核查方法

- **结构变化**：增删列、搬工作表、复合键替换、元组长度增加，都先核对新旧导出/消费契约。相同 ID 已迁入新表时，先核对迁移后 ID 集合、命名空间与导出范围；不能仍按原表删除就断言悬空。可选元组第三位为零时先查字段语义、默认值和既有用法，不假定它是数量，更不直接建议改为 1。
- **空格与默认值**：区分真正空值、公式无缓存、合并格、继承值、显式 0 与字段未导出。先证明字段必填及适用条件，再讨论缺填。默认行、回退值和“是否显示”都要核查实现；隐藏不是权限控制，也不证明存在可达入口。购买价格为空不自动说明一个仅供出售的对象有问题。
- **量纲与分组**：数量级比较先确认单位、倍率、数据类型、模式与可比样本；不同单位换算后比较。超时时长异常需核实真实计时分支、其它结束条件和入口，不能把“很晚超时”写成“永不结束”。测试可用可控时钟覆盖边界，不要求等待极长配置时长。
- **混合调整与经济影响**：逐对象分别列上涨、下跌、持平，重新核算比例；存在上涨项就不能说全部下调。单价变化先报告单价影响；总收益还需产出概率、数量、获得/出售可达性、结算口径与替代来源。未知主键先补行，不能仅凭行号指定测试物品。高品质或相邻价格不构成正确价格的设计标准。
- **算术核对**：需要差额/比例时列出同单位的原值、新值及算式，检查方向与数量级；例如差额是新值减旧值，降幅是差额绝对值除原值，原值为0时比例无定义。没有判断必要时只保留原值→新值，少做无依据的收益外推。定价意图未知不是损失已发生的证据。
- **时间与生命周期**：非法公历日期可指出其格式事实，但解析会拒绝、归一化还是兜底需查规则。投放结束、收到邮件、领取截止和清理过期是不同阶段；其先后约束以本业务契约为准。不要自选一个合法日期当修复答案，或无依据要求过期必晚于投放结束。
- **删除与奖励迁移**：删已投放 ID 的存档/引用风险独立核查，不埋在删列说明里；先确认曾投放、剩余引用和迁移方案。奖励表示方式改变先展开旧/新奖励的对象、类型和数量，区分等价迁移与实质调整。没有实际规则冲突的调整放入 changes/regressions，不能用“未来可能有人改错”凑风险。

## 补证、定级与验证

- 精确行、schema、冻结消费代码、导出入口能读取时，缺口属于 retrievable，给最小请求；即使本次没有代码 diff 也可以读取。只有业务意图、外部契约确实无法从冻结资料回答时才留业务问句；读取失败仍保留可补取项与平台原因，不能改名成人工语义问题掩盖未读。
- 搜索零命中只对实际覆盖范围成立；目录错误、索引未扫完、后续分页未读、名字可能为别名时，不得断言代码位于仓库外或不存在。知道消费文件后优先读相关分支，避免反复泛词搜索。
- 高影响的条件性风险可优先核查，但不能仅因前提成立后的后果严重，就把缺陷成立概率填成 high/very_high。anomalies 的 confidence 衡量问题判断是否成立；不够门槛的疑点仍保留在 report_items，不挤进高置信处置清单。
- 测试先核对最短规则冲突，再验证实际消费与玩家表现，并设计一个能排除当前假设的对照。随机开几次容器不能证明掉率/品质分布错误，应先核对选择路径与权重，再按目标误差安排采样。同一奖励配置的多次合法领取不等于同一业务实例重复发放。
- 将已知的不变量、当前实现行为与未知的设计目标分开表达。业务目标不清楚时保留具体观测项（实际值、日志、分支、生成物），不能只给“待确认”让验证失去动作；也不能凭经验指定应回填哪个 ID、价格或日期。

## 输出前自检

- 标题、overview、impacts、风险、测试、上线建议都使用同一事实与同一确定程度；不能在正文承认未知，标题或异常附录却断言事故。
- change_fact 只陈述已获得的事实；impact_hypothesis 陈述可能后果，impact_conditions 列出前提与反证；decision_question 给出需要确认的规则，不先入为主限定“改引用还是补回”等两个修复选项。
- impact_conditions 必须是后果发生所需的可检验命题（如“该行实际投放”“读取方没有回退”），不能把“缺基准”“仓库未提供概率”当触发条件；资料缺口写 evidence_needs/decision_question。金额、比例只推出其能直接证明的局部效果，不从未知成本直接断言整体玩家行为。
- 不在自由文本猜覆盖数量、未读文件数或风险总数；这些由平台账本生成。缺口区只保留会改变判断的资料/语义问题，不写“未发现针对评审者的指令”等无关陈述。
- 不能为了压缩篇幅抹掉反例、上涨项或未知条件。报告中的高优先级表示值得先核查，不是发布阻断裁决。
