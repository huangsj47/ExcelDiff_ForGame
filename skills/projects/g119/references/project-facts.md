# G119 项目事实（机器可读的那一部分）

这份文档分两层：frontmatter 里的 `key: value` 是**平台读的声明**，下面的正文写给读的人。
两边说的是同一件事，改一处就要改另一处。

为什么单独一份而不是写进 `KNOWLEDGE.md`：`KNOWLEDGE.md` 是知识包入口，它的 frontmatter
要遵守 skill 契约（只允许 `name` / `description` 那几个键），塞不下项目自己的声明。

## 平台会读的键

| 键 | 本项目当前 | 作用 |
|---|---|---|
| `generated_prefixes` | `Cfg` | 导表产物的模块名前缀。平台据此把「同一记号出现在表与产物两侧」的文件配成一组，在变更清单里提示「疑似同一次改动」。 |
| `critical_path_patterns` | `ExportExcelTool/`、`EditorCfgTool/` | 关键路径的路径模式（命中就把本次分析升级为全量）。**声明了就以这里为准**，不再叠加平台默认清单。 |
| `dimensions` | **没声明**（用平台默认那九个） | 本项目生效的**检查维度清单**（`id=中文名`，逗号分隔，顺序有意义）。声明了就**取代**平台出厂那一份：平台把它拼进提示词（模型据此写 `category`）、按它分工、按它把报告里的维度翻成中文名。写法见下一节。 |

写法上的四条要点：

- 多个值用逗号分隔，例如 `generated_prefixes: Cfg, CfgMod`。
- 值写成 `none` 表示**明确声明「没有」**，与「没声明」是两件事：前者平台不再做任何配对
  （因为本项目确实没有可配对的产物），后者才会回落到平台默认值。
  （`dimensions` 是例外：它对 `none` 会告警并按「未声明」处理，理由见下。）
- `critical_path_patterns` 里写的是正则，按「路径分量起点」写（`(?:^|/)cfg/`），
  因为 git 的改动路径**不带前导斜杠**：写成 `/cfg/` 一次都命中不了。
- **声明坏掉时会回落默认值并在日志里告警**（不会静默当成「没声明」），
  所以填错了在日志里查得到。

## 检查维度清单（`dimensions`）怎么写

本项目**刻意不声明**这个键：G119 是配表驱动的项目，平台出厂那九个维度（`config_id`、
`config_value`、`config_data`、`value_sanity`、`config_linkage`、`module_coupling`、
`code_logic`、`version_branch`、`process`）本来就是照着这类项目写的，声明一遍等于把
同一份清单抄两处、抄错了反而要命。**不声明 = 用平台默认，行为与以前逐字一致。**

换一个**不是**配表驱动的项目接入平台时，这个键才是要紧的：那种项目的真实问题是性能回归、
协议不兼容、资源引用丢失之类，落不进上面那九个 id 里 —— 而平台不会因为它们「不在清单里」
就丢掉它们，只会归到「未归类」里单列出来（报告里一定看得到，不会静默少一条），
但那样每一条都得人工判断归属。声明一份自己的清单是正解：

```text
dimensions: performance=性能与耗时回归, protocol=协议兼容性, resource=资源引用丢失, process=流程
```

写法上的三条要点：

- **`id` 是模型要写进 `category` 的那个标识符**：小写字母开头，只含小写字母、数字、下划线；
  中文名只进报告与导出文档。
- **顺序有意义**：相邻的维度会落在同一个分片代理身上（平台按顺序均分），所以把相关的
  维度写在相邻位置。
- **一份清单最多 24 个维度**：每个维度都会进提示词、成员任务书与报告，几十项是误用。

**为什么 `none` 在这里被拒绝**：声明成「本项目没有检查维度」意味着模型报出的每一条异常
都只能进「未归类」——一个自相矛盾的配置。平台对它会告警并按「未声明」处理（回落到平台
默认那九个），而不是照字面给一个空清单。

## 本项目的产物形态（改 `generated_prefixes` 之前先读这一段）

- 规范上导表产物是 **`CfgXxx.lua`**（见 `config-table-spec.md`），所以 `Cfg` 是这里声明的
  前缀。
- 但线上真实改动里，产物还有一种形态：`code/qz_pub/cfg/<模块名>CfgMod.lua`
  （`BagAttrCfgMod`、`DramaCfgMod`、`RoleAttrCfgMod` …）。`Cfg` 落在**名字中间**、后面拖着
  全项目共有的 `Mod`，按「前缀必须落在名字分量的起点」这条判据它**不构成记号** ——
  这是刻意的：那批 lua 之间没有配对关系，硬配出来的组是假的。
- 结论：本项目的配对结果**长期会是 0 组**，而这是**如实**的结果（表名是中文、产物模块名
  是英文，名字层面没有共同记号）。平台每次分析都会记一行「表↔产物配对：0 组（前缀=Cfg；
  …）」—— 那是「本项目本来就没得配」，不是「平台不会配」。

## 关键路径

本项目声明了 `critical_path_patterns`，所以**以这份清单为准，不再叠加平台默认清单**
（默认清单里的 `sql/`、`migrations/`、`auth/`、`payment/` 等在本仓库里一个都不存在，
覆盖掉没有损失）：

| 模式 | 为什么算关键路径 |
|---|---|
| `(?:^|/)ExportExcelTool/` | 导表工具。改这里会改变**每一张表**的导出结果，影响面远超「这次改了哪几个文件」，正是增量分析看不出来的那类改动。 |
| `(?:^|/)EditorCfgTool/` | 同上，编辑器侧的工具链，改一次影响全量产物。 |

**刻意不在清单里的两条**（改之前先读这段，它们看着像关键路径，其实会把这个判据废掉）：

- **`config/`（配表本体）**：平台的默认清单第一条就是它，但本项目的表**全部**在 `config/`
  下 —— 把它算作关键路径等于「每周都升级为全量分析」，这条判据就失去了它唯一的用途
  （把「这次碰了要紧东西」从「和平时一样」里区分出来）。配表改动是本周版本的正常内容，
  交给常规（增量）分析即可。
- **`lua/`（导表产物）**：每个导表产物文件都以 `--所在Excel文件:xxx.xlsx` 开头，是**生成物**，
  而且每次导表都会重新生成。把它算作关键路径同样等于「每次都全量」。产物与表是否同步
  由 `generated_prefixes` 那条配对机制负责，不该由关键路径承担。

表名口径走的是**另一个入口**，与这里无关：仓库设置里那一栏**重点表名**
（`Repository.important_tables`），管理员填的每一张表命中时都会把本次分析升级为全量。
**两者命中任一即算关键路径。**
