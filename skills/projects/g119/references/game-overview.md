## 0. 一句话背景

项目代号 **G119**（工作名 **破碎之地**）。易协作上的需求单项目名是 `G119-破碎之地`，**BUG 单在另一个项目**。

玩法骨架是 **搜打撤（PVE 为主，四人队）**：小队进入被「神秘力量」改写的**黑暗童话世界**，搜刮不该存在的异常物（即**回收物**），在迷失时限前撤离。
玩家身份是**「特藏阅览部」**成员；**灵宠**提供角色技能，**灵装背包 + 吸灵器**是核心探索工具。
基调 **微恐 + 黑暗童话**，只做 PVE（PVPVE / GVG 属后续扩展方向）。

一句话口径：**进去探、打一场、带着东西出来** —— 搜、打、撤三件事，改动影响哪一件都要说清。

## 1. 项目当前状态（写报告前先建立这个认知）

项目处于**铺量制作 + 上线标准对齐**的阶段。这个阶段有三个特征，直接决定报告怎么写：

1. **大量系统同时在铺**：新表、新代码、新玩法并行进主干。
2. **进主干 ≠ 对玩家生效**：很多内容「表已铺、程序还没接」，或「代码已合、入口还没开」。**这是常态，不是缺陷。**
3. **同一批提交里混着三种状态**：已生效的、在建的、只为将来铺路的。**只看 diff 分不出来** —— 要靠 §2/§3 的状态表 + `repo-layout.md` 的 `*CfgMod.lua` 判据。

→ 所以对每一个改动，报告的落点是「**它现在生效了吗 / 会不会误生效**」，**不是**「它属于哪个版本」。

## 4. ⚠️ 判定规则（本文件最该照着执行的一节）

### 4.1 不许贴版本标签

**不得**在结论、`title`、`evidence`、分类或任何字段里出现「版本」维度的说法：

- ❌ 里程碑名 / 代号（`M3`、`M4`、`M5`、`M6` …）
- ❌ 「本版本 / 下个版本 / 上个版本」「这期 / 下期」「本迭代」
- ❌ 「XX 版本要做」「排在 XX 之后」「上线后再说」这类**没有依据的时间承诺**
- ❌ 把「旧分支 / 新分支」当成内容状态的解释

**要说明一个改动现在算不算已生效，用 §3 的三种状态说话**（已落地 / 在建 / 待建）。
用户**明确**指定了版本或分支时，才允许在结论里出现用户给的那个词，且**只复述、不引申**。

### 4.2 按状态判定改动

| 看到什么 | 怎么判 | 写进报告的方式 |
|---|---|---|
| 命中 §3 的「**在建**」项（家园、赛季、BP、抽卡、月卡、PVPVE、UGC、天气生态、小熊猫、兵俑…） | 属**在建内容提前合入**，现在不该对玩家生效 | 写成「**在建内容已进主干**，需确认是否有开关护栏 / 会不会被误放」→ 用 `process`；**不要**写成「功能实现不完整」 |
| 改动落在 `config/` 下、但对应功能是「在建 / 待建」 | 提前铺表 | 写成「**尚未生效的表在铺量**」，并提示「确认程序是否已接读」（判据见 `repo-layout.md` §4 + `system-map.md` §9） |
| 商业化相关（`150_shopping_mall/`、`CfgStoreGoods`、`CfgStoreType`、充值、月卡、抽卡、BP） | 整体在建，**程序尚未接读** | 用 `process`；**不要**把「程序还没接读」写成「商城配置错误」 |
| 属「已落地」但功能看起来只做了一半 | **不能直接判缺陷**：可能是阶段性屏蔽 / 联调保护 / 灰度开关 | 按 `version-diff-review` 的反误报规则处理：先去要能区分「阶段性屏蔽」与「真漏改」的上下文 |
| 内容在 §3 里**完全找不到**（既非已落地也非在建） | 信息缺口 | 按「需求侧信息缺口」处理，**标注缺口，不自行编造它属于哪个阶段** |

⚠️ **不要用「目录/文件存在」直接推出「功能已上线」**：`490_home` 有表 ≠ 家园可玩。
判断生效与否，一律回到「**有没有 `*CfgMod.lua`、有没有开关、是不是只在测试包**」这三步。

## 6. ⚠️ 本知识包**不包含**的发布事实（不要假装知道）

这条针对**实测出现过的真实错误**：报告曾把「热更两端必须同时完成」「先同步一台服务器线上观察」「release 分支也要测」写成**该项目已知的发布流程**。本知识包**没有任何**发布流程事实。

以下事实**当前无记录，一律不得当作既成流程**，只能写成**条件性 QA 建议**（「若本项目采用 <流程>，则需…」）：

- release / 主干分支的名字、分支策略、合回规矩
- 热更的具体流程、配置与代码的先后顺序约定
- 灰度 / 分批放量的策略与开关机制
- 线上观察与全服推送的节奏
- 封包、提审、渠道分发的流程

**已知的相关事实只有三条**（其余待补）：
1. 周版本以**周**为节奏做版本聚合确认（平台侧就是按周版本分析）。
2. 导表产物与表是**同一次导表产生的**，要当成一次改动看（见 `system-map.md` §11）。
3. `ExportExcelTool/`、`EditorCfgTool/`、`lua/code/` 属关键路径，改一次影响**所有表**的导出结果或**diff 判据本身**。

> 写法要求：**没有项目事实支撑的发布动作，不得写成肯定句。** 这类内容要么删掉，要么明确标成条件性建议。
