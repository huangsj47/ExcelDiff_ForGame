# G119 项目知识包

这是 **G119 项目专属**的知识包，供平台在做版本分析时挂载到项目上。

## 这里放什么

**项目事实**——「这个项目长什么样」。凡是换个项目就不成立的内容都属于这里：

- **平台能读到什么**（两个仓库的目录地图、模块名前缀、每张表的代码说明书入口）→ `repo-layout.md`
- **游戏背景与当前内容范围**（这个游戏是什么、哪些系统已落地 / 在建 / 待建、按状态判定改动的规则）→ `game-overview.md`
- 玩法语义与局内流程 → `gameplay-semantics.md`
- 配置表的编号规则、命名规范、系统划分 → `system-map.md`
- **经济与数值基线的种类与出处**（具体数值不含，见文件内的说明）→ `economy-baseline.md`
- 项目的专有名词
- **导表产物的形态与前缀、哪些路径算关键路径**（这类事实平台要读，写在
  `references/project-facts.md` 的 frontmatter 里；平台的默认值对配表项目基本不适用）

## ⚠️ 两条硬规矩

### 1. 平台的可读范围只有两个仓库

```
能读：D:\_G119\_qz_project\qz_config         （配置仓库）
      D:\_G119\_qz_project\qz_luaworkspace   （代码仓库）
不能读：策划的设计/规划工作台、其他项目、外部网络；无写权限
```

由此产生**两条对称的禁令**：

| 层 | 例子 | 报告里怎么标 |
|---|---|---|
| **仓库里查得到** | 表结构、字段、id、代码引用、`*CfgMod.lua` 的文档块、`docs/` 下的设计文档 | 可作 `observed_diff` / `verified_context`，可写肯定句 |
| **仓库里查不到**（只在本知识包里） | 内容范围与生效状态、数值目标、发布流程 | 只能作 `project_assertion`。**不得因为「仓库里搜不到」就否认它**，也**不得声称「仓库里能看到」** |

### 2. 不许给改动贴版本标签

结论、`title`、`evidence`、分类或任何字段里，**都不要出现版本维度的说法**：

- ❌ 里程碑名或代号（`M3`、`M4`、`M5`、`M6` …）
- ❌ 「本版本 / 下个版本 / 上个版本」「这期 / 下期」「本迭代」
- ❌ 「XX 版本要做」「排在 XX 之后」这类没有依据的时间承诺
- ❌ 把「旧分支 / 新分支」当成内容状态的解释
- ⚠️ 表名 / 模块名里出现的编号（如 `CfgM5Progress`、`470_daily_lottery`）是**既有命名**，
  只当作名字读，**不要在结论里引申成版本线索**

**要说明一个改动现在算不算已生效，用 `game-overview.md` §3 的三种状态说话**：
**已落地 / 在建 / 待建**。用户**明确**指定了版本或分支时，才允许出现用户给的那个词，且**只复述、不引申**。

**尤其注意**：**本知识包没有任何发布流程事实**（release 分支、热更顺序、灰度、线上观察一律无记录）。
报告里凡涉及发布动作，只能是**条件性 QA 建议**，不能写成该项目已知的流程 —— 见 `game-overview.md` §6。

## 这里不放什么

**评审方法与门槛**不放这里，它们在平台内置 skill（`skills/version-diff-review/`）里。
那是**项目无关**的：输出协议、检查维度、证据与置信度门槛、反误报规则、通用事故清单。
换一个项目接入平台时，那份 skill 原样可用。

两者的关系是：内置 skill 提供**方法与门槛**，本知识包提供**事实**。
事实以本知识包为准；**方法与门槛不可被本知识包覆盖**。

## 接入新项目时

在 `skills/projects/` 下新建一个以项目代号命名的目录，结构与本目录一致即可。
目录名与平台里项目的代号对应，用于自动挂载。
