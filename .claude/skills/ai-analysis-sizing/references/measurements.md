# 实测数据与诊断记录（脱敏）

> 这里记的是「什么样的规模会把参数打穿」。项目名、仓库名、路径、模型端点的具体值都已去掉；
> 保留的是**规模量级与结构**，因为它们才决定参数该配多少。

## 一、一次「两个上限都被击穿」的周版本

规模：**约 850 个改动文件、约 70 个提交**，配表（`.xlsx`）与脚本（Lua）混合，
清单长到被取样（真实 767 个文件，清单只列 200 个）。

配置：出厂默认 —— 预算 560,000 字、轮次 8、索取 40、分片 3。

结果（连续四次运行的形态一致，不是偶发；最近一次里那个撞索取上限的分片换成了在 7 轮内交出结论）：

| 分片 | 撞的是哪个上限 | 后果 |
|---|---|---|
| S2 一类 | **索取上限**（7 轮就用满 40 次） | 后面几轮的维度只能靠已有证据 |
| S3 一类 | **轮次上限**（8 轮、38 次索取，额度还剩 2 次没用） | 最后一个轮次里模型交出的是一份 markdown 叙述，**这一片没有任何结构化结论** |

整次分析以 `subagent_gap` 收尾，并在报告末尾的「信息缺口（平台补充）」里逐条列出。
耗时约 17~21 分钟。

**读法**：这一类规模不是「某个参数差一点」，而是**规模本身超出这一档**。可选的做法是
① 按单个提交分析（范围缩小到 1/10 以内）；② 提高轮次与索取上限并按第三步同步加预算
（预算要到 720,000 字，需要窗口 ≥ 1.2M token 的模型）；③ 关掉分片、把这一档让给单代理。

## 二、「轮次上限」比「额度上限」隐蔽

同一批运行里反复看到：**额度还剩着，轮次却到顶了**。模型在最后一个轮次里被要求
「基于已有证据出结论」时，如果没人告诉它「这是最后一条消息」，它会把这一轮写成一段
叙述性的 markdown —— 看起来该说的都说了，但协议要求的是 JSON，于是那一片的结论
**一条都进不了报告**。

平台现在的做法：最后一轮的消息里明写「这是最后一条消息，再索取要等下一轮，而下一轮不存在」；
如果它仍然只给了 markdown，会**再问一次**「把上一条原样转成 JSON」，只给这一次机会。

**配置上的推论**：轮次上限调大**不能**替代索取上限，反之亦然 —— 两个是独立的稀缺资源，
先看报告里是哪一句（「轮次用尽」还是「索取额度用尽」），再动对应的那个。

## 三、观测到的耗时与占用

| 场景 | 实测 |
|---|---|
| 周版本（3 分片 / 8 轮 / 40 索取） | 17 ~ 21 分钟（一次运行的 5 个代理合计 31 次模型调用） |
| 分片之间 | **串行**：一个代理跑完再跑下一个，所以墙钟随分片数与轮次增长 |
| 后台 worker | 分析期间被独占；同步任务（优先级 3/5）在这段时间里排队，优先级更低的缓存任务等更久 |
| 调度器 | 每分钟 tick 一次；同一配置在分析进行中不会重复入队 |

**推论**：一个团队如果同时给多个配置开了「周版本自动分析」，这些分析会**串行**排在
单 worker 上，后面的会等前一个跑完（十几分钟一轮）。间隔配得太密只会堆队列。

## 四、几条踩过的坑（配置视角）

| 现象 | 根因 | 结论 |
|---|---|---|
| 报告说「本次分析总共可索取 0 次上下文」 | 那一轮确实把额度用完了，而文案当时只报了「剩余」 | 现在文案区分「总额 / 已用 / 还剩」与「配置就是 0」三种；**看到「配置是 0」要去配置页看，看到「已用」是正常消耗** |
| 报告里的「信息缺口」说某个文件取不到 | 该文件不在本批次的改动白名单里（模型自己配错了） | 与平台故障无关；平台会把「被拒的原因」交回给模型 |
| 结论条数不够、末尾有「结论条数上限（平台补充）」 | 报告的结论条数上限（配置项「单次异常上限」）截断，按严重度优先保留 | 调「单次异常上限」。**别与「上下文条数上限」混了**：后者每轮生效、自动跟着索取上限走，不是配置项 |
| 分析跑完状态是「降级」而不是「完成」 | 降级原因写在结果里（轮次/额度/markdown/上下文超长/分片没跑成） | 先看是哪一种再调参数；**降级不等于结果作废**，但会写明「这次是在什么基础上得出的」 |

## 五、量规模时容易数错的地方

- **报告的「N 个文件」是清单里的数量，不一定是真实改动数。** 被取样时报告会另写一句
  「还有 N 个文件的名字没有列出来」，两者要一起看。
- **配表的体积要按「表数与行数」看，不是按字节。** 单个配表正文按 11,000 字上限窗口化
  提供，一张几十万行的表靠一次索取看不完 —— 用改动的行窗口（`lines="1200-1600"`）或
  `file_diff` 才划算。
- **提交数多但文件数少**（例如同一个文件被反复改）属于「中」档，不必按提交数放大预算。
