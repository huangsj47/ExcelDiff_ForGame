# 按变更规模定 AI 分析预算（数值由平台推导）

这个平台的 AI 分析有五个互相咬合的数字。**2026-09-23 配置面收敛之后，用户能配的只剩一个
「提示词字符预算」加几个开关** —— 其余四个（轮次、索取上限、分片数、异常上限）由平台按
预算与本周规模**自动推导**（`services/ai/auto_sizing.py`，校准出处 runs 38~41，见
`references/measurements.md` 第〇节）。所以这个 skill 的工作变成了：

1. **量规模 → 定预算档**（唯一要配的数字）；
2. **核对推导值**：预算定了之后，平台会算出分片/轮次/索取/取样/异常五个数
   （预算计划的「每片名义额 / 家族共享池」与「推导依据」两行就是它们）——
   用第三步的算式复核它们装不装得下，装不下说明**预算**配小了（不是去调别的）；
3. **症状诊断**：报告里的「降级/缺口」多数要落在预算、范围或模型窗口上，而不是某个
   已经不存在的旋钮。

**它们仍然不能各调各的** —— 平台里有一条测试
（`tests/test_ai_models_and_migration.py::test_the_prompt_budget_can_honor_the_request_budget`）
专门守着这件事。预算装不下推导出的索取次数时，模型照常索取 N 个文件、其中一半被截断，
而它**分不清**「预算不够」和「文件就这么大」，于是把残缺当全部写进结论。

顺序永远是：**先量规模 → 再定预算 → 再验自洽 → 最后才谈时间与钱**。

## 〇、两条口径

**换算**：平台把**字符**当预算单位（不是 token），口径是 **1 token ≈ 1 字** ——
窗口 1M token 对应 600,000 字的水位，200k token 的窗口对应 120,000 字。

**这一栏算谁的内容**：配置里的「提示词字符预算」是**用户内容**的额度 —— 变更清单、
取回的上下文、历史结论基线、**项目知识包与项目补充指令**。**平台内置提示词不占它**，
由平台加在上面（约 16,000 字，随平台版本变）。所以：

```
整份提示词 = 平台内置（约 16,000）+ 配置值      ← 窗口水位压的是**这个和**
配置值      ≥ 清单 + 基线 + 知识包 + 补充指令 + 每片索取次数 × 11,000   ← 用户那部分
```

## 第一步：量规模（四条尺子）

| 尺子 | 为什么是它 | 怎么量 |
|---|---|---|
| **本版本真实改动的文件数** | 决定清单大小与预算档 | 报告首行「本次变更共 N 个提交、M 个文件」；被取样时另有一句「还有 N 个名字没有列出来」，两个数都要看 |
| **清单里实际列出的文件数** | 清单是每份提示词里最大的一块，第一轮必发；取样上限 clamp(文件数, 200, 500) | 同上；或按「真实文件数 与 500 取较小值」估 |
| **提交数** | 决定清单里的提交头与元数据 | 同上 |
| **有没有大配表 / 大文件** | 单条上下文上限 11,000 字（配表正文同值），大文件必须靠行窗口或 `file_diff` 反复索取 | 改动文件里 `.xlsx` 的数量与体积；单文件改动行数 |

从仓库量（把区间换成这个版本的两个提交）：

```bash
git log <起始>..<结束> --oneline | wc -l                    # 提交数
git diff --shortstat <起始>..<结束>                          # 文件数、增删行数
git diff --name-only <起始>..<结束> | grep -c '\.xlsx$'      # 配表数（按项目实际后缀改）
```

**没有仓库、或只想估个大概**：用平台跑一次真实分析，读报告首行的「N 个提交、M 个文件」。
那是平台自己数的，比估算准；第一轮永远会跑完，代价只是这一次分析的时间。

## 第二步：定预算档

档位是按「预算要装得下什么」倒推的（算式见第三步）。**每一档的清单字数是这一档的隐含
前提**，写出来是让算式可复核：

| 档 | 真实文件数 | 假设列出的文件数（取样后） | 清单字数 | 预算配置值（用户内容） | 平台推导出的每片索取 | 推导出的其他 |
|---|---|---|---|---|---|---|
| 小 | ≤ 50 | ≤ 50 | ~3,500 | 150,000 | 8（下限） | 单提交路径不走推导 |
| 中 | 50 ~ 300 | ≤ 300 | ~21,000 | 300,000 | ~24 | 5 片 / 10 轮 |
| 大 | 300 ~ 800 | ≤ 300 | ~22,000 | 560,000（出厂默认） | ~48 | 5 片 / 10 轮 |
| 超大 | > 800，或有超大配表 | 500（被取样） | ~36,500 | 580,000 ~ 720,000（须先过窗口） | 48 ~ 60（默认预算下 48） | 5 片 / 10 轮 / 异常 8/片 |

三条口径：

- **取样上限 = clamp(文件数, 200, 500)**：真实文件数超过 500 之后清单不再增长 ——
  多出来的文件由模型按需索取，钱花在索取次数上。
- 表里的预算是**配置值**（用户内容），平台内置那约 16,000 字不在里面。
- **周版本与单提交分开看**。子代理与推导只作用于周版本；单个提交的分析按「小/中」就够。
- **「超大」那一行要先确认模型窗口**：上限是「（内置 + 配置值）≤ 窗口 × 60%」。窗口 200k token
  的模型，配置值填 720,000 会被压到约 104,000 —— **填了等于没填**。先看端点声明的窗口，
  再决定预算；窗口不够就缩范围或换模型，不要靠加预算。

## 第三步：验自洽（这一步不能跳）

推导公式（平台在跑，你要会**复核**它）：

```
每片索取 = clamp((生效额度 − 清单字数 − 6,000 基线) ÷ 11,000, 8, 60)
清单字数 = 取样上限 × 73 字/个
```

三个用法：

- **正向检查**：把这一档的预算代进去，算出的每片索取是否在期望档（默认预算 → ≈50）。
- **反解预算**（窗口把额度顶死时最有用的一个动作）：先算出窗口给用户留了多少 ——
  `可用 = 窗口字数 × 60% − 平台内置（约 16,000）`；想要每片 K 次索取，就配
  `预算 ≈ 可用` 并检查 `(可用 − 6,000 − 清单) ÷ 11,000 ≥ K`。
  例：200k token 的窗口 → 120,000 总计 → 可用 104,000；清单 14,000 →
  每片 (104,000 − 6,000 − 14,000) ÷ 11,000 ≈ **7 次** —— 这种窗口下别指望深挖，
  缩范围或换模型。
- **加索取就是加预算**：每多 10 次索取，至少多 **110,000 字**；
  每片 40 → 60 就是 560,000 → **780,000**（还得窗口装得下）。

两处实际数值上的提醒：

- **闸门按「大版本清单」校准**（约 87,000 字），而小/中档的清单远小于此 —— 所以拿闸门去
  验小档的 150,000 会「失败」，那是**预期**：闸门是给「大档及以上」用的下限检查，
  不是通用校验。反过来，系统提示词实测约 16,000 字（闸门按 12,000 算），
  项目知识包写满还会再加最多 40,000 —— 配数字时按实际，别只按闸门。

改完预算跑一次闸门（它是一组数字之间的自洽检查，会真的拦住你）：

```bash
python -m pytest -q tests/test_ai_models_and_migration.py -k budget
```

## 第四步：代价（时间与调用次数）

| 项 | 实测口径 |
|---|---|
| 一次周版本分析（3 分片时代） | **17 ~ 21 分钟**（多次运行的区间；同一批运行的 5 个代理合计 31 次模型调用）。5 片会更长，量级按「代理数 × 每片轮次」放大 |
| 代理调用次数 | 每个代理各跑若干轮，**每一轮 = 一次模型调用**；一次分析 ≈ 分片(5) + 汇总(1) + 对账轮(0 或 1) 个代理的轮次之和 |
| 分片是**串行**的 | 一个跑完再跑下一个，所以墙钟随分片数与轮次增长（不是并行） |
| 额度是**串行共享池** | 全家共一个「索取池 + 轮次池」（池 = 片 × 名义额），**前片用剩的滚给后片**；名义额是保底、汇总另有下限。预算计划的「家族共享池」一行就是这笔账 |
| worker | 一次分析独占后台 worker 十几到二十几分钟，期间同步/缓存类任务排队等它 |

**别一次拉满。** 预算配得离谱大时每片索取封顶 60 —— 多出来的部分只是个数字，而多数项目的
真实瓶颈是「窗口不够」或「结论被门槛滤掉」，不是索取次数不够。

## 症状 → 该动哪一个

| 报告/面板上看到 | 真正缺的是 | 怎么调 |
|---|---|---|
| 「轮次用尽，基于已有证据出结论」 | 轮次（推导值 10，**不可配**） | 看预算计划的推导依据：轮次是常数 10；真不够就把范围缩小到单个提交，或开增量分析 |
| 「索取额度用尽」 | 索取（按预算反解，**不可配**） | 加预算（每 +10 次索取 ≈ +110,000 字，先过窗口水位）；或缩范围 |
| 末尾有「结论条数上限（平台补充）」 | 报告的结论条数上限（平台常量 20，**不可配**） | 按严重度门槛过滤本来就是设计 —— 真需要看全量结论就读报告正文，异常清单只是摘要 |
| 状态是「降级：提示词超出模型上下文窗口，已压缩上下文后出结论」 | 整份提示词相对窗口太大 | 先看窗口：（内置 + 配置值）压到窗口的 60% 以内；或换窗口更大的模型；或把范围缩到单个提交 |
| 「信息缺口（平台补充）」里说某个分片没跑成 | 分片规模超出这一档 | 关掉子代理模式（回到单代理），或加大预算让池变深 |
| 报告说「本次只看到 M/N 个文件」 | 取样上限（clamp 200~500，**不可配**） | 名字没列出 ≠ 读不到（模型可点名索取）；覆盖率低是窗口的结构上限，见 measurements 第〇节 |
| 一次分析越来越慢、同步任务在排队 | 频率太高 | 分析间隔拉长；或关掉一些配置的自动分析 |

## 反例（这几种配法一定是错的）

- **预算 2,000,000、窗口 200k**：整份提示词会被压到 120,000，用户那部分只剩约 104,000。
- **想靠加预算无限抬高索取**：每片封顶 60 次 —— 超过它再大的预算也不会变成更多索取。
- **给单提交分析操心分片**：子代理与推导只对周版本生效，单提交永远是单代理。
- **去改已经收敛的键**：`max_tool_requests` / `subagent_count` 等提交会直接 400
  （`endpoint_service.RETIRED_FIELDS`）—— 那是刻意的，别找绕过法。

## 交付给用户时怎么说

给出四样东西，缺一样用户就没法自己判断：

1. **量出来的规模**（提交数、真实文件数、清单列出几个、有没有大配表）+ 是哪一档；
2. **预算建议**（唯一要配的数字）+ 平台会推导出的那组数（分片 / 每片轮次与索取 / 取样 /
   异常上限，从预算计划或 `derive_family_sizing` 口算）；
3. **算式复核**：预算 ≥ 清单 + 基线 + 知识包 + 每片索取 × 11,000；窗口不够时给出
   「窗口可用额度」与反解结果，并如实说「这个窗口下只能到 X 次」；
4. **预期代价**：大约多少分钟、多少个代理、总调用次数量级。

改完预算建议**跑一次真实分析**再下结论：看报告首行的规模是否与预期一致、状态是不是
「完成」（降级会写明是哪一种）、预算计划里「家族共享池」与「推导依据」两行是否与
口算一致、面板上的 token 与费用是不是在预算内。
