# 按变更规模定 AI 分析参数

这个平台的 AI 分析有五个互相咬合的数字。**它们不能各调各的** —— 平台里有一条测试
（`tests/test_ai_models_and_migration.py::test_the_prompt_budget_can_honor_the_request_budget`）
专门守着这件事，随手调大一个、忘了另一个，会以一种很安静的方式变坏：模型照常索取 N 个文件，
其中一半被截断，而它**分不清**「预算不够」和「文件就这么大」，于是把残缺当全部写进结论。

所以顺序永远是：**先量规模 → 再定档 → 再验自洽 → 最后才谈时间与钱**。

## 〇、先记住一条换算口径

平台把**字符**当预算单位（不是 token），换算口径是 **1 token ≈ 1 字**：
窗口 1M token 对应 600,000 字的水位，200k token 的窗口对应 **120,000 字**。
下面所有「字」都是按这条口径算的。

## 第一步：量规模（四条尺子）

| 尺子 | 为什么是它 | 怎么量 |
|---|---|---|
| **本版本真实改动的文件数** | 决定清单大小与档位 | 报告首行「本次变更共 N 个提交、M 个文件」；被取样时另有一句「还有 N 个名字没有列出来」，两个数都要看 |
| **清单里实际列出的文件数** | 清单是每份提示词里最大的一块，第一轮必发；被取样后它远小于真实文件数 | 同上；或按「真实文件数 与 取样上限 取较小值」估 |
| **提交数** | 决定清单里的提交头与元数据 | 同上 |
| **有没有大配表 / 大文件** | 单条上下文上限 11,000 字（配表正文同值），大文件必须靠行窗口或 `file_diff` 反复索取 | 改动文件里 `.xlsx` 的数量与体积；单文件改动行数 |

从仓库量（把区间换成这个版本的两个提交）：

```bash
git log <起始>..<结束> --oneline | wc -l                    # 提交数
git diff --shortstat <起始>..<结束>                          # 文件数、增删行数
git diff --name-only <起始>..<结束> | grep -c '\.xlsx$'      # 配表数（按项目实际后缀改）
```

**没有仓库、或只想估个大概**：用平台跑一次真实分析，读报告首行的「N 个提交、M 个文件」。
那是平台自己数的，比估算准；第一轮永远会跑完，代价只是这一次分析的时间。

## 第二步：定档

档位是按「预算要装得下什么」倒推的（算式见第三步）。**每一档的清单字数是这一档的隐含前提**，
写出来是让算式可复核：

| 档 | 真实文件数 | 假设列出的文件数（取样后） | 清单字数 | 提示词预算 | 最大轮次 | 索取上限 | 单次异常上限 | 子代理 |
|---|---|---|---|---|---|---|---|---|
| 小 | ≤ 50 | ≤ 50 | ~3,500 | 150,000 | 6 | 10 | 20 | 关（1） |
| 中 | 50 ~ 300 | ≤ 300 | ~21,000 | 300,000 | 8 | 20 | 20 | 1~2 |
| 大 | 300 ~ 800 | ≤ 200（被取样） | ~14,000 | 560,000（出厂默认） | 8 | 40（默认） | 20 | 3（默认） |
| 超大 | > 800，或有超大配表 | 200（被取样） | ~14,000 | 720,000 | 10~12 | 60 | 30 | 4~6 |

三条口径：

- **「大」与「超大」两档都假设清单已被取样**（默认取样上限 200）。真实文件数超过 200 之后，
  清单不再随文件数增长 —— 多出来的文件由模型按需索取，钱花在索取次数上。
- **周版本与单提交分开看**。子代理只作用于周版本；单个提交的分析按「小/中」就够。
- **「超大」那一行要先确认模型窗口**：预算的上限是「窗口 × 60%」。窗口 200k token 的模型，
  把预算填 720,000 也会被压回 120,000 —— **填了等于没填**。先看端点声明的窗口，再决定预算。

## 第三步：验自洽（这一步不能跳）

```
提示词预算 ≥ 12,000（系统提示词：平台自检用的下限）
           + 项目知识包 + 项目补充指令（两项各自上限 20,000 字）
           + 6,000（历史结论基线，每轮都带）
           + 清单字数
           + 索取上限 × 11,000（单条上下文上限）
```

三个用法：

- **正向检查**：把这一档的五个数字代进去，右边必须 ≤ 左边。
- **反解索取上限**（窗口把预算顶死时最有用的一个动作）：
  `索取上限 ≈ (预算 − 12,000 − 6,000 − 清单字数) ÷ 11,000`。
  例：预算被窗口压到 120,000、清单 14,000 → 88,000 ÷ 11,000 ≈ **8 次**。
- **加索取上限要同时加预算**：每加 10 次索取，至少加 **110,000 字**；
  40 → 60 就是 560,000 → **780,000**。

两处实际数值上的提醒：

- **闸门按「大版本清单」校准**（约 87,000 字），而小/中档的清单远小于此 —— 所以拿闸门去
  验小档的 150,000 会「失败」，那是**预期**：闸门是给「大档及以上」用的下限检查，
  不是通用校验。反过来，系统提示词实测约 16,000 字（闸门按 12,000 算），
  项目知识包写满还会再加最多 40,000 —— 配数字时按实际，别只按闸门。

改完参数跑一次闸门（它是一组数字之间的自洽检查，会真的拦住你）：

```bash
python -m pytest -q tests/test_ai_models_and_migration.py -k budget
```

## 第四步：代价（时间与调用次数）

| 项 | 实测口径 |
|---|---|
| 一次周版本分析（3 分片） | **17 ~ 21 分钟**（多次运行的区间；同一批运行的 5 个代理合计 31 次模型调用） |
| 代理调用次数 | 每个代理各跑若干轮，**每一轮 = 一次模型调用**；一次分析 ≈ 汇总(1) + 分片(n) + 对账轮(0 或 1) 个代理的轮次之和 |
| 分片是**串行**的 | 一个跑完再跑下一个，所以墙钟随分片数与轮次增长（不是并行） |
| 每个分片拿到的额度 | 就是配置值**本身**，不按分片平分；整次分析的索取次数上限 ≈ 分片数 × 配置值（用不掉不花钱） |
| worker | 一次分析独占后台 worker 十几到二十几分钟，期间同步/缓存类任务排队等它 |

**别一次拉满。** 分片 6 + 索取 100 是 7 个代理的轮次之和，而多数项目的真实瓶颈是「轮次不够」
或「结论被上限截掉」，不是索取次数不够。

## 症状 → 该调哪一个

| 报告/面板上看到 | 真正缺的是 | 怎么调 |
|---|---|---|
| 「轮次用尽，基于已有证据出结论」 | 轮次 | 最大轮次 +2~4；或把分析范围缩小到单个提交 |
| 「索取额度用尽」 | 索取次数 | 索取上限 +10（**同时**按第三步加预算） |
| 末尾有「结论条数上限（平台补充）」 | 报告的结论条数上限 | 调「单次异常上限」（**不是**上下文条数） |
| 状态是「降级：提示词超出模型上下文窗口，已压缩上下文后出结论」 | 预算相对窗口太大 | 先看窗口：预算压到窗口的 60% 以内；或换窗口更大的模型；或把范围缩到单个提交 |
| 「信息缺口（平台补充）」里说某个分片没跑成 | 分片规模超出这一档 | 关掉分片（回到单代理）或调大轮次/索取 |
| 报告说「本次只看到 M/N 个文件」 | 取样上限 | 调大取样上限；但更省的是按单个提交分析 |
| 一次分析越来越慢、同步任务在排队 | 频率太高 | 分析间隔拉长；或关掉一些配置的自动分析 |

## 反例（这几种配法一定是错的）

- **索取上限 0** 不是「省钱的档」，而是「一次上下文都不给」：报告只能基于变更清单。
- **预算 2,000,000、窗口 200k**：会被水位压回 120,000 字，实际比默认值小得多。
- **只调索取上限、不调预算**：多出来的索取会被静默截断。
- **给单提交分析开 6 个分片**：调用次数按代理数放大，而单个提交的维度根本不够分。

## 交付给用户时怎么说

给出四样东西，缺一样用户就没法自己判断：

1. **量出来的规模**（提交数、真实文件数、清单列出几个、有没有大配表）+ 是哪一档；
2. **五个数字**（预算 / 轮次 / 索取上限 / 分片数 / 异常上限）+ 一句为什么是这一档；
3. **算式复核**：预算 ≥ 右边那一串（第三步），窗口不够时给出反解出来的索取上限；
4. **预期代价**：大约多少分钟、多少个代理、总调用次数量级。

改动参数之后建议**跑一次真实分析**再下结论：看报告首行的规模是否与预期一致、状态是不是
「完成」（降级会写明是哪一种）、面板上的 token 与费用是不是在预算内。
