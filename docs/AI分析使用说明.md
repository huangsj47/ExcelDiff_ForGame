# AI 变更风险分析使用说明

本文面向**测试（QA）**同学：说明平台里的 AI 变更风险分析**能帮你做什么**、
**报告怎么读**，以及它**看不到什么**。

- 想直接上手：看 [第 2 节](#2-在哪用三个入口) 与 [第 3 节](#3-报告怎么读)。
- 报告结论对不上你的判断时：直接看 [第 7 节 它看不到什么](#7-它看不到什么重要) 与
  [第 8 节 常见疑问](#8-常见疑问faq)。
- 管理员向的配置项在 [第 10 节](#10-配置项一览管理员)。

---

## 1. 这是什么

给一个版本（或一次提交）的变更，自动产出一份**面向回归的风险说明**：这次改了什么、
影响哪些系统、**建议测什么**、**回归哪些老功能**、上线与回滚要盯什么。

它不是「自动验收」，也不替代你看 diff。它更像一个**把全部变更清单读完的助手**：
一个周版本可能有几百个改动文件（线上 G119 的一次周版本是 767 个），你不可能逐个翻完；
它翻完了，并且告诉你**哪几处最值得先看**，以及理由。

一句话定位：**帮你决定「这个版本重点测哪几块」，并给出依据。**

## 2. 在哪用（三个入口）

| 入口 | 位置 | 覆盖范围 | 会自动跑吗 |
|---|---|---|---|
| 周版本 Diff 页 | `/weekly-version-config/<id>/diff` 右上角 **「AI分析」** 按钮 | 整个周版本（可缩小范围，见第 5 节） | **会**，默认每小时检查一次，有变更才跑 |
| 单提交 Diff 页 | 提交 diff 页右上角 **「AI分析」** 按钮 | 这一次提交 | 不会，只能手动 |
| 项目合并视图 | 版本卡片上的 **「版本AI分析：未分析」** 标签（点它打开抽屉） | 该周版本 | 同周版本 |

抽屉（右侧滑出）里有：

- **「刷新结果」**：只读已保存的结果，不重跑。
- **「重新分析」**：重跑一次；已经有过结果时会先弹确认框
  「已有分析结果，确定重新分析吗？」。

> **打开抽屉不会自动开跑分析。** 想跑就按「重新分析」。
> 自动分析只对**周版本**存在，单提交只能手动。

自动分析可以在项目里关掉：项目管理页 →「AI 分析配置」→「周版本自动分析」。
关掉之后，连**已经排上队**的那次也会被跳过（不会在你重启平台后偷偷跑一次）。

## 3. 报告怎么读

报告是 Markdown，固定 **7 个一级标题**，顺序固定：

| 章节 | 你可以怎么用 |
|---|---|
| `# 变更理解` | 一句话搞清「这次到底改了什么」，用来对齐你和策划/程序的理解 |
| `# 变更内容摘要` | 按模块/表列出改动范围 |
| `# 影响面分析` | 这次改动会牵动哪些系统、哪些老功能 |
| `# 风险评估` | **结论在这里**：风险点、严重度、判断依据 |
| `# 测试建议` | **QA 直接用**：建议测什么、怎么复现、要覆盖哪些组合 |
| `# 回归建议` | **QA 直接用**：哪些老功能需要复测（改了 A 影响 B 的那类） |
| `# 上线与回滚关注点` | 上线要盯什么、出问题怎么回退 |

抽屉顶部有一行元信息（meta），形如：

```
最近分析：2026-09-17 21:24 | 风险等级 高风险 | 范围 仅配表仓库
```

**风险等级**共 5 档：低风险 / 中低风险 / 中风险 / 中高风险 / 高风险。

> ⚠️ 如果 meta 里出现「本次未取得完整结论（原因），该等级仅按变更规模估算，**不是**模型评估结果」，
> 说明这次**没拿到完整报告**，那个等级只是按改动文件数量估出来的 ——
> 这种情况**不要**把它当结论用。

报告正文里出现的「已截断」「省略了多少字」是正常的：平台对每次取数都有字数上限，
超出会截断并**如实记账**（宁可告诉你"这块没看全"，也不会假装看全了）。

## 4. 结论的「门槛」与异常清单

平台会把报告里够格的结论抽成结构化条目（严重度 / 置信度 / 证据 / 涉及文件），并按门槛过滤：

- 默认门槛：**严重度 ≥ 高** 且 **置信度 ≥ 高**。
- 低于门槛的结论**只写进报告正文**，不进异常清单（这是配置页上的原话）。
- 单次最多保留 **10 条**，超出按严重度优先，并写明丢了多少条。
- 置信度只有「高 / 极高」两档 —— 模型被要求**没把握就别报**。
  所以「报告里没提」**不等于**「这里没问题」，只等于「它没有足够证据认定这是问题」。

> **两点如实说明（免得你找按钮找不到）：**
>
> 1. 异常清单目前**界面上没有单独列出**，你能看到的就是上面那份 Markdown 报告正文。
> 2. 「待确认 / 已确认 / 已忽略」这套人工处置，**数据层已经存在，但界面还没有入口**。
>    现在不用找那个按钮；需要标记时找平台维护者。它的设计语义见
>    [第 9 节](#9-原理简述)，其中「已忽略」不会变成「永远看不见」。

## 5. 分析范围（只影响「下一次」分析）

周版本抽屉里有一个「分析范围」下拉（当这个版本关联了多个仓库时出现）：

- `全部仓库（N 个）` / `只看配表仓库` / `只看代码仓库` / `只看「某个仓库」`

三条要点：

1. 这个下拉**只影响下次分析**；当前显示的结果覆盖哪个范围，看 meta 行上的范围文字。
2. 报告里会**写明本次范围**，并且被明确要求**不要把结论说成覆盖了整个版本**
   （否则「只看了配表」会被读成「整个版本没问题」）。
3. 选了范围但里面没有改动文件时，会直接提示
   「选定的分析范围里没有改动过的文件，换一个范围再试。」——不会跑一次空分析。

## 6. 它能「看到」什么

模型不能直接读你的仓库，只能通过**四个只读工具**按需索取（**只读**：不会改任何仓库、
不会触发 clone）：

| 工具 | 作用 | 单次上限 |
|---|---|---|
| `commit_detail` | 某个提交改了哪些文件（读平台数据库，不碰 Git） | 6,000 字 |
| `file_diff` | 某个文件在某个提交上的 diff（Excel 走结构化差异） | 11,000 字 |
| `file_content` | 某个文件在某个提交上的完整内容 | 11,000 字 |
| `read_reference` | 读平台内置的评审规程文档 | 11,000 字 |

- 索取次数默认 **20 次**，按**整次分析累计**（跨轮次），命中缓存也计入。
- 模型被要求**先分诊、再点名**：先看变更清单判断哪里可疑，再针对 **4~8 个**文件要 diff，
  而不是一上来把整批 diff 全要过来。
- 越权索取会被丢掉：只能要**本批次真实出现过**的提交、以及**那个提交确实改过**的文件。

## 7. 它看不到什么（重要）

这一节是**故意写全**的：这些边界决定了报告什么时候会「漏」，知道它们你才知道该怎么追问。

1. **不知道「为什么这么改」。** 周版本的变更清单里**没有提交说明**（平台只存了最新提交号）。
   所以它对改动的意图是推测出来的 —— 有疑问时以提交说明和程序员的说法为准。
2. **清单很长时只列出部分文件名**（上限约 6 万字符；767 个文件的全量清单装得下）。
   但**能读的范围给的是全部**：名字没列出来的文件，它依然可以点名索取 diff。
   报告里出现「还有 N 个文件的名字没有列出来」时，说的就是这种情况 ——
   那是**「不知道路」而不是「读不到」**。
3. **只覆盖被提交进仓库的文件。** 没 commit 的东西它看不到。
4. **表与生成物的配对在本项目基本不会生效。** 平台会尝试把「表 ↔ 它的生成物」配成一组
   一起看（表改了、产物没跟上，这种事只有一起看才发现）。但在 G119 上两类名字对不上
   （表名是中文、生成物里是英文），所以这类关联提示**现在基本都是 0 组** ——
   这是**如实**的结果，不是功能没生效。
5. **预算按字符估算，不是 token。** 平台也不知道你的模型上下文窗口有多大；
   只有在端点**主动声明**了窗口、且「按最乐观的 1 字 1 token 也已超窗」时，
   才会把预算压回窗口大小。换模型后建议让管理员确认一下预算。
6. **每次取数都有上限**（见第 6 节），所以「这次没看到某个文件」是可能的 ——
   但这种情况平台会让模型写成**「信息缺口」**，而不是写成「没问题」。

## 8. 常见疑问（FAQ）

**Q：抽屉一直显示「AI 分析进行中...」，是不是卡住了？**
A：三种可能，看 meta 行能区分：① 真在跑（首次可能要几分钟）；② 上次被**平台重启**
打断，会显示「平台重启，本次分析被中断（未跑完，可以重新分析）。」——直接重新分析即可；
③ 确实卡死，超过 1 小时会被调度器重置（提示「AI分析任务超时，已被调度器重置」）。

**Q：提示「请在项目概览页的「AI 分析配置」里补全：接口地址 / 模型名字 / Token」？**
A：AI 配置不全（缺哪项会列出来）。这属于项目管理员的配置，找管理员补。

**Q：报告只写了一半就停了 / 没有 JSON 结构？**
A：模型没按协议输出，平台会**按 markdown 降级保存**，并在结果里标出降级原因
（例如「轮次用尽」「上下文索取额度用尽」「模型没有按协议输出 JSON」）。
降级不等于失败：报告仍然可用，只是可能不完整。

**Q：报告说没问题，但我确实发现了 bug。**
A：按这个顺序排查：① 它在**范围外**吗（meta 行的范围）？② 那个文件**是不是这次改的**
（只分析本批次的变更）？③ 清单里没列出来、它也没去点名索取？④ 取数失败（报告里会写「信息缺口」）。
**报告是辅助，不是验收结论** —— 它给的是「先看哪里」，不是「这里一定没问题」。

**Q：为什么两次分析的结果不一样？**
A：设计如此。第一次是**全量**；之后是**增量**（只带上次分析之后变化的部分），
并且每次都把「上次报过的问题」清单交给模型，要求它逐条标注
**仍成立 / 已修复 / 已被推翻**。报告的语义是「这个版本截至目前的那一份」，
**不是**「本轮新增了 N 条」。

**Q：某个问题上次报了，这次没了，是修好了吗？**
A：报告语义是「截至目前的完整结论」，所以从清单里消失通常意味着它被判定为已修复或被推翻。
但**判定需要依据**（模型被要求给出依据）——拿不准时以实际验证为准。

## 9. 原理简述

**一句话：** 平台把「这个版本改了哪些文件」整理成一份清单交给大模型，
模型**看不到 diff**，只能按需点名索取；拿到证据后再输出一份固定结构的报告，
平台把它过门槛、去重、封顶、入库，最后在页面上渲染成 Markdown。

链路 6 步：

1. **组装输入**：平台从数据库取出本批次的变更文件（含每个文件的提交号），
   分成两份清单 —— 一份是**给模型看的名字**，一份是**允许它读的范围**（白名单给全部）。
2. **渲染变更清单**：把「提交 → 文件」渲染成文本。清单里**不含任何 diff**。
3. **拼系统提示词**：平台内置的评审规程（`skills/version-diff-review/SKILL.md`）
   + 项目知识包 + 项目补充指令。**前两者优先级高于项目补充指令**，补充指令不能放宽内置协议。
4. **多轮取数**：模型输出「我还需要哪些上下文」→ 平台用第 6 节那四个只读工具去取
   （带缓存、截断、预算与记账）→ 回灌给模型 → 直到它给出最终结论，
   或轮次/额度耗尽（耗尽就**降级出结论**，不报错）。
5. **结果加工**：过门槛 → 证据裁剪（每条最多 3 条证据）→ 近似去重 → 封顶 10 条 → 入库
   （连同逐轮 trace，可回答「为什么这次只报了两条」）。
6. **渲染**：通过 SSE 逐段推给页面，或读已保存结果；页面按 Markdown 子集渲染
   （只支持标题/列表/引用/代码块/粗体/行内码，**不支持链接与表格**，不支持的写法按普通文字显示）。

**提示词里几条最要紧的纪律**（这些决定了报告的可信度）：

- **不许把「没看到」说成「没有」。** 取数失败会显式写成「信息缺口」，
  并明确要求「不要凭猜测给出结论」。
- **名字没列出来 ≠ 读不到。** 名字没列全时，要求它用 `commit_detail` 查出提交的完整文件清单，
  再点名索取 —— 而不是当成读不到。
- **证据必须具体。** 「配置可能有问题」这种空泛表述不算证据，会被丢弃；
  证据要指到文件、字段、ID、行或提交。
- **先分诊再点名。** 不允许一上来索取整批 diff，必须先判断哪里可疑，再要 4~8 个文件。
- **反误报。** 看着像问题但可能是「阶段性屏蔽 / 半成品提交 / 联调保护 / 灰度开关 /
  故意提前 return / 故意注释掉的事件」时，默认动作是**先索取能区分两种解释的上下文**，
  而不是直接报成问题。
- **九个维度都要留痕**（`config_id` 配置 ID、`config_value` 配置取值、
  `config_data` 配置数据本身、`value_sanity` 数值是否合理、`config_linkage` 单表连锁、
  `module_coupling` 模块耦合、`code_logic` 代码逻辑、`version_branch` 版本分支、
  `process` 流程），没命中也要写明理由，防止「只报容易报的」。
- **配置数据本身是否说得通，是单独一个维度。** 配表 diff 里最常见的问题不在 ID、也不在
  数值边界，而在**这一行、这一格自己是否成立**：描述/备注与同行取值互相打架（只改了一列
  文案、它描述的字段没跟着改）、新增或改动行漏填必填列、类型与日期格式和同表其它行不一致、
  枚举值不在允许集合里、全角半角或首尾空格（平台按文本原样比较，`'  x  '` 与 `'x'` 是
  两回事）、复制粘贴出来只改了一半的重复行、以及列之间的联动规则（「A 列为空则 B 列为空」
  这类约定）被打破。报告里对这类问题要指到**具体是哪一行、哪一列、与哪一列矛盾**。
- **数值是否合理，是单独一个维度。** 上面那条看的是「这一行自己说不说得通」，
  这条看的是**这个值放在这个系统或玩法里合不合理**：可以从三个方向问 ——
  ① **量级对不对**：同一张表里同类行（同品质、同等级、同稀有度）本来是什么数量级，
  改后是不是跳了一两个数量级，例如道具价值 `1000` 改成 `1000000`、奖励数量
  `10` 改成 `100000`；② **经济闭环有没有被打破**：买入价与卖出/回收价的关系反了
  （售价 `100` 的东西卖给商店能卖 `10000`）、合成或分解的产出大于投入 —— 这类配置
  会被玩家刷爆，是最高优先级之一；③ **单位与档位**：百分比与万分比、秒与毫秒、
  元与分，以及这个字段本来该在的取值区间（品质档位、等级段）。
  **这条维度的门槛比其他维度更严**：报告里必须说清是跟哪一行、哪个字段、哪张表比出来的
  （或者依据项目知识包里的哪条规则），**给不出比较基准的不许当成结论报** ——
  「这个值看起来很大」是猜测不是证据，而策划改数值是日常操作。
  反过来，新系统、新玩法的首次填数本来就没有历史基准，它「看起来很大」可能只是
  因为这个系统还没放过量，这种情况会写成待确认。
- **模块耦合必须落成测试风险点。** 平台会专门分析这次改动**跨了哪几个模块、模块之间靠
  什么绑在一起**，并盯住最容易出事的一类：**本该成对改动的两边只改了一边**（配表 ↔ 它的
  生成物、客户端 ↔ 服务端、协议 ↔ 打包解包、字段 ↔ 读取方、公共件 ↔ 它的调用方）。
  只要认定存在耦合，报告里就必须说清「哪两端、靠什么耦合、这次改了哪一端、不同步会以什么
  现象暴露」，并把耦合点写进「测试建议」——**只说「注意联调」不算**。
  针对耦合的测试风险点至少要覆盖三条路径：两端都改了的、只改了一端的、
  以及老数据 / 老客户端的。
- **它读不到耦合的另一端时会怎么写？** 它只能读本批次改动过的文件。所以「另一端这次
  根本没改」（能从文件清单看出来）会写成结论；而「另一端不在这批变更里、我读不到」
  只能写成**待确认的耦合点** —— 这两种说法在报告里是分开的，看到「待确认」就说明需要
  人工去确认那一端是否同步改了。
- **报告是累积语义**：产出的是「这个版本截至目前的那一份」，不是「第 N 份」；
  已报过的不重复报，已修复的从清单里去掉，报告里不写「本轮新增 N 条」。

**关于人工处置（设计语义，界面入口待补）**：

- `待确认` / `已确认` 的结论，下一轮会作为「仍待处理」继续带着。
- `已忽略` 的结论**默认不再提**，但**它涉及的文件又被改动时，会重新出现**
  （证据过期了，需要重新确认）。这条是「忽略不会变成永远看不见」的保证。

## 10. 配置项一览（管理员）

位置：项目管理页 →「AI 分析配置」。**仅项目管理员可修改**；
Token 只以密文保存在服务端、**不会回显**（留空表示沿用已保存的）。

| 字段（界面标签） | 默认值 | 取值范围 | 说明 |
|---|---|---|---|
| 接口地址 | 空 | — | OpenAI 兼容端点；可选「OpenAI 官方 / 自定义端点」 |
| 模型名字 | 空 | — | 可以手填（端点取不到列表时） |
| API Token | 空 | — | 只存密文，不回显 |
| 周版本自动分析 | 开 | 开/关 | 关掉后连已排队的任务也会跳过 |
| 分析间隔（分钟） | 60 | 5~10080 | 仅在开启自动分析时生效 |
| 清单过长时的取样上限 | 200 | 1~5000 | **只**在清单长到列不下时决定取样多少个；不再限制「能分析多少文件」或「能读多少」 |
| 最大分析轮次 | 8 | 1~30 | 多轮取数的轮次上限 |
| 上下文索取上限 | 20 | 0~100 | 见第 6 节；调大会同时抬高能带走的条数上限 |
| 提示词字符预算 | 360000 | 10000~2000000 | 按字符估算，不是 token |
| 单次请求超时（秒） | 300 | 10~3600 | 分析是非流式请求，网关要先吃下整份提示词 |
| 严重度门槛 | 高及以上 | 高及以上 / 仅严重 | 见第 4 节 |
| 置信度门槛 | 高及以上 | 高及以上 / 仅极高 | 见第 4 节 |
| 单次异常上限 | 10 | 0~200 | 超出按严重度优先保留 |
| 项目补充指令 | 空 | ≤20000 字 | 追加在最后，**不能**放宽内置协议 |
| 项目补充知识 | 空 | ≤20000 字 | 项目背景、红线、历史高频事故 |
| 模型单价表（JSON） | 空 | ≤20000 字 | 只影响「AI 消耗」页面上的**费用估算**，见第 12 节 |

> **改了「索取上限」记得同时看「字符预算」与「单次异常上限」**：
> 这几个数字是互相约束的（预算要装得下「系统提示词 + 变更清单 + 历史结论 + 索取次数 × 单条上限」）。

## 12. 消耗与费用（token / 缓存命中）

分析跑了很多轮、每轮都要把整份提示词（系统提示词 + 变更清单 + 历史结论 + 上一轮取回的
上下文）再发一遍，**花了多少**这件事在这里看。

**入口**：顶部导航 →「AI 消耗」。页面上先给你一行平台合计，再按项目、周版本（分组键）
与单次运行逐层下钻；AI 分析抽屉的底部也有一行「本次消耗 … tokens · 命中缓存 …」，
点旁边的「明细」看这一轮的逐次明细。

### 各列什么意思

| 指标 | 口径 |
|---|---|
| 输入 token | 每次模型调用的输入合计，**逐轮累加**（每轮都重发上一轮的上下文，所以后几轮更贵） |
| 其中命中缓存 | **上游接口报的** prompt cache 命中 token。与「工具结果在本次分析里的内存缓存」是两件事，界面上分开显示 |
| 输出 token | 模型生成的 token |
| 缓存命中率 | 命中缓存的输入 ÷ 输入合计。**只有分子分母都上报了才给这个数** |
| 费用估算 | 按你配置的单价表算出来的金额，见下 |
| 上下文索取 / 取回字符 | 模型索要了几次文件、实际取回多少字符（被预算拒绝、被截断的也会各自计数） |

### 「未上报」不等于 0

接口不保证回缓存字段（不同厂商的字段名也不一样）。**没回的时候显示「未上报」、
命中率一列留空** —— 那表示未知，不是「一次都没命中」。同理，本功能上线之前的分析
没有采集过用量，明细里显示「本次用量未采集」，也不会显示 0。

### 费用是估算，且必须自己配单价

接口只回 token 数、**不回金额**，所以金额是按你填的单价表算的：

```json
{
  "version": "2026-09-18",
  "currency": "CNY",
  "models": {
    "model-name":      {"input": 2.0, "output": 8.0, "cache_read": 0.2},
    "gateway-model-*": {"input": 1.0, "output": 2.0}
  }
}
```

- 单位是**每 100 万 token**；`cache_read`（命中缓存的单价）不填时，命中那部分按未命中价
  计入，页面上会注明「费用偏保守」。
- 模型名按「精确 → 前缀（`xxx-*`）」匹配，**不做包含匹配**（那会让 `gpt-4` 命中 `gpt-4o`，
  价格差一个量级却毫无提示）。
- **改单价必须同时改 `version`**。每次运行都会把当时的版本号记下来；面板上的金额一律按
  **当前**价格表重算，并在明细里注明「这条记录落库时的单价表版本是 X」。
- 没配（或算不出，例如模型不在表里）时**不显示金额**，并说明原因 —— 不会回落到 0。
