# AI 变更风险分析使用说明

本文面向**测试（QA）**同学：说明平台里的 AI 变更风险分析**能帮你做什么**、
**报告怎么读**，以及它**看不到什么**。

- 想直接上手：看 [第 2 节](#2-在哪用三个入口) 与 [第 3 节](#3-报告怎么读)。
- 报告结论对不上你的判断时：直接看 [第 7 节 它看不到什么](#7-它看不到什么重要) 与
  [第 8 节 常见疑问](#8-常见疑问faq)。
- 管理员向的配置项在 [第 10 节](#10-配置项一览管理员)。

---

## 1. 这是什么

给一个版本（或一次提交）的变更，自动产出一份**面向回归的风险说明**：这次改了什么、
影响哪些系统、**建议测什么**、**回归哪些老功能**、上线与回滚要盯什么。

它不是「自动验收」，也不替代你看 diff。它更像一个**把全部变更清单读完的助手**：
一个周版本可能有几百个改动文件（线上 G119 的一次周版本是 767 个），你不可能逐个翻完；
它翻完了，并且告诉你**哪几处最值得先看**，以及理由。

一句话定位：**帮你决定「这个版本重点测哪几块」，并给出依据。**

## 2. 在哪用（三个入口）

| 入口 | 位置 | 覆盖范围 | 会自动跑吗 |
|---|---|---|---|
| 周版本 Diff 页 | `/weekly-version-config/<id>/diff` 右上角 **「AI分析」** 按钮 | 整个周版本（可缩小范围，见第 5 节） | **会**，默认每小时检查一次，有变更才跑 |
| 单提交 Diff 页 | 提交 diff 页右上角 **「AI分析」** 按钮 | 这一次提交 | 不会，只能手动 |
| 项目合并视图 | 版本卡片上的 **「版本AI分析：未分析」** 标签（点它打开抽屉） | 该周版本 | 同周版本 |

抽屉（右侧滑出）里有：

- **「刷新结果」**：只读已保存的结果，不重跑。
- **「重新分析」**：重跑一次；已经有过结果时会先弹确认框
  「已有分析结果，确定重新分析吗？」。

> **打开抽屉不会自动开跑分析。** 想跑就按「重新分析」。
> 自动分析只对**周版本**存在，单提交只能手动。

自动分析可以在项目里关掉：项目管理页 →「AI 分析配置」→「周版本自动分析」。
关掉之后，连**已经排上队**的那次也会被跳过（不会在你重启平台后偷偷跑一次）。

## 3. 报告怎么读

报告是 Markdown，固定 **7 个一级标题**，顺序固定：

| 章节 | 你可以怎么用 |
|---|---|
| `# 变更理解` | 一句话搞清「这次到底改了什么」，用来对齐你和策划/程序的理解 |
| `# 变更内容摘要` | 按模块/表列出改动范围 |
| `# 影响面分析` | 这次改动会牵动哪些系统、哪些老功能 |
| `# 风险评估` | **结论在这里**：风险点、严重度、判断依据 |
| `# 测试建议` | **QA 直接用**：建议测什么、怎么复现、要覆盖哪些组合 |
| `# 回归建议` | **QA 直接用**：哪些老功能需要复测（改了 A 影响 B 的那类） |
| `# 上线与回滚关注点` | 上线要盯什么、出问题怎么回退 |

抽屉顶部有一行元信息（meta），形如：

```
最近分析：2026-09-17 21:24 | 风险等级 高风险 | 范围 仅配表仓库
```

**风险等级**共 5 档：低风险 / 中低风险 / 中风险 / 中高风险 / 高风险。

> ⚠️ 如果 meta 里出现「本次未取得完整结论（原因），该等级仅按变更规模估算，**不是**模型评估结果」，
> 说明这次**没拿到完整报告**，那个等级只是按改动文件数量估出来的 ——
> 这种情况**不要**把它当结论用。

报告正文里出现的「已截断」「省略了多少字」是正常的：平台对每次取数都有字数上限，
超出会截断并**如实记账**（宁可告诉你"这块没看全"，也不会假装看全了）。

## 4. 结论的「门槛」与异常清单

平台会把报告里够格的结论抽成结构化条目（严重度 / 置信度 / 证据 / 涉及文件），并按门槛过滤：

- 默认门槛：**严重度 ≥ 高** 且 **置信度 ≥ 高**。
- 低于门槛的结论**只写进报告正文**，不进异常清单（这是配置页上的原话）。
- 单次最多保留 **10 条**，超出按严重度优先，并写明丢了多少条。
- 置信度只有「高 / 极高」两档 —— 模型被要求**没把握就别报**。
  所以「报告里没提」**不等于**「这里没问题」，只等于「它没有足够证据认定这是问题」。

> **两点如实说明（免得你找按钮找不到）：**
>
> 1. 异常清单目前**界面上没有单独列出**，你能看到的就是上面那份 Markdown 报告正文。
> 2. 「待确认 / 已确认 / 已忽略」这套人工处置，**数据层已经存在，但界面还没有入口**。
>    现在不用找那个按钮；需要标记时找平台维护者。它的设计语义见
>    [第 9 节](#9-原理简述)，其中「已忽略」不会变成「永远看不见」。

## 5. 分析范围（只影响「下一次」分析）

周版本抽屉里有一个「分析范围」下拉（当这个版本关联了多个仓库时出现）：

- `全部仓库（N 个）` / `只看配表仓库` / `只看代码仓库` / `只看「某个仓库」`

三条要点：

1. 这个下拉**只影响下次分析**；当前显示的结果覆盖哪个范围，看 meta 行上的范围文字。
2. 报告里会**写明本次范围**，并且被明确要求**不要把结论说成覆盖了整个版本**
   （否则「只看了配表」会被读成「整个版本没问题」）。
3. 选了范围但里面没有改动文件时，会直接提示
   「选定的分析范围里没有改动过的文件，换一个范围再试。」——不会跑一次空分析。

## 6. 它能「看到」什么

它拿到手的起点只有一份**变更清单**（提交信息 + 改了哪些文件），**里面没有 diff 正文**；
**要看哪一份，得它自己点名索取**。这不是「读不到 diff」——恰恰相反，下面这五个工具
就是专门用来取 diff 与文件正文的。模型不能直接读你的仓库，只能通过**只读工具**按需
索取（**只读**：不会改任何仓库、不会触发 clone）：

| 工具 | 作用 | 单次上限 |
|---|---|---|
| `commit_detail` | 某个提交改了哪些文件（读平台数据库，不碰 Git） | 6,000 字 |
| `file_diff` | 某个文件在某个提交上的 diff（Excel 走结构化差异） | 11,000 字 |
| `file_content` | 某个文件在某个提交上的内容（代码文件**默认只给改动附近的一段**，可点名要哪一段） | 11,000 字 |
| `read_reference` | 读平台内置的评审规程文档 | 11,000 字 |
| `find_references` | **在本次改动的文件里搜一个标识符**（字段名、协议名、函数名），只回「哪个文件的第几行」，不回正文 | 8,000 字 |

**内容超长时不是砍一刀，而是分段让你点名。** 上面除 `file_content` 之外的三个长内容工具
（`file_diff` / `read_reference` / `commit_detail`）在超长时会把内容按**结构**切成段
（改动块 / 文档小节 / 一个文件一段），并在开头写明**一共几段、这里是第几段、要看别的段
怎么写** —— 模型可以接着点名要后面的。所以报告里出现「共 5 段，这里是第 1-2 段」时，
那是**它自己知道没看全**，不是平台悄悄砍掉了中间。`file_content` 用的是另一套坐标：
行号（`"lines": "1180-1260"`）。

**`find_references` 是找「耦合的另一端」用的**：一个周版本 767 个文件，「这个字段还有谁在
读」原先只能靠猜文件名去逐个索取。它的搜索范围**只有本次改动的文件**（与其它工具同一条
白名单，不扩大读取面），非文本文件（配表）会被跳过。它给的回报里会写明**扫了几个、跳过了
几个、有没有到上限就停**：「没搜到」与「没搜完」是两回事 —— 只有扫完了才能说「本批次里
没有别处引用」。

- 索取次数默认 **20 次**，按**整次分析累计**（跨轮次），命中缓存也计入。
- 模型被要求**先分诊、再点名**：先看变更清单判断哪里可疑，再针对 **4~8 个**文件要 diff，
  而不是一上来把整批 diff 全要过来。
- 越权索取会被丢掉：只能要**本批次真实出现过**的提交、以及**那个提交确实改过**的文件。
- 代码文件的正文动辄几千行，`file_content` **默认只给一段**（400 行左右，**位置在本次改动
  附近**而不是文件开头 —— 模型没点名时平台从 diff 的块头里读出行号自己定位），正文每行带
  行号，抬头写明「共 N 行、下面是第 a–b 行、不是全文」。模型也可以点名要哪一段
  （请求里写 `"lines": "1180-1260"`），行号与 diff 里的 `@@` 是同一套坐标。
  这样给的代价是「一次只看一段」，换来的是**一次分析里能看的文件数**（单条上限只有
  11,000 字，整份塞进来等于把预算全花在一个文件上，而从中间截断的正文没有上下文价值）。
- **多节点部署（platform/agent 模式）下正文与「某一条提交的 diff」从哪来**：平台自己不
  clone 仓库（这是刻意的，见「平台配置说明」），所以这两样都由**业务节点上的 Agent** 在
  它的工作副本里取出，平台只读结果 —— 正文是 `file_content` 任务，单条提交的 diff 是
  `file_diff` 任务。于是有两条边界：**项目没绑 Agent**、或 **Agent 离线**时，这两样一时
  拿不到 —— 这时报告里会写成「信息缺口」（**并且要写明是哪个文件、取数是怎么失败的**），
  而不是「这个文件没问题」（这两句的区别是本模块的底线）。任务会留在队列里，Agent 上线后
  取回并落库，**下次分析直接命中、不再等**；在线时的等待也是有上限的（默认 15 秒），
  不会让一次分析卡在某个文件上。配表（`.xlsx`）的正文同样由 Agent 渲染成文本表格后再回传
  —— 两端**同一个渲染函数**，所以单机与多节点看到的表格内容一致。
- **周版本分析的 diff 与「某一条提交的 diff」不是同一份**：周版本分析优先读平台**已经算好
  并落库**的合并差异（就是周版本页面上那一份，覆盖整个窗口），只有当它读不到、或者模型
  点名问「某一条提交改了什么」时，才去业务节点上现算那一条提交的 diff ——
  现算回来的那份会在开头写明「只含这一条提交对这个文件的改动」，免得被当成整周的改动。

## 7. 它看不到什么（重要）

这一节是**故意写全**的：这些边界决定了报告什么时候会「漏」，知道它们你才知道该怎么追问。

1. **不知道「为什么这么改」。** 周版本的变更清单里**没有提交说明**（平台只存了最新提交号）。
   所以它对改动的意图是推测出来的 —— 有疑问时以提交说明和程序员的说法为准。
2. **清单很长时只列出部分文件名**（上限约 6 万字符；767 个文件的全量清单装得下）。
   但**能读的范围给的是全部**：名字没列出来的文件，它依然可以点名索取 diff。
   报告里出现「还有 N 个文件的名字没有列出来」时，说的就是这种情况 ——
   那是**「不知道路」而不是「读不到」**。
3. **只覆盖被提交进仓库的文件。** 没 commit 的东西它看不到。
4. **表与生成物的配对在本项目基本不会生效。** 平台会尝试把「表 ↔ 它的生成物」配成一组
   一起看（表改了、产物没跟上，这种事只有一起看才发现）。但在 G119 上两类名字对不上
   （表名是中文、生成物里是英文），所以这类关联提示**现在基本都是 0 组** ——
   这是**如实**的结果，不是功能没生效。
5. **预算按字符估算，不是 token。** 平台也不知道你的模型上下文窗口有多大；
   只有在端点**主动声明**了窗口、且「按最乐观的 1 字 1 token 也已超窗」时，
   才会把预算压回窗口大小。换模型后建议让管理员确认一下预算。
6. **每次取数都有上限**（见第 6 节），所以「这次没看到某个文件」是可能的 ——
   但这种情况平台会让模型写成**「信息缺口」**，而不是写成「没问题」。
7. **开了子代理模式时，可能有一整块维度没人看过。** 分片代理里只要有一个没跑成（上游
   出错、轮次用尽），或者因为预算不够被跳过，报告末尾的「信息缺口（平台补充）」里就会
   点名写出**是哪个分片、它负责哪几个维度**。那几块这一轮**没有任何人看过** ——
   读报告时看到那一段，要当「这里没有结论」，不是「这里没问题」。

## 8. 常见疑问（FAQ）

**Q：抽屉一直显示「AI 分析进行中...」，是不是卡住了？**
A：三种可能，看 meta 行能区分：① 真在跑（首次可能要几分钟）；② 上次被**平台重启**
打断，会显示「平台重启，本次分析被中断（未跑完，可以重新分析）。」——直接重新分析即可；
③ 确实卡死，超过 1 小时会被调度器重置（提示「AI分析任务超时，已被调度器重置」）。

**Q：提示「请在项目概览页的「AI 分析配置」里补全：接口地址 / 模型名字 / Token」？**
A：AI 配置不全（缺哪项会列出来）。这属于项目管理员的配置，找管理员补。

**Q：报告只写了一半就停了 / 没有 JSON 结构？**
A：模型没按协议输出，平台会**按 markdown 降级保存**，并在结果里标出降级原因
（例如「轮次用尽」「上下文索取额度用尽」「模型没有按协议输出 JSON」）。
降级不等于失败：报告仍然可用，只是可能不完整。

**Q：报告说没问题，但我确实发现了 bug。**
A：按这个顺序排查：① 它在**范围外**吗（meta 行的范围）？② 那个文件**是不是这次改的**
（只分析本批次的变更）？③ 清单里没列出来、它也没去点名索取？④ 取数失败（报告里会写「信息缺口」）。
**报告是辅助，不是验收结论** —— 它给的是「先看哪里」，不是「这里一定没问题」。

**Q：为什么两次分析的结果不一样？**
A：设计如此。第一次是**全量**；之后是**增量**（只带上次分析之后变化的部分），
并且每次都把「上次报过的问题」清单交给模型，要求它逐条标注
**仍成立 / 已修复 / 已被推翻**。报告的语义是「这个版本截至目前的那一份」，
**不是**「本轮新增了 N 条」。

**Q：某个问题上次报了，这次没了，是修好了吗？**
A：报告语义是「截至目前的完整结论」，所以从清单里消失通常意味着它被判定为已修复或被推翻。
但**判定需要依据**（模型被要求给出依据）——拿不准时以实际验证为准。

## 9. 原理简述

**一句话：** 平台把「这个版本改了哪些文件」整理成一份清单交给大模型 ——
清单里**只有提交信息与文件名，没有 diff 正文**，模型点名索取它要看的那几个文件；
拿到证据后再输出一份固定结构的报告，
平台把它过门槛、去重、封顶、入库，最后在页面上渲染成 Markdown。

链路 6 步：

1. **组装输入**：平台从数据库取出本批次的变更文件（含每个文件的提交号），
   分成两份清单 —— 一份是**给模型看的名字**，一份是**允许它读的范围**（白名单给全部）。
2. **渲染变更清单**：把「提交 → 文件」渲染成文本。清单里**不含任何 diff**。
3. **拼系统提示词**：平台内置的评审规程（`skills/version-diff-review/SKILL.md`）
   + 项目知识包 + 项目补充指令。**前两者优先级高于项目补充指令**，补充指令不能放宽内置协议。
4. **多轮取数**：模型输出「我还需要哪些上下文」→ 平台用第 6 节那五个只读工具去取
   （带缓存、截断、预算与记账）→ 回灌给模型 → 直到它给出最终结论，
   或轮次/额度耗尽（耗尽就**降级出结论**，不报错）。
5. **结果加工**：过门槛 → 证据裁剪（每条最多 3 条证据）→ 近似去重 → 封顶 10 条 → 入库
   （连同逐轮 trace，可回答「为什么这次只报了两条」）。
6. **渲染**：通过 SSE 逐段推给页面，或读已保存结果；页面按 Markdown 子集渲染
   （只支持标题/列表/引用/代码块/粗体/行内码，**不支持链接与表格**，不支持的写法按普通文字显示）。

**提示词里几条最要紧的纪律**（这些决定了报告的可信度）：

- **不许把「没看到」说成「没有」。** 取数失败会显式写成「信息缺口」，
  并明确要求「不要凭猜测给出结论」。
- **名字没列出来 ≠ 读不到。** 名字没列全时，要求它用 `commit_detail` 查出提交的完整文件清单，
  再点名索取 —— 而不是当成读不到。
- **证据必须具体。** 「配置可能有问题」这种空泛表述不算证据，会被丢弃；
  证据要指到文件、字段、ID、行或提交。
- **先分诊再点名。** 不允许一上来索取整批 diff，必须先判断哪里可疑，再要 4~8 个文件。
- **反误报。** 看着像问题但可能是「阶段性屏蔽 / 半成品提交 / 联调保护 / 灰度开关 /
  故意提前 return / 故意注释掉的事件」时，默认动作是**先索取能区分两种解释的上下文**，
  而不是直接报成问题。
- **九个维度都要留痕**（`config_id` 配置 ID、`config_value` 配置取值、
  `config_data` 配置数据本身、`value_sanity` 数值是否合理、`config_linkage` 单表连锁、
  `module_coupling` 模块耦合、`code_logic` 代码逻辑、`version_branch` 版本分支、
  `process` 流程），没命中也要写明理由，防止「只报容易报的」。
- **配置数据本身是否说得通，是单独一个维度。** 配表 diff 里最常见的问题不在 ID、也不在
  数值边界，而在**这一行、这一格自己是否成立**：描述/备注与同行取值互相打架（只改了一列
  文案、它描述的字段没跟着改）、新增或改动行漏填必填列、类型与日期格式和同表其它行不一致、
  枚举值不在允许集合里、全角半角或首尾空格（平台按文本原样比较，`'  x  '` 与 `'x'` 是
  两回事）、复制粘贴出来只改了一半的重复行、以及列之间的联动规则（「A 列为空则 B 列为空」
  这类约定）被打破。报告里对这类问题要指到**具体是哪一行、哪一列、与哪一列矛盾**。
- **数值是否合理，是单独一个维度。** 上面那条看的是「这一行自己说不说得通」，
  这条看的是**这个值放在这个系统或玩法里合不合理**：可以从三个方向问 ——
  ① **量级对不对**：同一张表里同类行（同品质、同等级、同稀有度）本来是什么数量级，
  改后是不是跳了一两个数量级，例如道具价值 `1000` 改成 `1000000`、奖励数量
  `10` 改成 `100000`；② **经济闭环有没有被打破**：买入价与卖出/回收价的关系反了
  （售价 `100` 的东西卖给商店能卖 `10000`）、合成或分解的产出大于投入 —— 这类配置
  会被玩家刷爆，是最高优先级之一；③ **单位与档位**：百分比与万分比、秒与毫秒、
  元与分，以及这个字段本来该在的取值区间（品质档位、等级段）。
  **这条维度的口径是「疑似即可报，但必须写明基准来自哪里」**：宁可多报一条待确认，
  也不让一个数量级写错的配置悄悄放过去。有基准的（同表同类行的分布、这张表的历史版本、
  知识包或字段描述里的量级规则）要**把基准本身写进证据**，例如「该列 1200 行，
  中位 800、最大 12000，本行改后 1000000」；确实拿不到基准的**也允许报**，但证据里
  必须显式写「缺基准：<为什么>」，而且**置信度只能给「高」，不能给「极高」** ——
  这样读的人一眼能分出哪条是「疑似」、哪条是「确认」。
  **基准是平台给的，不需要它自己拼凑**：读表格内容时，平台会在正文之前附一段
  **整表统计**（每个数值列的最小 / 中位 / P90 / 最大，每个文本列的取值分布），
  这段统计是**按整表算出来的，不受正文截断影响** —— 所以「这个值是不是大得离谱」
  有东西可比，而不是拿一个孤零零的数字猜。同一张表在本批次里有更早的提交时，
  它还会读那份做历史对照（比的是**分布**：中位数从 800 涨到 900 是正常调整，
  最大值从 12000 跳到 1000000 才是信号）。
- **模块耦合必须落成测试风险点。** 平台会专门分析这次改动**跨了哪几个模块、模块之间靠
  什么绑在一起**，并盯住最容易出事的一类：**本该成对改动的两边只改了一边**（配表 ↔ 它的
  生成物、客户端 ↔ 服务端、协议 ↔ 打包解包、字段 ↔ 读取方、公共件 ↔ 它的调用方）。
  只要认定存在耦合，报告里就必须说清「哪两端、靠什么耦合、这次改了哪一端、不同步会以什么
  现象暴露」，并把耦合点写进「测试建议」——**只说「注意联调」不算**。
  针对耦合的测试风险点至少要覆盖三条路径：两端都改了的、只改了一端的、
  以及老数据 / 老客户端的。
- **它读不到耦合的另一端时会怎么写？** 它只能读本批次改动过的文件。所以「另一端这次
  根本没改」（能从文件清单看出来）会写成结论；而「另一端不在这批变更里、我读不到」
  只能写成**待确认的耦合点** —— 这两种说法在报告里是分开的，看到「待确认」就说明需要
  人工去确认那一端是否同步改了。
- **报告是累积语义**：产出的是「这个版本截至目前的那一份」，不是「第 N 份」；
  已报过的不重复报，已修复的从清单里去掉，报告里不写「本轮新增 N 条」。

**关于人工处置（设计语义，界面入口待补）**：

- `待确认` / `已确认` 的结论，下一轮会作为「仍待处理」继续带着。
- `已忽略` 的结论**默认不再提**，但**它涉及的文件又被改动时，会重新出现**
  （证据过期了，需要重新确认）。这条是「忽略不会变成永远看不见」的保证。

## 11. 项目专属知识（这个项目自己的配置表说明与分析规程）

位置：项目管理页 →「AI 分析配置」卡片右边的**「项目专属知识」**。**仅项目管理员可修改**，
其他成员可以打开看。

它维护的是 `skills/projects/<项目代号>/` 这一包东西 —— 在这之前只能靠人往服务器上放文件，
界面上没有任何入口。

### 11.1 三类内容，作用完全不同

| 类型 | 位置 | 谁读它、什么时候读 |
|---|---|---|
| **知识包清单** | `KNOWLEDGE.md` | 它是**模型的目录**：AI 先看到它的一句话说明（`description`），而正文里用反引号列出的文档才会被按需读取 |
| **知识文档** | `references/*.md` | **按需读取**：AI 判断「属于哪个系统」「按什么规则编号」「这个改动算不算越界」时会来读 |
| **子 skill** | `<目录名>/SKILL.md` | 这个项目自己的分析规程：说明进提示词索引，正文按需读取 |

**这个区别值得记住**：往清单里写「配表规范很重要」不会有任何效果，
只有**在清单里用反引号写出文件名、并且那份文档真的存在**，AI 才会去读它。

### 11.2 界面会替你做的两件事（都不是可选项）

清单与 `references/` 之间是**双向强制**的：正文提到的文件必须存在，存在的文件必须被正文提到。
这条规则有一个直接后果 —— 「先建文档再改清单」和「先改清单再建文档」**两种顺序都不成立**
（总有一次保存会撞上校验）。所以：

- **新建知识文档时**，平台会同时在 `KNOWLEDGE.md` 末尾补一行
  `- \`文件名\` —— <你填的一句话说明>`。清单里已经有这一行时不动它（那是你自己的措辞）。
- **删除知识文档时**，平台会**同时摘掉那一行引用**。二次确认里会写明这一点 ——
  不摘的话知识包会变成不合法的，分析连清单里其他文档一起读不到。

**子 skill 的 frontmatter 由平台生成**（从「目录名 + 一句话说明」拼），不需要也不能手写。
编辑器里会实时显示将要写入的那段 frontmatter。这不是限制，是避免一类必然的错：
`frontmatter` 看着像 YAML 但不是（平台刻意不引入 PyYAML 依赖），说明里出现一个 `": "`
就会被判非法，而错误信息对策划完全不可读。

### 11.3 改完会发生什么

保存成功后，**此前的分析结论会被标记为「旧」**。原因：每份分析结果都记着当时的规则版本号
（它由平台规程 + 项目知识包的全部内容一起算出来），知识包一变，旧结论就不再是「当前规则下」
的结论。它们**不会消失**，仍然看得到，只是会被标注出来 —— 这点与「平台评审规程升级」是同一套机制。

### 11.4 数据属于部署实例，不进版本库

`.gitignore` 里 `skills/projects/*/` 是被忽略的（只放行随仓库分发的 `skills/projects/g119/` 示例）。
也就是说：**你在界面上建的知识包只存在于这台服务器上**，换一台部署就是空的。这是设计如此，
不是缺陷 —— 项目知识是运营数据，不该跟着代码走。

### 11.5 命名与限额

- 文件名 / 目录名只允许**小写字母、数字、连字符**（例如 `config-table-spec`），
  知识文档会自动补 `.md`。中文名、下划线、空格、大写都不行 —— 这个名字会变成磁盘路径。
- 单份文件 ≤ 64 KB，整个知识包 ≤ 512 KB。超长会被拒绝并提示原因。
  上限不是防滥用：文档会进提示词，超长必被压缩，用户会拿到「我明明写了、模型却说没看到」。
- 子 skill 的 `SKILL.md` ≤ 500 行；知识文档超过 300 行要带目录（这两条来自平台契约，保存时会校验）。

### 11.6 别和平台内置规程搞混

- **平台内置的评审规程**：`skills/version-diff-review/SKILL.md`，随平台升级、**所有项目共用**。
  它定义了检查维度、输出格式、报告结构。**改它等于改 AI 的行为**，不通过这个面板维护
  （面板上也会写明这一点）。
- **项目专属知识**：只有这个项目能看到，就是这一页。

两者冲突时**以平台内置的为准**。

### 11.7 已知的待办

**子 skill 自己的 `references/` 目录还没有界面入口** —— 目前只能编辑 `<子 skill>/SKILL.md`。
磁盘上已经存在的子 skill references 仍然会被校验与加载，只是建不了新的。

## 12. 消耗与费用（token / 缓存命中）

分析跑了很多轮、每轮都要把整份提示词（系统提示词 + 变更清单 + 历史结论 + 上一轮取回的
上下文）再发一遍，**花了多少**这件事在这里看。

**入口**：顶部导航 →「AI 消耗」。页面上先给你一行合计（**你所负责的那些项目**加起来的），
再按项目、周版本（分组键）与单次运行逐层下钻；AI 分析抽屉的底部也有一行
「本次消耗 … tokens · 命中缓存 …」，点旁边的「明细」看这一轮的逐次明细。

**谁能看到什么**：这一页按你的项目权限过滤，看不到别人的项目。

* 「合计」那一行是**你能看到的项目**的合计 —— 平台管理员因为能看到所有项目，它才等于
  全平台合计；普通成员看到的是自己那几个项目的合计。
* **全平台合计与「平台总预算」只有平台管理员能看**：它是一个运营数字，把所有人的花费
  加起来就能反推出别的项目烧了多少钱。所以普通成员看到的是「仅平台管理员可见」这句
  说明，而**不是 0**——0 会被读成「一点都没用」，那是另一件事。
* 拦不拦不受这个开关影响：平台总预算超了照样挡住所有人的下一次分析，普通成员在自己的
  项目那一行看得到「平台已超」，分析被拦时那句理由也会说明是平台档（只是不带额度数字）。

### 各列什么意思

| 指标 | 口径 |
|---|---|
| 输入 token | 每次模型调用的输入合计，**逐轮累加**（每轮都重发上一轮的上下文，所以后几轮更贵） |
| 其中命中缓存 | **上游接口报的** prompt cache 命中 token。与「工具结果在本次分析里的内存缓存」是两件事，界面上分开显示 |
| 输出 token | 模型生成的 token |
| 缓存命中率 | 命中缓存的输入 ÷ 输入合计。**只有分子分母都上报了才给这个数** |
| 费用估算 | 按你配置的单价表算出来的金额，见下 |
| 上下文索取 / 取回字符 | 模型索要了几次文件、实际取回多少字符（被预算拒绝、被截断的也会各自计数） |

### 单次运行的「明细」里有什么

点到某一次运行的明细（「逐次运行」表或分析抽屉底部的那个按钮），弹层里有两块是
**回答「这次为什么没看到某个文件」**用的：

* **逐轮表的「明细」列**：点开一轮，能看见它**点名要了什么**（原样的索取，含行窗口）、
  **实际拿到的那一份是内容还是一句「取不到」**（取不到会把工具给的原因照抄出来，标红；
  「工具明确回了没有内容」是另一种，不算失败）、**哪几条被丢掉及原因**、**模型原样返回
  的文字**。计数是分不出这些的：一次失败的索取在「条数 + 字符数」上与真的读了一份 diff
  完全一样。
* **「取数（按工具类型）」表**：这次分析里每类工具索取/执行/缓存命中/**失败**/超预算/
  截断各多少次、取回与交给模型各多少字符。「失败」列就是那些「工具跑完了但没拿到内容」
  的次数（例如没绑 Agent、Agent 离线、同步还没跑完）。

**上线之前的老运行没有这两块**，弹层里会写「这一轮的明细未采集」—— 那不是「它什么
都没要」，只是当时没记。

### 12.1 子代理模式：为什么它贵「分片数 + 1」倍

周版本很大时（几百个文件），一个 agent 在 8 轮 / 20 次索取里把这些全看一遍是不可能的。
打开「子代理模式」之后（**默认关**，项目管理页 →「AI 分析配置」），平台会：

1. 把九个检查维度**按固定方式分组**（3 个分片时是「配置 ID / 取值 / 单表连锁」
   「配置数据 / 数值合理性」「模块耦合 / 代码逻辑 / 版本分支 / 流程」）；
2. 让每个分片代理**各自通读整批变更**、只对自己那几组维度负责（**读取权限不按维度切**：
   跨模块耦合本来就只能越片去读才发现）；
3. 再由一个主代理把所有分片的候选结论审一遍、合成最终报告。

**代价是模型调用次数变成「分片数 + 1」倍**（分片各自的轮次 + 一次汇总）。省下来的部分
靠的是缓存：所有分片的请求**前两条消息逐字节相同**（系统提示词 + 整份变更清单），
所以第一个分片把这段前缀写进缓存、其余分片与汇总那一次直接命中，按便宜得多的缓存价
计费。「变更清单」正是整份提示词里最大的一段（顶到上限时约 8.7 万字符）。

**取数也是这一家子共用的**：两个分片都要看同一个文件时，正文只取一次、**两边都拿到全文**
（不是「另一个分片已经看过了」那种转述）—— 配表的结构化差异是秒级操作，省下的是整次分析
的等待。反过来，某个分片自己重复要同一份内容时不会再给一遍正文，与单代理的行为一致。

另外两条口径：

* **「上下文索取上限」按分片数分摊**（n 个分片 + 1 次汇总各拿一份），所以**整次分析的
  总索取次数不变** —— 分片换来的是「每个维度看得更深」，不是「能多要几次」；
  调大那一项会同时抬高每个分片的那一份。
* **一次分片分析在面板上仍然只有一行**（运行条数不变）：它的 token 是**一家子的合计**，
  逐片的花费在那一行的明细里（「分片代理」那张表），逐轮的「分片」列能看出哪一轮是
  谁跑的。

**哪个分片没跑成，报告里一定写。** 上游出错、轮次用尽、预算不足提前收工 —— 这三种都会
在报告末尾的「信息缺口（平台补充）」里点名，面板上那一行的状态也是「降级」而不是
「完成」。**那一块维度这一轮没有任何人看过**，不能当成「没问题」。

### 「未上报」不等于 0

接口不保证回缓存字段（不同厂商的字段名也不一样）。**没回的时候显示「未上报」、
命中率一列留空** —— 那表示未知，不是「一次都没命中」。同理，本功能上线之前的分析
没有采集过用量，明细里显示「本次用量未采集」，也不会显示 0。

### 费用是估算，且必须自己配单价

接口只回 token 数、**不回金额**，所以金额是按你填的单价表算的。

**配置入口在「AI 消耗」页面上的「模型单价表」卡片**（不在项目配置里）。点「按行编辑」
逐条填模型名与三档单价，或者展开「高级模式」直接粘贴 JSON；两种模式编辑的是同一份内容。
保存时**改了价格就必须同时改 `version`**，否则保存会被拒绝 —— 版本号是历史费用的唯一
追溯依据。

```json
{
  "version": "2026-09-18",
  "currency": "CNY",
  "models": {
    "model-name":      {"input": 2.0, "output": 8.0, "cache_read": 0.2},
    "gateway-model-*": {"input": 1.0, "output": 2.0}
  }
}
```

- 单位是**每 100 万 token**；`cache_read`（命中缓存的单价）不填时，命中那部分按未命中价
  计入，页面上会注明「费用偏保守」。
- 模型名按「精确 → 前缀（`xxx-*`）」匹配，**不做包含匹配**（那会让 `gpt-4` 命中 `gpt-4o`，
  价格差一个量级却毫无提示）。
- **改单价必须同时改 `version`**。每次运行都会把当时的版本号记下来；面板上的金额一律按
  **当前**价格表重算，并在明细里注明「这条记录落库时的单价表版本是 X」。
- 没配（或算不出，例如模型不在表里）时**不显示金额**，并说明原因 —— 不会回落到 0。

### 预算：超了就暂停分析

「AI 分析配置」里可以给项目设**周期内 token 上限**与**周期内费用上限**（周期默认本月）。
**留空 = 不限制**，两项都留空就是现在这样、不做任何限制。

- 用超之后 AI 分析会被**暂停**：抽屉里的「重新分析」按钮变灰并写明已用多少、上限多少，
  定时分析也会跳过（日志里记成 skipped，不会静默）。调高上限或等到下个周期即可恢复。
- 判定**只认确定的数**：token 那一档用的是「已上报部分的合计」，它超了才算超；
  费用那一档只要有**任何一次**运行算不出金额（没配价格表、模型名对不上、上游没报
  token），就**不按费用拦截** —— 宁可放过一次，也不会因为算不出钱就把功能锁死。
- 面板上「各项目消耗」的预算列与抽屉里的按钮用的是**同一份判定**，不会出现
  「面板说超预算、按钮却还能点」。
- 除项目预算外，平台管理员还能在「AI 消耗」页面设**平台总预算**（同样按周期）。
  两档是**叠加**的：任意一档超了都会挡住下一次分析；都没配就等于不限制。
  **平台总预算的额度与已用量只有平台管理员能看**（普通成员看到「仅平台管理员可见」）；
  平台档超了的时候，普通成员拿到的拦截理由里会说明是平台档，但不带额度数字。

### 统计口径：设置起点（可逆）与全量重置（不可逆）

页面上的数字是**全部历史**的累计。同一个库上反复试跑（调提示词、验证部署、压测）之后，
那一屏的总量就永远带着这些噪音，而它恰恰是给人看「这个版本花了多少」的地方。
所以「AI 消耗」页面上多了一张「**统计口径**」卡片，两个动作**性质完全不同**：

| | 设置统计起点 | 全量重置 |
|---|---|---|
| 删数据吗 | **不删**，一条记录都不动 | **真删**：运行记录、AI 报告正文、异常清单、分轮轨迹 |
| 能撤销吗 | 随时点「恢复为全部历史」即可 | **不能**，没有回收站 |
| 影响预算吗 | **不影响**：起点之前的运行照旧计入预算的「已用」与拦截判定 | 会：记录没了，预算的「已用」自然归零 |
| 谁能操作 | 平台管理员（状态行对所有人可见） | 平台管理员 |

**「设置统计起点」**填一个北京时间，之后**只在消耗面板这一页**统计那一刻
（含）之后创建的运行：合计、各项目消耗、逐次明细一起变，并且会写明「当前这一屏还有 N 次
运行在起点之前，未计入」。它是**平台级口径**（对所有人、所有筛选都生效），与筛选区那个
「时间范围」不是一回事 —— 后者只是你自己临时看一眼。填**未来**的时间会被拒绝：那会把
之后的分析也一起排除掉，页面永远是空的，而你还以为自己在「重置」。

**「全量重置」**是这个页面上唯一的破坏性动作，所以它单独一个红色按钮、单独一个弹层、
并且要输入确认词才让提交。弹层里如实列出后果，包括两条容易被忽略的：

* **预算的「已用」也会归零** —— 它不是被「重置」了，是记录没了、闸门那边没有可算的数；
* 下一次分析会退化成**全量分析**（没有「上一次分析」可比）：「上次报过的问题」这个
  基线一并消失。

有分析**正在跑**（进行中或排队中）时会被拒绝：那条运行回写结果时会踩到已经被删掉的行，
你看到的会是「分析失败」而不是「你刚重置过」。等它跑完再重置即可；真的卡死的那条会被
调度器在超时后重置成失败，届时就可以重置了。

## 13. 上下文与模型的窗口（为什么分析不会「撑爆」而中断）

一次分析要把「系统提示词 + 变更清单 + 历史结论 + 已经取回的上下文」整体发给模型，
而模型的上下文窗口是有限的。这里说明平台怎么保证**它不会在跑到一半时因为太长而作废**。

### 提示词预算是多少

配置里的「提示词字符预算」（默认 360,000 字）是上限，但**真正生效的是它与窗口水位的较小值**：

| 模型窗口 | 怎么知道 | 生效预算 |
|---|---|---|
| 端点声明了（`/v1/models`） | 直接读 | 窗口 × 60% |
| 端点没声明 | 按 **1M token** 处理，并在结果里注明「按默认值」 | 600,000 字 |

字符按 1:1 当 token 算（中文约 1:1、英文约 4:1），所以这个换算是**偏保守**的：
按它压出来的提示词一定装得下，代价是可能少塞了一点本来放得下的内容。

> 默认的 360,000 字在两种情况下都不触发水位，所以**没调过预算的项目行为不变**。

### 超了会怎样：压掉历史，而不是让你少看

提示词超出预算时，平台会**压掉最早的几轮历史**，只留一段摘要（第几轮、索取了什么、
需要就重新索取），并保留最近一轮的原文：

- **系统提示词与第一轮不压** —— 第一轮里是变更清单与历史结论基线，就是这次分析要回答的
  问题本身；它们同时也是跨运行复用缓存的前缀。
- 被压掉的轮次**会告诉模型**（它会看到那段摘要），也**会写进这一轮的记录**里。
- 结果里带一份「压缩记录」（压过几次、压掉几轮、省下多少字），抽屉里会显示一行说明。

另外，**变更清单只在第一轮发一次**。它在这次对话的上下文里一直在（模型看得到），
后续轮次只给一句指针说明它在哪、仍然有效 —— 每轮重发一遍既挤窗口，又按未命中价计费。

### 万一上游还是拒绝（收尾请求）

估算终究是估算。如果上游以「上下文超长」拒绝了请求，平台**不会就此放弃**：
它换成一段**必然装得下**的「收尾」提示词 —— 只带变更清单的开头（够认出改的是哪一片，
并注明被截断）与「你已经取到过哪些内容」的目录 —— 让模型基于手上的证据直接出结论。

这种情况下：

- 结论**仍然算数**，但状态是**降级**：结果里写明「提示词超出模型上下文窗口，已压掉历史
  后收尾出结论」，抽屉里会有一行 ⚠️ 说明。
- 报告里的「信息缺口」要**认真看** —— 它是在被裁剪过的上下文里得出的。
- 收尾请求也失败时，这次分析才会记成失败，并给出可照着做的建议（缩小范围 / 换窗口更大的
  模型）。**失败的记录不会被当成已有结论回放**，重试就是重新跑。

### 上一句「降级」是什么意思

不在超窗场景里的降级也一样会显示在抽屉里，都是同一类事实：**这次不是正常跑完的**。

| 结果里的降级 | 意味着什么 |
|---|---|
| 轮次用尽 | 模型没在轮次内收口，结论基于它当时手上的证据 |
| 索取额度用尽 | 还有文件没看 |
| 按 markdown 降级 | 模型没按协议吐 JSON，平台把它的正文原样留了下来 |
| 协议纠错次数用尽 | 连续多轮都解析不出 JSON |
| 上下文超长后收尾 | 上游拒绝了完整提示词，收缩后重新问了一次 |
| 子代理有分片没跑成 | 开了子代理模式时，某个分片失败/被跳过，或者它报出的结论没有进入最终报告 —— **报告末尾的「信息缺口（平台补充）」里逐条列着**，那几块不能当成「没问题」 |

**没有降级 ≠ 没有问题**：它只表示流程跑完了，不表示平台替你确认过风险。
