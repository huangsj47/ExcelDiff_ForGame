# AI 变更风险分析使用说明

本文面向**测试（QA）**同学：说明平台里的 AI 变更风险分析**能帮你做什么**、
**报告怎么读**，以及它**看不到什么**。

- 想直接上手：看 [第 2 节](#2-在哪用三个入口) 与 [第 3 节](#3-报告怎么读)。
- 报告结论对不上你的判断时：看 [第 7 节 它看不到什么](#7-它看不到什么重要) 与
  [第 8 节 常见疑问](#8-常见疑问faq)；管理员向的配置项在 [第 10 节](#10-配置项一览管理员)。

---

## 1. 这是什么

给一个版本（或一次提交）的变更，自动产出一份**面向回归的风险说明**：这次改了什么、
影响哪些系统、**建议测什么**、**回归哪些老功能**、上线与回滚要盯什么。

一句话定位：**帮你决定「这个版本重点测哪几块」，并给出依据。**

它不是「自动验收」，也不替代你看 diff。它对**全部**改动做确定性预检（关键路径命中、
表与生成物的配对，不花模型的钱），再对**有嫌疑的那几十个**逐个取证 ——
一个周版本可能有几百个改动文件（线上 G119 的一次是 996 个），你不可能逐个翻完。

> ⚠️ **它不会「把每个文件都读一遍」。** 一次周版本分析里，真正取到过证据的文件通常只有
> 几十个（实测：996 个改动文件里 60 个）。报告与导出文档会**如实写出覆盖率与缺口**
> （见 [第 3 节](#报告里的覆盖与缺口怎么读)）。把「清单里有 996 个名字」当成
> 「996 个都看过了」，是读这份报告最容易犯的错。

## 2. 在哪用（三个入口）

| 入口 | 位置 | 覆盖范围 | 会自动跑吗 |
|---|---|---|---|
| 周版本 Diff 页 | `/weekly-version-config/<id>/diff` 右上角 **「AI分析」** 按钮 | 整个周版本（可缩小范围，见第 5 节） | **会**，默认每 2 小时检查一次，有变更才跑 |
| 单提交 Diff 页 | 提交 diff 页右上角 **「AI分析」** 按钮 | 这一次提交 | 不会，只能手动 |
| 项目合并视图 | 版本卡片上的 **「版本AI分析：未分析」** 标签（点它打开抽屉） | 该周版本 | 同周版本 |

抽屉（右侧滑出）里有：

- **两个标签**：「思考过程」与「完整结论」（见第 3 节末尾）。
- **「刷新结果」**：只读已保存的结果，不重跑。
- **「增量分析」**（绿色，默认）：只分析**上次结论之后变化的那部分**。它是默认动作，
  点下去**不会弹确认框** —— 除非真有事要说（见下一条）。
- **「全量重新分析」**（红色）：忽略增量基线，把**整个窗口**重新做一遍完整评审。
  它比增量贵、也慢，所以点下去**先摆出预计代价**：预计文件数、预计 token 区间、
  最近一次实际耗时、这次能不能命中可复用基线（是历史实测区间，不是精确值）。
  **没有配置模型单价时只给 token 与时间，不给金额** —— 编一个金额比不显示更坏。
- **「导出 md」**：把**这一次**的结论存成一份 `.md` 文件（见第 3 节末尾）。
  没有可导出的结论时这个按钮不出现（不会给你一个点了没反应的按钮）。
- **「历次结论」**：这个目标跑过的**每一次**都列出来，可以翻看其中任意一次
  （见第 3 节末尾）。**正在分析时也能点** —— 你可以在等的时候先看上一版结论。

> **打开抽屉不会自动开跑分析。** 想跑就按「增量分析」或「全量重新分析」。
> 自动分析只对**周版本**存在，单提交只能手动。

**单提交 Diff 页只有一个「重新分析」**：一份提交没有增量基线（每次都只能是对这一份
diff 的完整评审），所以那里不会给你一个按下去会说「没有这个概念」的按钮。
它的颜色与周版本的「全量重新分析」一致（同一种语义 → 同一种颜色）。

### 规则/提示词/模型变了之后，增量会先问你一句

增量是拿**上次那份结论**做差的。如果那份结论是**旧版评审规程**（提示词 / skill /
规则门槛 / 模型换过）产出的，新结论与它**不可比** —— 这时点「增量分析」会弹一次提示，
并推荐「按新规则全量重新分析」；你也可以选「仍然只做增量」，那次分析的报告顶部会写明
**这次增量与基线不可比**。

> **两点如实说明：**
> 1. 提示框里只写「这一次的评审规程与上次那份结论不一致」，**列不出到底哪一项变了**
>    （平台手里只有「一致 / 不一致」这一个结论），不要指望它给逐字段的差异明细。
> 2. 这个提示**只在真的不一致时才弹**：规程没变、基线还在时，点增量一路不弹窗。
> 3. 「没有可复用基线」时，平台会把增量**升级为全量**，并且**在开跑之前**先把预计代价
>    摆出来问你；其余升级原因（文件数多 / 占比高 / 命中关键路径）发生在执行过程中，
>    做不到事前问 —— 它们会在页面与报告里**事后说清原因**（见第 3 节）。

**自动分析默认是关的。** 想让它自己跑，去项目管理页 →「AI 分析配置」→ 打开「周版本自动分析」，
再设一个间隔（默认 2 小时）。关掉之后，连**已经排上队**的那次也会被跳过（不会在你重启平台后偷偷跑一次）。
每次自动分析都是**增量**（拿上次结论做差）；要全量就手动按「全量重新分析」。

## 3. 报告怎么读

报告是 Markdown，固定 **7 个一级标题**，顺序固定：

| 章节 | 你可以怎么用 |
|---|---|
| `# 变更理解` | 开场，**简明扼要**：一句话搞清「这次到底改了什么」，用来对齐你和策划/程序的理解 |
| `# 变更内容摘要` | 开场，**简明扼要**：按策划/玩家能感知到的变化归类汇总，不逐条罗列改动 |
| `# 影响面分析` | **重点**：这次改动会牵动哪些系统、哪些老功能、哪些入口 |
| `# 风险评估` | **重点，结论在这里**：风险点、严重度、判断依据。**按系统模块归组**（形如 `【好友系统】`），组内按严重度排；列的是**当前仍然成立的全部问题**——本次新报的标「（本次新增）」，上次报过、这次仍成立的标「（上次遗留，仍成立）」；低风险不列 |
| `# 测试建议` | **重点，QA 直接用**：建议测什么、怎么复现、要覆盖哪些组合 |
| `# 回归建议` | **重点，QA 直接用**：哪些老功能需要复测（改了 A 影响 B 的那类） |
| `# 上线与回滚关注点` | **重点**：上线要盯什么、出问题怎么回退 |

头两节是**给你对齐理解的开场**，篇幅有意压短；后五节才是重点，信息密度都在那里。

> 📌 报告正文**不贴代码片段**，也**不会逐条点名「某文件某行」** —— 它写的是
> 「哪块逻辑有问题、QA 该去验什么」，用的是模块、表、字段、入口这类你能直接对上功能的
> 说法。真要定位到文件和行，看报告附的异常清单（那是给人工跟进用的结构化条目）。

抽屉顶部有一行元信息（meta），形如：

```
最近分析：2026-09-17 21:24 | 风险等级 高风险 | 范围 仅配表仓库
```

**风险等级**共 5 档：低风险 / 中低风险 / 中风险 / 中高风险 / 高风险。

> ⚠️ 如果 meta 里出现「本次未取得完整结论（原因），该等级仅按变更规模估算，**不是**模型评估结果」，
> 说明这次**没拿到完整报告**，那个等级只是按改动文件数量估出来的 ——
> 这种情况**不要**把它当结论用。

报告正文里出现的「已截断」「省略了多少字」是正常的：平台对每次取数都有字数上限，
超出会截断并**如实记账**（宁可告诉你"这块没看全"，也不会假装看全了）。

### 报告里的「覆盖与缺口」怎么读

元信息表里有几个**覆盖**行，表下还有一段**覆盖与缺口**。它们回答的是同一个问题：
**这份结论建立在「看了多少东西」之上**。

| 口径 | 分子 / 分母 | 回答的问题 |
|---|---|---|
| 本次覆盖 | 本版本改动过的文件 → 本次输入 → 真的取到证据的 | 三个数连成一条**收窄的链**：这个版本改过的文件里，多少进了本次输入、其中多少真的被看过（2026-09-25 收口：原来这几件事各占一行，读者与模型都要自己拼） |
| 结论（本轮 / 继承） | 本轮新增 + 基线继承 = 在挂 | 结论清单里有几条是这次新报的、几条是上一轮继承下来的（**正文的「风险评估」应当覆盖全部在挂条目** —— 明显少于这个数就是正文没写全） |

2026-09-25 又收了一次（用户：「只留一行计数，不重要的甚至可以不说明」）：原来的
`覆盖（分层）` 与 `额外输入` 两行撤掉了，它们的信息挪到了更有用的地方 —— 分层的两个数
跟着「没有取到证据」那条缺口走（在那里才回答得了「为什么没取到」），补偿项 / 依赖核查项
只在**没取到证据**时出现（那才有下一步动作）。

**「本次覆盖」那一条里还有两小截**：

- **按文件去重 N** —— 宽松口径的另一个数（见下），两个数一样时不重复写；
- **本窗口 N 条提交、其中 M 条进了本次输入** —— **产品里只有这一处说得出这个窗口的
  提交数**。报告正文里若另给了一个提交数，以这里为准（实测出现过正文写 2 条、账上是 4 条）。
  只改了「本次没装进输入」的那些文件的提交只进第一个数，所以第二个数通常更小。
  **平台记不出这两个数时写「未记录」，不写 0** —— 0 是一句断言（「这个窗口一条提交都
  没有」），而这里只是没这个数。

（单提交分析时没有「版本」这个概念，第一条写的是「这条提交改了 N 个文件 → 取证 K」。）

**「取到证据」有两种去重口径，两个数不一样，报告里两个都写：**

- **保守口径（报告里的结论按这一份读）**：按「(本批次最新提交, 文件)」去重 —— 只有
  「取到的证据正好是本批次那条最新提交上的版本」才算。它翻的是某个文件**更早**那条提交
  的版本时，这一条不算（要看的是这个版本当时的改动）。
- **宽松口径**：按「文件」去重 —— 取过这个文件的任何一版就算。它一定 ≥ 保守口径；
  两个数**一样**时，说明它这次没有去翻更早的提交。

> 同一个数**只有一个**：报告里凡是提到覆盖，用的都是保守口径。「同一份数据算出两个
> 覆盖率」正是这两个口径必须同时写明的原因。

除覆盖之外，那一段还会逐条列出**缺口**（有哪几条就写哪几条）—— 每一类都是
「类别：条数 —— 下一步做什么」，**逐条的未读清单与每条失败原因在面板「思考过程」里**：

- **变更清单长到列不下**：提示词里只列出了一部分文件名 —— 名字没列出来 ≠ 读不到，
  这些文件仍在可读范围内，可以点名索取；
- **没有取到证据**：本次输入里还有多少个文件这次没有任何 diff 或正文进来
  （**这不是「这些文件没问题」，是「这次没有看」**）；
- **补偿项 / 依赖核查项没有取到证据**：这两类文件进来就是为了「补上一轮没看到的那部分」
  与「跟着看改了它就要看的那一跳」，没取到等于这件事没做成；
- **分片这一轮没跑起来**：那条分片被跳过了（原因写在它那一行上，多半是额度或预算）——
  **不是「模型漏看」**，它们已经进下一轮的补偿清单，补跑一次就会轮到；
- **取数失败**：没绑 Agent、Agent 离线、同步还没跑完 —— 报告正文里应写成信息缺口；
- **有几次索取因为超出本次的上下文额度没有执行**：还有想看的文件没看成（提高额度见第 10 节）；
- **有 N 条取数在交给模型之前被截断**：拿到之后被砍掉了尾巴；
- **本次只分析了「某个范围」**：其它仓库的改动不在这次输入里。

**覆盖率告诉你有多少没看，缺口告诉你「为什么没看」** —— 这两件事下一步该做什么完全
不同（一个要缩小分析范围，一个要去查 Agent 或调额度）。

> **「分析范围：全量」是分析口径，不等于「整个版本都看过了」。**
> `全量 / 增量` 说的是这一轮**按什么口径出结论**。而判定回「全量」的那几种情形（本批
> 文件多、命中关键路径）里，输入**仍然是上次分析之后的那一部分** —— 窗口里另一部分它
> 这次一个都没重新看。所以只要这一轮有没看全的地方，报告里那一格就会带上限定语
> （「**分析口径**，不等于『整个版本都看过了』」），紧跟其后的就是覆盖那几行。

### 你点的是增量、平台跑的是全量时，页面会告诉你为什么

平台会因为几种原因把一次增量**升级为全量**（没有可复用基线 / 变化文件数超过阈值 /
变化占比超过阈值 / 变更命中关键路径）。这是平台替你做的决定，所以页面**事后一定说明
原因**（那句话在抽屉的状态行上，不是让你去翻日志）。

其中**只有「没有可复用基线」这一种能在开跑之前看见**（这一轮还没有任何可用结论）：
那时点增量会先把预计代价摆出来、问过你才发起。其余几种的升级判断发生在后台执行过程里、
快照冻结之后，做不到事前问 —— 这一轮**只做事后说明**，不做一个假的事前确认框。

### 抽屉里的两个标签

| 标签 | 里面是什么 | 什么时候默认显示它 |
|---|---|---|
| **完整结论** | 就是上面那份 7 章报告 | 没在跑的时候（打开抽屉、跑完自动切回来） |
| **思考过程** | 这次运行的**逐轮**记录：每一轮它点名要了什么、哪一条**取不到**（附原因）、哪些请求**没执行**、这一轮的结局与花销 | 正在跑的时候（那时唯一有内容的就是它） |

> ⚠️ **「思考过程」是按轮更新的，不是逐字输出。** 模型的调用是非流式的：一次请求把整份
> 提示词吃进去、跑完才拿到回复，所以面板上**每跑完一轮才会多一条**，两条之间可能隔几十秒
> 不动 —— 那不表示它卡住了。这句话也写在面板顶上，因为它最容易让人误会。

几条口径：

- **不会把你从正在读的地方拽走。** 跑完时会自动切回「完整结论」；但如果你在这次运行里
  自己点过标签，就留在原处，只在「完整结论」上打一个未读点。
- **跑完之后「思考过程」仍然在**，显示的是**落库的逐轮明细**（比实时那份更全：实时那份
  对长回复做了截断，因为它每 3 秒要随进度整份重发一次）。这次功能上线之前的分析没有记
  逐轮明细，那时这里会说明「没有留下逐轮记录」，而不是画一张空表。
- **重新打开抽屉、刷新页面、或这条运行跑在别的进程时，进度会从逐轮事件账本补一份**：
  已跑完的轮次与用量都还在（每跑完一轮落一条，不随进程重启丢掉）；被中断的那一次会
  写明「没有跑完，已完成的轮次与用量已按账本补记，平台没有重跑任何一次模型调用」。
- **点开「思考过程」时才去读明细**（一次请求），没打开过这个标签的人不会为它多付一次。
- 「取不到」（例如项目没绑 Agent，读不到文件正文，带原因）与「确实没有内容」（工具明确
  回了「没有」）**分开写、颜色也不同** —— 合并这两者等于把「没有证据」说成「这里没问题」。
- 卡片上**不贴模型返回的原文**（结论那一轮是一段 JSON 信封），只说明「这是谁的结论、
  去哪儿看」。**这句话随状态变**：主分析者那几轮给的才是整份报告，`S1`/`S2` 这些分片
  给的只是**这个分片**那份（会并入最终报告）；运行还没结束时，它会写明「完整结论」里
  **还没有内容、要等它跑完**，不会让你以为已经可以点过去。

### 把这一次的结论导出成 md

抽屉 footer 的 **「导出 md」**（三个入口都有）会把**屏幕上这一次**的结论存成一份 markdown
文件：交给策划/QA，或者直接贴进工单。文件三段，用 `---` 隔开：

1. **元信息表**：项目、目标（提交号 + 提交说明，或周版本名 + 版本时间窗）、分析时间
   （北京时间）、风险等级**与定级依据**、分析范围（有没看全的地方时会带上限定语，
   见第 3 节）、**覆盖**（一条收窄链：版本 → 输入 → 取证；另有两种去重口径里的另一个数）、触发方式、
   是否降级、分析模型、运行号；表下紧跟一段**覆盖与缺口**（清单截断 / 取数失败 /
   超出额度被拒 / 被截断）。
2. **报告原文**：就是「完整结论」里那一份，**逐字**、不改写不重排 —— 平台加的元信息与
   附录都在正文之外。
3. **异常清单（平台按门槛过滤后）**：一张表（严重度 / 置信度 / 维度 / 处置 / 标题 / 文件 /
   影响），下面是逐条的**证据**与**建议**。

几条口径：

- **附录不是「发现的所有问题」**：只有达到门槛（严重度 / 置信度 / 条数，见第 4 节）的条目
  会进这张表，没达到门槛的只写在报告正文里。附录开头就是这么写的。
- **被人工忽略过的条目不进这张表**，但文件里会写明「另有 N 条此前已被人工标记忽略」——
  免得「报告里提过、附录里没有」看起来像平台漏了。
- **附录里有「处置」这一列**：它写的是**导出那一刻**平台上的人工处置状态（待确认 / 已确认），
  不是模型说的话 —— 模型压根不知道人处理到哪一步了。所以**同一份报告隔天再导，这一列可能
  不一样**，那是预期（报告正文逐字不变，变的是处置进度）。列里的 `-` 表示平台上没有这一条
  的记录（不是「还没人处理过」—— 那是两回事，平台宁可不写，也不替你断言）。
- **一次运行一份文件**：导的是**当前显示的这一次**结论。文件名形如
  `AI分析报告-<项目>-<目标>-20260912.md`（日期是北京时间）。导出**只读**：不重跑分析、
  不产生任何消耗。

---

### 翻看历次结论

抽屉 footer 的 **「历次结论」** 会列出一个目标跑过的每一次（新的在最上面）：

| 列 | 是什么 |
|---|---|
| 时间 | 那一次分析的时间（北京时间） |
| 状态 | 已有结论 / 分析失败 |
| 风险 | 那一次定出来的等级（失败的那次没有等级，显示 `-`） |
| 这一次说了什么 | 报告的第一句；失败的是失败原因；降级的会把「降级（原因）」写在最前面 |

几条口径：

- **点「看这一份」就能读那一次的报告**，报告上方会写明「这是 \<时间\> 的结论（历史）」；
  如果那一份正是抽屉里显示的那次，写的是「这是当前显示的结论」。
- **在跑动中也能点开** —— 这正是它存在的理由：点「重新分析」之后，屏幕上那句
  「AI 分析进行中...」会把旧报告换掉，旧结论就要从这里翻。
- **失败的那次也列出来**（那是「为什么失败」的答案），但它没有报告正文、也没有导出按钮。
- **只列**在这个窗口内的（默认 90 天，与平台保留策略同一天数，弹层顶部会写明），而且只列
  **有结论的**和**失败的** —— 正在跑的那次不进这个列表（它由抽屉自己说）。
- 弹层里那个「导出这一份 md」导的是**你正在看的那一份**，与抽屉 footer 上那个（导当前这次）
  是两件事。翻看历史是**只读**的：不重跑分析、不产生任何消耗。

## 4. 结论的「门槛」与异常清单

平台会把报告里够格的结论抽成结构化条目（严重度 / 置信度 / 证据 / 涉及文件），并按门槛过滤：

- 默认门槛：**严重度 ≥ 高** 且 **置信度 ≥ 高**。
- 低于门槛的结论**只写进报告正文**，不进异常清单（这是配置页上的原话）。
- 单次最多保留 **20 条**（平台内置上限，不可配），超出按严重度优先，并写明丢了多少条。
- 置信度只有「高 / 极高」两档 —— 模型被要求**没把握就别报**。
  所以「报告里没提」**不等于**「这里没问题」，只等于「它没有足够证据认定这是问题」。

> **两点如实说明（免得你找按钮找不到）：**
>
> 1. 上面那份 Markdown 报告是**叙事**；同一批结论还有一份**可操作形态** ——
>    「历次结论」弹层里、报告正文**下方**的结构化结论清单，逐条带严重度 / 置信度 / 维度。
> 2. 「待确认 / 已确认 / 已忽略」这套人工处置就在那份清单上做（逐条**确认 / 忽略 / 撤销**），
>    不需要找平台维护者。它的设计语义见 [第 9 节](#9-原理简述)，
>    其中「已忽略」不会变成「永远看不见」。

## 5. 分析范围（只影响「下一次」分析）

周版本抽屉里有一个「分析范围」下拉（当这个版本关联了多个仓库时出现）：

- `全部仓库（N 个）` / `只看配表仓库` / `只看代码仓库` / `只看「某个仓库」`

三条要点：

1. 这个下拉**只影响下次分析**；当前显示的结果覆盖哪个范围，看 meta 行上的范围文字。
2. 报告里会**写明本次范围**，并且被明确要求**不要把结论说成覆盖了整个版本**
   （否则「只看了配表」会被读成「整个版本没问题」）。
3. 选了范围但里面没有改动文件时，会直接提示
   「选定的分析范围里没有改动过的文件，换一个范围再试。」——不会跑一次空分析。

## 6. 它能「看到」什么

它拿到手的起点只有一份**变更清单**（提交信息 + 改了哪些文件），**里面没有 diff 正文**；
**要看哪一份，得它自己点名索取**。模型不能直接读你的仓库，只能通过**只读工具**按需
索取（**只读**：不会改任何仓库、不会触发 clone）：

| 工具 | 作用 | 单次上限 |
|---|---|---|
| `commit_detail` | 某个提交改了哪些文件（读平台数据库，不碰 Git） | 6,000~20,000 字 |
| `file_diff` | 某个文件在某个提交上的 diff（Excel 走结构化差异） | 11,000~32,000 字 |
| `file_content` | 某个文件在某个提交上的内容（代码文件**默认只给改动附近的一段**，可点名要哪一段；配表按工作表、`.docx` 按渲染后的文本行） | 11,000~32,000 字 |
| `read_reference` | 读平台内置的评审规程文档 | 11,000~32,000 字 |
| `find_references` | **搜一个标识符**（字段名、协议名、函数名），只回「哪个文件的第几行」，不回正文 | 8,000~20,000 字 |

（「单次上限」由平台按提示词预算推导：**默认预算下** `file_diff` / `file_content` /
`read_reference` 约 **30,333 字**，`commit_detail` 与 `find_references` 顶到 2 万字上限。
它们以前被固定夹在 11,000 字上，把预算调高也没用 —— 现在不是了，见下面「内容超长」
那一段。）

### 读的范围：默认是整个冻结版本（2026-09-24 起放宽）

原先它只能读**本次改动过的那几个文件**。小 diff 恰好改了公共接口时，这会把它卡在中间：
「别的模块还有谁在调这个函数」—— 调用方不在本批次里，它**既证实不了也证伪不了**，
只能在报告里写一条「信息缺口」。现在：

- `find_references` 默认搜**整个冻结版本的仓库**（这次同步到的那个版本上 Git 跟踪的
  **全部**文件），不再只搜本批次；
- `file_content` 能读**同一个冻结版本上任意 Git 跟踪文件**的指定行窗 —— 所以「调用方
  改了没有」这类问题，它读得到证据了。

同时有几条**仍然不读**，都是刻意的：

- **读的是「冻结的提交对象」，不是工作区。** 版本由服务端定：本次同步到的那个提交
  （tip）。工作副本此刻的内容可能与本次快照不是一回事（同步每 2~3 分钟一跑），读它等于
  给你一份「没有版本的证据」；模型给的提交号 / 分支名一概忽略。
- **仓库外的路径一律拒绝**：绝对路径、盘符、`..`、控制字符都不行。拒绝时会**写明理由**
  与「可以改成什么」（例如「只接受仓库内的相对路径」）—— 让它下一轮能改对，而不是把它
  读成「平台取数失败」再写进信息缺口。
- **凭证与密钥类文件不送进模型上下文**：按文件名与目录判（`.env`、`*.pem`、`id_rsa`、
  `.ssh/` 等）。这是**拒绝读取**，不是「读不到」。
- **没 commit 的东西它看不到**（Git 不跟踪的东西不在里面）。
- **仓库太大时只索引一部分**：一次索引有一页的上限，回执会如实写「还有 N 个文件没索引」
  并给出按目录分页的**下一页前缀**（可以直接抄进下一次索取）。这时它**只报「覆盖不足」、
  不下「全仓没有引用」的结论**。
- **找不到本地仓库时报「无法检索」，不是「没有命中」**（多节点部署、项目没绑 Agent、
  不是 git 仓库、或对象库里读不到那个提交）。这时它会退回「只搜本批次」，并在结果里写明
  范围只有本批次 ——「没搜到」与「没搜那么宽」是两回事，混了就会把一次小范围搜索说成
  「仓库里没有引用」。

### 内容超长时不是砍一刀，而是分段 / 分页让你继续点名

四个会返回长内容的工具（`file_diff` / `read_reference` / `commit_detail` / 配表的
`file_content`）在超长时会按**结构**切成段（改动块 / 文档小节 / 一个文件一段 / 一张表），
并在开头写明**一共几段 / 这里给了哪几段 / 要看别的段怎么写**。所以报告里出现
「共 5 段，这里是第 1-2 段」时，那是**它自己知道没看全**，不是平台悄悄砍掉了中间。

**代码正文则是分页**：一页给不下时，抬头里带一条**回执**，形如
`｜回执：total_chars=… returned_range=a-b returned_chars=… truncated=… next_cursor="…"`。
`next_cursor` 是一段**可以直接抄进下一轮 `lines`** 的字符串（例如 `"1181-1260"`）——
「继续看」从「自己做行号算术」变成「复制这一格」；没有更多内容时它写 `无`（**不是空**：
「没给」与「没有了」是两件事）。

`file_content` 的坐标随文件类型变：代码/文本是**行号**（`"lines": "1180-1260"`，与 diff 里
的 `@@` 是同一套坐标），配表（`.xlsx` / `.xlsm`）是**第几张工作表**（`"lines": "2"` 或
`"2-3"`）。**Word 文档（`.docx` / `.docm`）按渲染后的文本行**给（段落、标题、表格都渲染成
文本，行号就是那份文本的行号）—— 与代码/文本同一套坐标，模型不必学第二套。
`.doc` / `.pptx` / `.pdf` 仍然读不到正文（回「无法展示的内容」），平台不会假装读到了。
配表按张而不是按行，是因为它的正文是「每张表各自的整表统计 + 前若干行」，没有「整个文件
的第几行」这个坐标；一次给不下的表会在抬头里逐张点名（「另有 N 张表的正文没给：第 3 张
「…」」），模型写一句 `"lines": "3"` 就能单独拿到 —— 所以配表**不会**出现「被告知内容被
截断、却什么也做不了」那种死路。整表统计（min / 中位 / P90 / max、枚举取值分布）**永远
覆盖整表、且排在正文之前**，与「这次给了哪几张的正文」无关。

### 索取与越权的几条口径

- **一次分析能索取几次，由本次规模与提示词预算一起定**：小批次 40 次；大版本按变更簇
  分工时，每片的名义额由**它那一簇的证据体量**推导，预算只作上限（见第 12.1 节）。
  额度按**单个分析者**累计（跨该角色的轮次），命中缓存也计入，**每一轮都会把这笔账报给
  它**（这一段上限几次、已经用掉几次、还能再要几次），因为它是在第一轮决定「一次要完
  还是逐步逼近」的。额度被压到 **0** 时，那句提示会明说「本次分析不允许索取上下文
  （额度是 0 次）」—— 报告只能基于变更清单，而**不是**「额度用完了」：前者要去加预算，
  后者要去查额度花在哪了，两件事的下一步动作不一样。
- **模型被要求先分诊、再点名**：先看变更清单判断哪里可疑，再针对 **4~8 个**文件要 diff，
  而不是一上来把整批 diff 全要过来。
- **越权索取会被丢掉并说明原因**：提交必须是本批次真实出现过的，文件必须是那个提交确实
  改过、或本次冻结版本上 Git 跟踪的路径。
- 代码文件的正文动辄几千行，`file_content` **默认只给一段**（400 行左右，**位置在本次改动
  附近**而不是文件开头 —— 模型没点名时平台从 diff 的块头里读出行号自己定位），正文每行带
  行号，抬头写明「共 N 行、下面是第 a–b 行、不是全文」。这样给的代价是「一次只看一段」，
  换来的是**一次分析里能看的文件数**。
- **多节点部署（platform/agent 模式）下正文与「某一条提交的 diff」从哪来**：平台自己不
  clone 仓库（这是刻意的），所以这两样都由**业务节点上的 Agent** 在它的工作副本里取出，
  平台只读结果 —— 正文是 `file_content` 任务，单条提交的 diff 是 `file_diff` 任务。
  于是有两条边界：**项目没绑 Agent**、或 **Agent 离线**时，这两样一时拿不到 —— 这时报告里
  会写成「信息缺口」（**并写明是哪个文件、取数怎么失败的**），而不是「这个文件没问题」。
  任务会留在队列里，Agent 上线后取回并落库，**下次分析直接命中、不再等**；在线时的等待
  也有上限（默认 15 秒）。配表（`.xlsx`）的正文同样由 Agent 渲染成文本表格后再回传 ——
  两端**同一个渲染函数**，所以单机与多节点看到的表格内容一致。
- **周版本分析的 diff 与「某一条提交的 diff」不是同一份**：周版本分析优先读平台**已经算好
  并落库**的合并差异（就是周版本页面上那一份，覆盖整个窗口），只有当它读不到、或者模型
  点名问「某一条提交改了什么」时，才去业务节点上现算那一条提交的 diff ——
  现算回来的那份会在开头写明「只含这一条提交对这个文件的改动」，免得被当成整周的改动。

## 7. 它看不到什么（重要）

这一节是**故意写全**的：这些边界决定了报告什么时候会「漏」，知道它们你才知道该怎么追问。

1. **不知道「为什么这么改」。** 周版本的变更清单里**没有提交说明**（平台只存了最新提交号）。
   所以它对改动的意图是推测出来的 —— 有疑问时以提交说明和程序员的说法为准。
2. **清单很长时只列出部分文件名**（上限约 6 万字符；767 个文件的全量清单装得下）。
   但**能读的范围比清单大**：名字没列出来的文件它依然可以点名索取 diff，而且本次冻结
   版本上**任意 Git 跟踪文件**都能读（见 [第 6 节](#6-它能看到什么)）。报告里出现
   「还有 N 个文件的名字没有列出来」时，说的就是这种情况 —— 那是**「不知道路」而不是
   「读不到」**。
3. **只覆盖被提交进仓库的文件。** 没 commit 的东西它看不到。
4. **表与生成物的配对在本项目基本不会生效。** 平台会尝试把「表 ↔ 它的生成物」配成一组
   一起看（表改了、产物没跟上，这种事只有一起看才发现）。但在 G119 上两类名字对不上
   （表名是中文、生成物里是英文），所以这类关联提示**现在基本都是 0 组** ——
   这是**如实**的结果，不是功能没生效。
5. **预算按字符估算，不是 token。** 平台不知道你的模型上下文窗口有多大；只有在端点
   **主动声明**了窗口、且「按最乐观的 1 字 1 token 也已超窗」时，才会把预算压回窗口大小。
   换模型后建议让管理员确认一下预算。
6. **每次取数都有上限**（见第 6 节），所以「这次没看到某个文件」是可能的 ——
   但这种情况平台会让模型写成**「信息缺口」**，而不是写成「没问题」。
7. **开了子代理模式时，可能有一整块维度没人看过。** 分片代理里只要有一个没跑成（上游
   出错、轮次用尽），或者因为预算不够被跳过，报告末尾的「信息缺口（平台补充）」里就会
   点名写出**是哪个分片、它负责哪几个维度**。那几块这一轮**没有任何人看过** ——
   读报告时看到那一段，要当「这里没有结论」，不是「这里没问题」。
8. **不是「每个改动文件都被逐份看过」。** 平台枚举的是**完整清单**，对全部改动做的那些
   确定性计算（关键路径命中、表与生成物的配对）也不花钱、不挑文件；但**逐份取证只发生在
   它判断可疑的那几十个上**（实测：996 个改动文件里 60 个）。报告与导出文档里会**如实
   写出覆盖率与缺口**，见 [第 3 节](#报告里的覆盖与缺口怎么读)。

## 8. 常见疑问（FAQ）

**Q：抽屉一直显示「AI 分析进行中...」，是不是卡住了？**
A：三种可能，看 meta 行能区分：① 真在跑（首次可能要几分钟）；② 上次被**平台重启**
打断，会显示「平台重启，本次分析被中断（未跑完，可以重新分析）。」—— 它**已经跑完的
轮次与用量不会丢**（平台按逐轮事件账本补记，也没有重跑任何模型调用），直接重新分析即可；
③ 确实卡死，超过 1 小时会被调度器重置（提示「AI分析任务超时，已被调度器重置」）。

**Q：提示「请在项目概览页的「AI 分析配置」里补全：接口地址 / 模型名字 / Token」？**
A：AI 配置不全（缺哪项会列出来）。这属于项目管理员的配置，找管理员补。

**Q：报告只写了一半就停了 / 没有 JSON 结构？**
A：模型没按协议输出，平台会**按 markdown 降级保存**，并在结果里标出降级原因
（例如「轮次用尽」「上下文索取额度用尽」「模型没有按协议输出 JSON」）。
降级不等于失败：报告仍然可用，只是可能不完整。

**Q：报告说没问题，但我确实发现了 bug。**
A：按这个顺序排查：① 它在**范围外**吗（meta 行的范围）？② 那个文件**是不是这次改的**
（只分析本批次的变更）？③ 清单里没列出来、它也没去点名索取？④ 取数失败（报告里会写「信息缺口」）。
**报告是辅助，不是验收结论** —— 它给的是「先看哪里」，不是「这里一定没问题」。

**Q：为什么两次分析的结果不一样？某个问题上次报了、这次没了，是修好了吗？**
A：设计如此。第一次是**全量**；之后是**增量**（只带上次分析之后变化的部分），并且每次都把
「上次报过的问题」清单交给模型，要求它逐条标注**仍成立 / 已修复 / 已被推翻**。报告的语义
是「这个版本截至目前的**那**一份」，**不是**「本轮新增了 N 条」—— 所以从清单里消失通常
意味着它被判定为已修复或被推翻。但**判定需要依据**（模型被要求给出依据），拿不准时以实际
验证为准。
唯一的例外是**你自己点了「全量重新分析」的那一次**：那是「从零重判」的指令，平台按你说的
做，不带上次那份清单（报告顶部也会写明）。**平台自己把增量升成全量**的那些情形（见上一节）
不属于这个例外 —— 那几次照常带上历史结论：用户点的是增量，旧问题一条都没失效。

**Q：我提交了代码，但自动分析好像没跑？**
A：自动分析只在**上次分析的那份输入已经变了**的时候才跑。判据是内容指纹
（每个文件的「基线提交 / 最新提交 / diff 版本」排序后的哈希）：指纹没变 = 这一轮能看到的
东西与上次逐字相同 = 再跑一遍只会得到同一份结果，于是跳过（日志里写「输入与上次分析逐字相同」）。
两个常见成因：① 同步还没跑完（同步逐文件写缓存，跑到一半的清单会静默变小，所以先等同步）；
② 仓库还没被 fetch 到新提交。另外，**降级的 run 也记指纹** —— 否则「降级不推时间水位线」会让
同一份输入每小时重跑一次。手动点「AI 分析」不受这条限制，一定照跑。

## 9. 原理简述

**一句话：** 平台把「这个版本改了哪些文件」整理成一份清单交给大模型 ——
清单里**只有提交信息与文件名，没有 diff 正文**；模型点名索取它要看的那几个文件，
拿到证据后输出一份固定结构的报告；平台把它过门槛、去重、封顶（20 条）、入库，
最后在页面上渲染成 Markdown（渲染只支持标题 / 列表 / 引用 / 代码块 / 粗体 / 行内码，
**不支持链接与表格**，不支持的写法按普通文字显示）。

提示词的构成是：平台内置的评审规程 + 项目知识包 + 项目补充指令。**前两者优先级高于
补充指令**，补充指令不能放宽内置协议。

**提示词里几条最要紧的纪律**（这些决定了报告的可信度）：

- **不许把「没看到」说成「没有」。** 取数失败会显式写成「信息缺口」，并明确要求
  「不要凭猜测给出结论」。
- **证据必须具体。** 「配置可能有问题」这种空泛表述不算证据，会被丢弃；证据要指到
  文件、字段、ID、行或提交。
- **维度清单上的每一项都要留痕**（出厂默认那九个见第 12.3 节；项目也可以声明自己的
  清单），没命中也要写明理由，防止「只报容易报的」。
- **反误报。** 看着像问题但可能是「阶段性屏蔽 / 半成品提交 / 联调保护 / 灰度开关 /
  故意提前 return / 故意注释掉的事件」时，默认动作是**先索取能区分两种解释的上下文**，
  而不是直接报成问题。
- **模块耦合必须落成测试风险点。** 平台会专门分析这次改动**跨了哪几个模块、模块之间靠
  什么绑在一起**，并盯住最容易出事的一类：**本该成对改动的两边只改了一边**（配表 ↔ 它的
  生成物、客户端 ↔ 服务端、协议 ↔ 打包解包、字段 ↔ 读取方、公共件 ↔ 它的调用方）。
  只要认定存在耦合，报告里就必须说清「哪两端、靠什么耦合、这次改了哪一端、不同步会以什么
  现象暴露」，并把耦合点写进「测试建议」——**只说「注意联调」不算**。针对耦合的测试风险点
  至少要覆盖三条路径：两端都改了的、只改了一端的、以及老数据 / 老客户端的。
- **它读不到耦合的另一端时会怎么写？** 它读的是**整个冻结版本**（见第 6 节），所以
  「另一端这次没改」在搜索覆盖完整时能给出结论；**覆盖不足**（仓库只索引了一部分、
  或这台部署拿不到冻结版本）时只能写成**待确认的耦合点** —— 这两种说法在报告里是分开的，
  看到「待确认」就说明需要人工去确认那一端是否同步改了。
- **报告是累积语义**：产出的是「这个版本截至目前的那一份」，不是「第 N 份」。
  「风险评估」里列的是**当前仍然成立的全部问题**：本次新增的标「（本次新增）」，上次报过、
  这次仍成立的标「（上次遗留，仍成立）」——后者只写标题与等级，**不会为它补写证据**
  （它本轮没有被重新取证，补一条出来就是编的）；已修复的从清单里去掉，报告里不写
  「本轮新增 N 条」。能不能列全看「结论（本轮 / 继承）」那一行的在挂条数，正文比它少就是
  正文没写全。

### 两个最常被问到的维度

- **`config_data`（配置数据本身是否说得通）**：配表 diff 里最常见的问题不在 ID、也不在
  数值边界，而在**这一行、这一格自己是否成立**：描述/备注与同行取值互相打架（只改了一列
  文案、它描述的字段没跟着改）、新增或改动行漏填必填列、类型与日期格式和同表其它行
  不一致、枚举值不在允许集合里、全角半角或首尾空格（平台按文本原样比较，`'  x  '` 与
  `'x'` 是两回事）、复制粘贴出来只改了一半的重复行、以及列之间的联动规则（「A 列为空则
  B 列为空」这类约定）被打破。报告里对这类问题要指到**具体是哪一行、哪一列、与哪一列
  矛盾**。
- **`value_sanity`（数值是否合理）**：看的是**这个值放在这个系统或玩法里合不合理**，
  三个方向 —— ① **量级**：同类行（同品质、同等级）本来是什么数量级，改后是不是跳了一两
  个数量级（道具价值 `1000` → `1000000`）；② **经济闭环**：买入价与卖出/回收价反了、
  合成或分解的产出大于投入（这类会被玩家刷爆，是最高优先级之一）；③ **单位与档位**：
  百分比与万分比、秒与毫秒、元与分，以及这个字段本来该在的取值区间。口径是「**疑似即可报，
  但必须写明基准来自哪里**」：有基准的要把**基准本身写进证据**（例如「该列 1200 行，
  中位 800、最大 12000，本行改后 1000000」）；拿不到基准的也允许报，但要显式写
  「缺基准：<为什么>」，而且**置信度只能给「高」，不能给「极高」** —— 这样读的人一眼
  能分出哪条是「疑似」、哪条是「确认」。**基准是平台给的**：读表格内容时，平台会在正文
  之前附一段**整表统计**（每个数值列的最小 / 中位 / P90 / 最大、每个文本列的取值分布），
  它**按整表算、不受正文截断影响**；同一张表在本批次里有更早的提交时，还会读那份做历史
  对照（比的是**分布**：中位数从 800 涨到 900 是正常调整，最大值从 12000 跳到 1000000
  才是信号）。

**关于人工处置（设计语义）**：

> 入口在「历次结论」弹层里、报告正文下方的结构化结论清单上，逐条可**确认 / 忽略 / 撤销**。

- `待确认` / `已确认` 的结论，下一轮会作为「仍待处理」继续带着。
- `已忽略` 的结论**默认不再提**，但**它涉及的文件又被改动时，会重新出现**
  （证据过期了，需要重新确认）。这条是「忽略不会变成永远看不见」的保证。

## 11. 项目专属知识（这个项目自己的配置表说明与分析规程）

位置：项目管理页 →「AI 分析配置」卡片右边的**「项目专属知识」**。**仅项目管理员可修改**，
其他成员可以打开看。它维护的是 `skills/projects/<项目代号>/` 这一包东西 —— 在这之前只能
靠人往服务器上放文件，界面上没有任何入口。

### 11.1 三类内容，作用完全不同

| 类型 | 位置 | 谁读它、什么时候读 |
|---|---|---|
| **知识包清单** | `KNOWLEDGE.md` | 它是**模型的目录**：AI 先看到它的一句话说明（`description`），而正文里用反引号列出的文档才会被按需读取 |
| **知识文档** | `references/*.md` | **按需读取**：AI 判断「属于哪个系统」「按什么规则编号」「这个改动算不算越界」时会来读 |
| **子 skill** | `<目录名>/SKILL.md` | 这个项目自己的分析规程：说明进提示词索引，正文按需读取 |

**这个区别值得记住**：往清单里写「配表规范很重要」不会有任何效果，只有**在清单里用反引号
写出文件名、并且那份文档真的存在**，AI 才会去读它。

### 11.2 界面会替你做的两件事（都不是可选项）

清单与 `references/` 之间是**双向强制**的：正文提到的文件必须存在，存在的文件必须被正文
提到。这条规则有一个直接后果 —— 「先建文档再改清单」和「先改清单再建文档」**两种顺序都
不成立**（总有一次保存会撞上校验）。所以：

- **新建知识文档时**，平台会同时在 `KNOWLEDGE.md` 末尾补一行
  `- \`文件名\` —— <你填的一句话说明>`。清单里已经有这一行时不动它（那是你自己的措辞）。
- **删除知识文档时**，平台会**同时摘掉那一行引用**。二次确认里会写明这一点 —— 不摘的话
  知识包会变成不合法的，分析连清单里其他文档一起读不到。

**子 skill 的 frontmatter 由平台生成**（从「目录名 + 一句话说明」拼），不需要也不能手写；
编辑器里会实时显示将要写入的那段 frontmatter。这不是限制，是避免一类必然的错：说明里出现
一个 `": "` 就会让那段 frontmatter 被判非法，而错误信息对策划完全不可读。

### 11.3 改完会发生什么

保存成功后，**此前的分析结论会被标记为「旧」**：每份分析结果都记着当时的规则版本号（它由
平台规程 + 项目知识包的全部内容一起算出来），知识包一变，旧结论就不再是「当前规则下」的
结论。它们**不会消失**，仍然看得到，只是会被标注出来 —— 与「平台评审规程升级」是同一套机制。

### 11.4 数据属于部署实例，不进版本库

**你在界面上建的知识包只存在于这台服务器上**（它落在 `skills/projects/<项目代号>/` 下，
而那条路径被 `.gitignore` 忽略，只放行随仓库分发的 `g119` 示例）。换一台部署就是空的。
这是设计如此，不是缺陷 —— 项目知识是运营数据，不该跟着代码走。

### 11.5 命名与限额

- 文件名 / 目录名只允许**小写字母、数字、连字符**（例如 `config-table-spec`），知识文档会
  自动补 `.md`。中文名、下划线、空格、大写都不行 —— 这个名字会变成磁盘路径。
- 单份文件 ≤ 64 KB，整个知识包 ≤ 512 KB。超长会被拒绝并提示原因。上限不是防滥用：文档会
  进提示词，超长必被压缩，用户会拿到「我明明写了、模型却说没看到」。
- 子 skill 的 `SKILL.md` ≤ 500 行；知识文档超过 300 行要带目录（这两条来自平台契约，
  保存时会校验）。

### 11.6 别和平台内置规程搞混，以及一条已知的待办

- **平台内置的评审规程**：`skills/version-diff-review/SKILL.md`，随平台升级、**所有项目
  共用**，定义了检查维度、输出格式、报告结构。**改它等于改 AI 的行为**，不通过这个面板
  维护（面板上也会写明这一点）。
- **项目专属知识**：只有这个项目能看到，就是这一页。两者冲突时**以平台内置的为准**。
- **子 skill 自己的 `references/` 目录还没有界面入口** —— 目前只能编辑
  `<子 skill>/SKILL.md`；磁盘上已经存在的子 skill references 仍然会被校验与加载，
  只是建不了新的。

## 12. 消耗与费用（token / 缓存命中）

分析跑了很多轮、每轮都要把整份提示词（系统提示词 + 变更清单 + 历史结论 + 上一轮取回的
上下文）再发一遍，**花了多少**这件事在这里看。

**入口**：顶部导航 →「AI 消耗」。页面上先给你一行合计（**你所负责的那些项目**加起来的），
再按项目、周版本（分组键）与单次运行逐层下钻；AI 分析抽屉的底部也有一行
「本次消耗 … tokens · 命中缓存 …」，点旁边的「明细」看这一轮的逐次明细。

**谁能看到什么**：这一页按你的项目权限过滤，看不到别人的项目。

* 「合计」那一行是**你能看到的项目**的合计 —— 平台管理员因为能看到所有项目，它才等于
  全平台合计；普通成员看到的是自己那几个项目的合计。
* **全平台合计与「平台总预算」只有平台管理员能看**：它是一个运营数字，把所有人的花费
  加起来就能反推出别的项目烧了多少钱。所以普通成员看到的是「仅平台管理员可见」这句
  说明，而**不是 0** —— 0 会被读成「一点都没用」，那是另一件事。平台总预算超了照样挡住
  所有人的下一次分析（普通成员在自己的项目那一行看得到「平台已超」，只是不带额度数字）。

### 各列什么意思

| 指标 | 口径 |
|---|---|
| 输入 token | 每次模型调用的输入合计，**逐轮累加**（每轮都重发上一轮的上下文，所以后几轮更贵） |
| 其中命中缓存 | **上游接口报的** prompt cache 命中 token。与「工具结果在本次分析里的内存缓存」是两件事，界面上分开显示 |
| 其中未命中 | 输入 − 命中缓存，**真正按未命中价计费的那一档**。**只在两个加数都上报了才算**：任一没上报就是「未上报」，不显示 0 |
| 输出 token | 模型生成的 token（含下面那一格「推理」，如果上游报的话） |
| 缓存命中率 | 命中缓存的输入 ÷ 输入合计。**只有分子分母都上报了才给这个数** |
| 费用估算 | 按你配置的单价表算出来的金额，见下 |
| 上下文索取 / 取回字符 | 模型索要了几次文件、实际取回多少字符（被预算拒绝、被截断的也会各自计数） |

### 单次运行的「明细」里有什么

点到某一次运行的明细（「逐次运行」表或分析抽屉底部的那个按钮），弹层里有两块是
**回答「这次为什么没看到某个文件」**用的：

* **逐轮表的「明细」列**：点开一轮，能看见它**点名要了什么**（原样的索取，含行窗口）、
  **实际拿到的那一份是内容还是一句「取不到」**（取不到会把工具给的原因照抄出来，标红；
  「工具明确回了没有内容」是另一种，不算失败）、**哪几条被丢掉及原因**、**模型原样返回
  的文字**。计数是分不出这些的：一次失败的索取在「条数 + 字符数」上与真的读了一份 diff
  完全一样。
* **「取数（按工具类型）」表**：这次分析里每类工具索取/执行/缓存命中/**失败**/超预算/
  截断各多少次、取回与交给模型各多少字符。「失败」列就是那些「工具跑完了但没拿到内容」
  的次数（例如没绑 Agent、Agent 离线、同步还没跑完）。

### 逐轮那一行里的「分叉原因」与分开的耗时

**这两个数是给「缓存为什么没命中」用的，不是命中率。** 一次没命中既可能是平台自己把
请求前缀改写了（要修），也可能是必要的压缩、提示词或知识包更新、服务端缓存过期
（不该修）。只看命中率这两件事长得一模一样，所以平台在**每次模型调用之前**对真正发
出去的那份请求算几个诊断值，落在「明细」里：

* **分叉原因**：`首次请求`（这次运行还没有可比的上一请求）/ `追加`（这次的消息是上一次
  的延长 —— 缓存能命中的理想形态）/ `压缩`（平台压过历史或压小重发）/ `提示词版本变了`
  / `快照变了`（后两种是允许的自然失效）/ **`其他`** —— 前缀变了而提示词版本与快照都
  没变，**这一类才是要去看代码的**。同一块里还有「与前一次请求的公共前缀：N 条消息 /
  M 字」以及两串指纹，用来在两个运行之间对照同一段前缀有没有变。
* **耗时构成**：模型调用 / 本地取数 / 建索引**分开记**。合成一个总数就分不清钱花在
  等模型还是等本地 git 上。
* 逐轮表里**只有在真有哪一轮上报了推理 token 时才多一列「其中推理」** —— 多数端点
  一次都不报，给它们加一列全是「未上报」的列只会把表挤宽。

> **哈希是本机诊断指标，不是命中率。** 提供商按 token 和自己的内部单元匹配缓存，
> 哈希相同**不保证**命中（服务端可能已过期），哈希不同也**不保证**未命中（平台这侧
> 多一个不参与匹配的字段就会让哈希变掉）。所以那一栏叫「分叉原因」，不叫「命中/未
> 命中」。这几列**不存提示词正文**（只有哈希与计数），也**不存 API key**。

**这是跑完才有的**：诊断值在跑的时候逐轮写进账本，运行中的抽屉里看不到，分析结束后
在用量面板的明细里看。

**上线之前的老运行没有这两块**，弹层里会写「这一轮的明细未采集」—— 那不是「它什么都
没要」，只是当时没记。

### 12.1 子代理模式：为什么它贵「分片数 + 1」倍

周版本很大时（几百上千个文件），一个 agent 在固定轮次/索取里把这些全看一遍是不可能的。
打开「子代理模式」之后（**默认关**，可在项目管理页 →「AI 分析配置」里打开），平台会：

1. 先按**冻结快照的确定性事实**（变更文件数、差异载荷估算的 diff 体量、单文件最大值、是否被
   截断）定**要不要分工、分几片**（`services/ai/auto_sizing.py`）：
   * 小版本（文件 ≤ 8、合计 ≤ 8 万字、无单文件超过 4 万字、输入没被截断过）→
     **一个分析者**，但它仍然要覆盖**全部**声明维度；
   * 大版本才按**变更簇**（同目录、同提交、配置表与它的产物成对）切 2~5 片，每片的
     轮次/索取按**它要看的证据体量**定，并用提示词预算**封顶**（预算只是上限）；
   * 变更簇太多或归属说不清时，才多花**一次**受限的规划模型调用（只给元数据与摘要、
     不给整表正文），它给的分工要过平台校验（每个文件至少被分到一次、路径都在快照内、
     没有空片、总数不超上限）；**不合规就退回确定性分组**，不会因此跑偏；
   * 清单取样上限、每片/单次异常上限、单次请求超时同样在这里定，**不再需要也不接受
     手动配置**；
2. 把**本次生效的检查维度清单**分给各片：有上面那次规划的分工就按它声明，没有则按
   **相邻顺序均分**（默认那九个；顺序即相关性，所以相邻的维度会落在同一个人身上）；
3. 让每个分片代理**各自拿到整份变更清单**、只对自己那几组维度负责（**能读的范围不按
   维度切**：跨模块耦合本来就只能越片去读才发现）；再由一个主代理把所有分片的候选结论
   审一遍、合成最终报告。

**这份计划只算一次**（周版本输入构建时），**预估弹窗与真正开跑读的是同一份**，并且随
运行记录落库 —— 「确认框说 5 片、实际跑 3 片」在结构上不会发生；事后也能回答「当时是
凭什么这么分的工」。

**代价是模型调用次数变成「分片数 + 1」倍**（分片各自的轮次 + 一次汇总）。省下来的部分
靠的是缓存：所有分片的请求**前两条消息逐字节相同**（系统提示词 + 整份变更清单），
所以第一个分片把这段前缀写进缓存、其余分片与汇总那一次直接命中，按便宜得多的缓存价
计费。**取数也是这一家子共用的**：两个分片都要看同一个文件时，正文只取一次、**两边都
拿到全文**（不是「另一个分片已经看过了」那种转述）；某个分片自己重复要同一份内容时
不会再给一遍正文，与单代理的行为一致。

另外两条口径：

* **额度是串行共享池，不按「每人一份」发**：全家共一个「索取池 + 轮次池」（池 = 分片数 ×
  每片名义额）。分片**串行**执行，每个分片开跑前按池里剩余算当片上限，**用剩的滚给后面的
  分片**。名义额是保底：后面还有角色要跑时，池会给他们留出下限；汇总另有保底下限（可越池）。
  额度是上限、不是预扣，用不掉不花钱。
* **一次分片分析在面板上仍然只有一行**（运行条数不变）：它的 token 是**一家子的合计**，
  逐片的花费在那一行的明细里（「分片代理」那张表），逐轮的「分片」列能看出哪一轮是
  谁跑的。

**哪个分片没跑成，报告里一定写。** 上游出错、轮次用尽、预算不足提前收工 —— 这三种都会
在报告末尾的「信息缺口（平台补充）」里点名，面板上那一行的状态也是「降级」而不是
「完成」。**那一块维度这一轮没有任何人看过**，不能当成「没问题」。

### 12.2 对账轮（找反证）：它买的是「有人去推翻过」

子代理模式解决的是「几个维度分头看」，但每个分片报出的结论**没有第二个人核过** ——
而模型对自己写下的东西天然偏向确认。打开「对账轮」（**默认关**，要先开子代理模式）之后，
平台会在汇总完成后再跑一次独立的请求，把报告里**最严重的 3 条**交给它，指令是反过来的：

> **去找反证。** 能证明某条结论不成立的具体文件、具体行是什么？找不到就写明
> 「未找到反证（我查了哪里）」。**不要重复确认它是对的** —— 原文里的理由不是新证据。

两种答复都算结论，而且都有代价：**「反证成立」意味着那一条不该按原样采信**；
**「未找到反证」意味着有人去找过、没找到** —— 后者比「没人核过」强，但不等于「这条是真的」。
结论写在报告里**两节**（2026-09-24 起）：

* **开篇的「## 复核摘要（平台）」**：覆盖了几条、被核的那几条各自什么下场
  （撤销 / 降级 / 转人工核验 / 维持原结论）—— 第一眼就能看到；
* **正文之后的「## 复核标注（平台）」**：只列**被改判的那几条**（标题、原等级、**一句**理由）。

完整理由与依据存在本次运行的结论存档里，逐条断言的状态在异常面板里；报告不重复它们的正文
（2026-09-25 收口：这一节原本逐条抄理由、依据、平台说明、复核方式与断言，真机实测占整份报告
的 30%）。

没进复核的那几条按模型原话留在正文里，读正文时对着开头那节看。
（对账轮自己交回的那份原文**不进报告正文**，它作为存档在结论载荷的
`verify_report_markdown` 里。）

三条口径：

* **只核对最严重的几条**（默认 3 条，按与报告封顶时同一套严重度排序）。对账要的是深度，
  不是覆盖面 —— 覆盖面是汇总那一次的事；
* **不额外分索取额度**：它核对的是已经拿到的证据，用剩下的额度就够；
* **它也是一次正常的模型调用**，同样命中变更清单那段缓存。**开了却这一轮没跑起来时会如实
  写在报告里** —— 预算早停跳过了它、它自己失败、或这次规模太小只分得出一个分析者（没有分片）：
  报告开篇的「复核摘要（平台）」写明「本次没有跑『找反证』复核」以及是哪一种；**压根没开**时
  报告里没有这一节。两种情况下的结论**没有经过这道复核**，读的时候要当成未经复核的初稿。
  它新发现的问题写在那一节里，不混进异常清单。

### 12.3 检查维度清单：默认九个，项目可以声明自己的一套

平台出厂自带九个检查维度（`config_id` 配置 ID、`config_value` 配置取值、
`config_data` 配置数据本身、`value_sanity` 数值是否合理、`config_linkage` 单表连锁、
`module_coupling` 模块耦合、`code_logic` 代码逻辑、`version_branch` 版本分支、
`process` 流程）。这一份是照着**配表驱动**的项目写的。

换一个不是配表驱动的项目（改的主要是代码、协议、资源引用、存档结构）时，上面那九个里的
五个没有对应物，而那个项目的真实问题又落不进剩下的四个。这时项目可以声明**自己的一套**，
写在知识包 `skills/projects/<项目代号>/references/project-facts.md` 的 frontmatter 里：

```text
dimensions: performance=性能与耗时, protocol=协议兼容性, resource=资源引用丢失
```

五条口径：

* `id=中文名`，多个用逗号分隔。**顺序有意义**：顺序相邻的维度在语义上相关，平台按这个
  顺序把维度**相邻地**分给各分片代理（相邻的几个落在同一个人身上）。
* 声明之后这套清单**取代**出厂那九个：平台把它拼进提示词（模型据此写 `category`）、
  按它分工、按它把报告与导出文档里的维度翻成中文名。
* **没声明 = 用出厂那九个，行为与以前完全一致**（提示词里一个字节都不会多）。
* 声明写坏了（形状不对、id 重复、写成 `none`）→ **回落出厂清单，并在日志里告警**，
  不会悄悄按「没声明」处理。
* **清单外的发现不会消失。** 模型给出的 `category` 落不进生效清单时，平台**按原样保留**
  那一条（原始 category 与它自己的证据都在），把它单独列在报告的
  **「## 未归类（不在本次维度清单内的条目）」**一节里，导出文档里那一格显示成
  「未归类（<原始 category>）」。也就是说：**少一条发现是不可能的，最多是需要人工归位**。

### 「未上报」不等于 0

接口不保证回缓存字段（不同厂商的字段名也不一样）。**没回的时候显示「未上报」、
命中率一列留空** —— 那表示未知，不是「一次都没命中」。同理，本功能上线之前的分析
没有采集过用量，明细里显示「本次用量未采集」，也不会显示 0。

### 跑了一半被打断的运行，账不会丢

**这一页永远显示已经落库的历史值**：还在跑的任务不算在里面，页面会写明
「当前筛选范围内有 N 个新任务运行中（**当前任务未实时统计**，实时用量尚未计入）；
以下统计截至运行 #X，任务完成后自动更新」。那一句里另给的「临时值」只是进度快照里的
下界（只含上游已上报的部分），**不计入上面的统计** ——「还没统计进来」不是
「统计里少了它们」。

每跑完一轮，平台会**立刻落一条独立的轮次事件**。所以 worker 中途被杀、平台重启之后：
**已经跑完的轮次与用量仍然在**（平台按这份账本补记进运行记录，**没有重跑任何一次
模型调用**），也不会把同一笔用量算两遍 —— 补记只填空着的字段，不覆盖已有的数。

### 费用是估算，且必须自己配单价

接口只回 token 数、**不回金额**，所以金额是按你填的单价表算的。**配置入口在「AI 消耗」
页面上的「模型单价表」卡片**（不在项目配置里）：点「按行编辑」逐条填模型名与三档单价，
或者展开「高级模式」直接粘贴 JSON，两种模式编辑的是同一份内容。

```json
{
  "version": "2026-09-18",
  "currency": "CNY",
  "models": {
    "model-name":      {"input": 2.0, "output": 8.0, "cache_read": 0.2},
    "gateway-model-*": {"input": 1.0, "output": 2.0}
  }
}
```

- 单位是**每 100 万 token**；`cache_read`（命中缓存的单价）不填时，命中那部分按未命中价
  计入，页面上会注明「费用偏保守」。
- 模型名按「精确 → 前缀（`xxx-*`）」匹配，**不做包含匹配**（那会让 `gpt-4` 命中 `gpt-4o`，
  价格差一个量级却毫无提示）。
- **改了价格就必须同时改 `version`**，否则保存会被拒绝 —— 每次运行都会记下当时的版本号，
  而面板上的金额一律按**当前**价格表重算（明细里会注明「这条记录落库时的单价表版本是 X」），
  版本号是历史费用的唯一追溯依据。
- 没配（或算不出，例如模型不在表里）时**不显示金额**，并说明原因 —— 不会回落到 0。

### 预算：超了就暂停分析

「AI 分析配置」里可以给项目设**周期内 token 上限**与**周期内费用上限**（周期默认本月）。
项目 token 上限留空会启用 **100M/月安全默认**；项目费用上限留空表示不按金额限制。
平台总预算另由管理员在「AI 消耗」页面配置（同样按周期）。两档是**叠加**的：任意一档超了
都会挡住下一次分析；平台两项都没配时仍有项目默认额度兜底。

- 用超之后 AI 分析会被**暂停**：抽屉里的「重新分析」按钮变灰并写明已用多少、上限多少，
  定时分析也会跳过（日志里记成 skipped，不会静默）。调高上限或等到下个周期即可恢复。
- 判定**只认确定的数**：token 那一档用的是「已上报部分的合计」，它超了才算超；费用那一档
  只要有**任何一次**运行算不出金额（没配价格表、模型名对不上、上游没报 token），就**不按
  费用拦截** —— 宁可放过一次，也不会因为算不出钱就把功能锁死。
- 面板上「各项目消耗」的预算列与抽屉里的按钮用的是**同一份判定**，不会出现「面板说超
  预算、按钮却还能点」。**平台总预算的额度与已用量只有平台管理员能看**（普通成员看到
  「仅平台管理员可见」）；平台档超了时，普通成员拿到的拦截理由里会说明是平台档，
  但不带额度数字。

### 统计口径：设置起点（可逆）与全量重置（不可逆）

页面上的数字是**全部历史**的累计。同一个库上反复试跑（调提示词、验证部署、压测）之后，
那一屏的总量就永远带着这些噪音，而它恰恰是给人看「这个版本花了多少」的地方。
所以「AI 消耗」页面上多了一张「**统计口径**」卡片，两个动作**性质完全不同**：

| | 设置统计起点 | 全量重置 |
|---|---|---|
| 删数据吗 | **不删**，一条记录都不动 | **真删**：运行记录、AI 报告正文、异常清单、分轮轨迹 |
| 能撤销吗 | 随时点「恢复为全部历史」即可 | **不能**，没有回收站 |
| 影响预算吗 | **不影响**：起点之前的运行照旧计入预算的「已用」与拦截判定 | 会：记录没了，预算的「已用」自然归零 |
| 谁能操作 | 平台管理员（状态行对所有人可见） | 平台管理员 |

**「设置统计起点」**填一个北京时间，之后**只在消耗面板这一页**统计那一刻（含）之后创建的
运行：合计、各项目消耗、逐次明细一起变，并且会写明「当前这一屏还有 N 次运行在起点之前，
未计入」。它是**平台级口径**（对所有人、所有筛选都生效），与筛选区那个「时间范围」不是
一回事 —— 后者只是你自己临时看一眼。填**未来**的时间会被拒绝：那会把之后的分析也一起
排除掉，页面永远是空的，而你还以为自己在「重置」。

**「全量重置」**是唯一的破坏性动作，所以它单独一个红色按钮、单独一个弹层、并且要输入确认词
才让提交。两条容易被忽略的后果：**预算的「已用」也会归零**（不是被「重置」了，是记录没了、
闸门那边没有可算的数）；下一次分析会退化成**全量分析**（没有「上一次分析」可比，
「上次报过的问题」这个基线一并消失）。

有分析**正在跑**（进行中或排队中）时会被拒绝：那条运行回写结果时会踩到已经被删掉的行，
你看到的会是「分析失败」而不是「你刚重置过」。等它跑完再重置即可；真的卡死的那条会被
调度器在超时后重置成失败，届时就可以重置了。

## 13. 上下文与模型的窗口（为什么分析不会「撑爆」而中断）

一次分析要把「系统提示词 + 变更清单 + 历史结论 + 已经取回的上下文」整体发给模型，而
模型的上下文窗口是有限的。平台保证**它不会在跑到一半时因为太长而作废**：

- 配置里的「提示词字符预算」（默认 560,000 字）是上限，但**真正生效的是它与窗口水位的
  较小值**：

| 模型窗口 | 怎么知道 | 生效预算 |
|---|---|---|
| 端点声明了（`/v1/models`） | 直接读 | 窗口 × 60% |
| 端点没声明 | 按 **1M token** 处理，并在结果里注明「按默认值」 | 600,000 字 |

- 字符按 1:1 当 token 算（中文约 1:1、英文约 4:1），这个换算是**偏保守**的：按它压出来的
  提示词一定装得下，代价是可能少塞了一点本来放得下的内容。默认的 560,000 字低于
  「窗口问不到」时的水位（600,000），所以那种情况下没调过预算的项目行为不变。**端点声明了
  窗口、且窗口小于约 930,000 token 时**，默认预算会被压到那个窗口的水位 —— 那是窗口本身
  装不下，与预算配了多少无关。
- **超出预算时压掉的是最早的几轮历史**（只留一段摘要：第几轮、索取了什么、需要就重新
  索取），而不是让你少看：系统提示词与第一轮不压（变更清单与历史结论基线在里面），
  被压掉的轮次**会告诉模型**，也**会写进这一轮的记录**（结果里带一份「压缩记录」，
  抽屉里有一行说明）。变更清单只在第一轮发一次，后续轮次只给一句指针。
- **万一上游仍以「上下文超长」拒绝**，平台不会空手而归：按「丢得越少越先试」先压本轮的
  文件正文（无损，模型可以重新索取），再丢早期历史，最后换成一段**必然装得下**的「收尾」
  提示词（只带清单开头与「你已经取到过哪些内容」的目录）。每一步都**先算出它确实压小了**
  才发出去（压不动的那一步跳过，不白烧一次调用）；三级都失败时这次分析才记成失败，并给出
  可照着做的建议（缩小范围 / 换窗口更大的模型）—— **失败的记录不会被当成已有结论回放**，
  重试就是重新跑。

出现任何一种补救时，结论**仍然算数**，但状态是**降级**（抽屉里会有一行 ⚠️ 说明）。报告里的
「信息缺口」要**认真看** —— 它是在被裁剪过的上下文里得出的。

### 上一句「降级」是什么意思

不在超窗场景里的降级也一样会显示在抽屉里，都是同一类事实：**这次不是正常跑完的**。

| 结果里的降级 | 意味着什么 |
|---|---|
| 轮次用尽 | 模型没在轮次内收口，结论基于它当时手上的证据 |
| 索取额度用尽 | 还有文件没看 |
| 按 markdown 降级 | 模型没按协议吐 JSON，平台把它的正文原样留了下来 |
| 协议纠错次数用尽 | 连续多轮都解析不出 JSON |
| 上下文超长后收尾 | 上游拒绝了完整提示词，压小上下文（必要时连历史一起丢）后重新问了一次（见上面的三级补救） |
| 子代理有分片没跑成 | 开了子代理模式时，某个分片失败/被跳过，或者它报出的结论没有进入最终报告 —— **报告末尾的「信息缺口（平台补充）」里逐条列着**，那几块不能当成「没问题」 |
| 对账轮没有跑成 | 开了「对账轮」但那一轮失败/被跳过 —— **报告开篇的「复核摘要（平台）」会写明这一轮没有跑复核**，结论按未经复核的初稿来读（见第 12.2 节）。规模太小只分得出一个分析者时同样写在报告里，只是不标降级（那一轮压根没开分片） |

**没有降级 ≠ 没有问题**：它只表示流程跑完了，不表示平台替你确认过风险。
