1. **先复现**：写一个能失败的用例（或在 `git archive` 出来的 pristine 树上跑），
   记录修复前的原始失败输出；
2. **再定位**：给出 `file:line` 与触发条件，并判断真实后果
   （例如 `.tsv` 读不出表格是「显式报错」而不是「漏报」——危害表述必须准确）；
3. **修复**：改完让同一条用例转绿，且不放松既有断言；
4. **回归**：跑相关既有测试 + 全量套件。

### 3.1 ACCESS-001：三条独立的提权路径

报告只点了 1 条，复核发现是 3 条，**只修其中一条补不上**：

1. `auth/providers.py` 的 `EnvAuthProvider.has_*` 直接读 `session["is_admin"]` ——
   而该 key 由数据库登录写成「登录那一刻的角色快照」。根因不是组合 Provider 的
   `or` 短路（短路只是求值顺序），而是环境变量管理员与数据库用户**共用了同一个 key**。
2. `utils/request_security.py::_has_admin_access()` 的第 3 级兜底
   `return bool(session.get("is_admin"))` —— 它在第 2 级返回 False 后必然执行。
3. `auth/decorators.py::require_role()` 读 `session["auth_role"]`（同样是快照）。
   当前全仓无调用点，属潜在路径，按「不保留提权路径」一并修掉。

修法：以「会话有没有绑定数据库用户」为唯一判据（数据库用户会话 → 授权每请求回查数据库；
未绑定 → 环境变量管理员会话，快照即授权），并在取不到判据时 **fail-closed**。
环境变量管理员的既有能力由 4 条用例证明未被误伤。

### 3.2 两条独立 XSS 链路

- **链路 A（报告点名的 DIFF-B03）**：`templates/diff_partials/excel_diff.html` 的
  `onclick="showExcelSheet('{{ sheet_name }}')"` 与 `static/js/diff-handlers.js` 的
  模板字符串拼 `onclick` + `innerHTML`。关键点是 **Jinja 的 HTML 转义救不了内联脚本**：
  `onclick` 的属性值是先被 HTML 解码（`&#39;` → `'`）、再交给 JS 引擎编译的。
  已改为 `data-sheet` + `addEventListener`；同时扫掉另外 6 处同类注入点
  （`commit_diff.html`、`merge_diff.html` ×2、`weekly_version_full_diff.html` 等）。
- **链路 B（复核新发现，比 A 更严重：插入即执行，不需要点击）**：
  `services/diff_render_helpers.py` 的 `render_deleted_file_content` /
  `render_git_diff_content` / `render_new_file_content` **漏了 `html.escape`**
  （同文件的兄弟函数都做了），而 `templates/weekly_version_full_diff.html`
  对插入的 HTML 逐个 **`eval(script.textContent)`**。被审核仓库里的文件内容、
  文件名（git 允许路径含 `<>`）都能经这条汇点变成可执行代码。

  链路 B 的修复要点：`eval` 不是纯多余（`render_excel_diff_html` 确实会产出内联
  `<script>` 来初始化周版本 Excel 合并 diff），所以**不能只删 eval**。
  改为：服务端只产出**非可执行**载荷（`<script type="application/json">`），
  页面侧显式 `JSON.parse` 后调用同一个初始化函数（时序不变）；
  并且 `json.dumps` 不转义 `</script>` —— 必须手工把 `</` 转成 `<\/`，
  否则 sheet 名里的结束标签会提前闭合标签、落回 HTML 上下文（已加测试）。

### 3.3 `df05236` 自身引入的一个回归（复核新发现）

`services/agent_task_result_service.py` 用 `db.session.get(AgentTask, task_id)` 读取后
判断终态。命中 SQLAlchemy 身份映射时会拿到**旧快照** → 库里是 `processing` 的新批次
被判成 `duplicate=true`，`result_summary` 永不落库。
已在两处读改为 `populate_existing=True`（判定一律以库内当前行为准）。
如实说明：生产 HTTP 路径是「每请求一个 app context/Session」，身份映射天然为空，
所以它主要影响同 context 内的调用方与嵌入式部署 —— 属防御性修复，不是线上必现。

## 7. 上线与运维注意事项

1. **`DIFF_LOGIC_VERSION` 1.9.0 → 1.10.0**（三处字面量同步，有新测试锁定）。
   不升版本号的话，已缓存的旧 diff 会继续命中，**这次的行过滤修复在界面上看不见**。
   代价：首次访问会重算一次（大表会慢）。
2. **节点工作副本目录会变**（`agent/repos_base_dir` 改为与 CWD 无关、并与平台同名同锚）：
   - 已部署节点若 `.env` 里仍写 `agent_repos`，升级后落点从
     `<安装根>\agent\agent_repos\` 变为 `<安装根>\agent_repos\`，
     旧目录成为孤儿，**每个仓库需重新同步一次**（磁盘与带宽成本）；
   - 想保留旧目录：把 `AGENT_REPOS_BASE_DIR` 设为旧目录的**绝对路径**，两侧都会原样使用；
   - 平台侧默认仍是 `<仓库根>/repos`，未设该变量时行为逐字节不变（有测试锁定）。
3. **平台与 Agent 必须同时部署**（沿用上一轮报告的结论）：不带 `attempt` 的旧 Agent
   只能提交尚未回收的首批任务，被回收过的任务会一直 409。
4. 历史脏数据（例如 `overall_status='banana'` 的行）不会被自动订正：
   这类文件在周版本列表的筛选与统计里不可见，建议一次性
   `UPDATE weekly_version_diff_cache SET overall_status='pending' WHERE overall_status NOT IN ('pending','confirmed','rejected')`
   （同时清理 `confirmation_status.dev`）。**本次未擅自改数据。**
