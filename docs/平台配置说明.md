本文用于说明：
- 如何启动平台

- 如何配置“有项目”或“空项目”启动 Agent

## 1. 平台启动（基础）

### 1.1 准备
- Python 3.9+
- `git` 命令可用（如要接 SVN 还需 `svn` 命令）
- 在项目根目录安装依赖：

```bash
pip install -r requirements.txt
```

### 1.2 配置 `.env`
- 可从 `.env.simple` 复制：

```bash
cp .env.simple .env
```

Windows:

```bat
copy .env.simple .env
```

#### 1.2.1 两个密钥必须替换（否则拒绝启动）

> 这一节原先写在 `README.md` 里。它属于「部署时踩坑的细节」，所以挪到这里。

`.env.simple` 是**模板**：`FLASK_SECRET_KEY` 与 `AGENT_SHARED_SECRET` 的值是占位串
（形如 `__REPLACE_ME_WITH_A_RANDOM_...__`），不是可用密钥。

生成随机密钥（两个键各生成一次，**不要复用同一个值**）：

```bash
python -c "import secrets;print(secrets.token_urlsafe(48))"
```

填入 `.env` 的 `FLASK_SECRET_KEY` 与 `AGENT_SHARED_SECRET`；Agent 节点机的
`AGENT_SHARED_SECRET` 必须与平台侧完全一致。

**校验有两道门，覆盖面不同：**

1. 启动脚本 `start.bat` / `start.sh` → `python -m utils.env_bootstrap`
   （退出码 2 即中止）；
2. 进程入口 `bootstrap/runtime_entry.py::_enforce_env_secrets_or_exit`
   —— Web 模式与 `DEPLOYMENT_MODE=agent` 都走这里，所以**直接 `python app.py`
   也绕不过去**。

**判定标准**：这两个键仍是占位值，或长度不足（`FLASK_SECRET_KEY` < 32 字符、
`AGENT_SHARED_SECRET` < 16 字符）→ **拒绝启动**并打印中文修复指引。

**Agent 节点机自带一份同等校验**：Agent 通常直接跑 `agent/start_agent.py`
（既不过启动脚本，也不过 `runtime_entry`），所以 `agent/runner_runtime.py`
里有一份独立实现（`_assert_agent_secret_is_usable`）—— Agent 是单独打包部署的，
平台的 `utils` 在节点机上未必存在。

**本地调试临时放行**（**切勿用于生产**）：`set TESTING=1`（Windows cmd）或
`export TESTING=1`（Linux/macOS）。pytest 环境（`tests/conftest.py` 已设 `TESTING=1`）
不受此校验影响。

该密钥为空（未配置）时**不拒绝启动**，只保留既有降级行为（运行期随机
`FLASK_SECRET_KEY`，Agent 接口返回 503）—— 只有「看起来配好了、实际是公开常量」
才是必须拦下的情形。

### 1.3 启动平台
- Linux/macOS:

```bash
bash start.sh
```

- Windows:

```bat
start.bat
```

- 或直接：

```bash
python app.py
```

默认访问地址：`http://127.0.0.1:8002`

## 2. 账号系统配置（local / qkit）

核心开关：

```env
AUTH_BACKEND=local
```

或

```env
AUTH_BACKEND=qkit
```

### 2.1 local 账号系统（本地用户名密码）

推荐最小配置：

```env
AUTH_BACKEND=local
FLASK_SECRET_KEY=请替换为随机密钥
ADMIN_USERNAME=admin
ADMIN_PASSWORD=请设置
ADMIN_API_TOKEN=可选，供接口鉴权
ENABLE_ADMIN_SECURITY=true
AUTH_DEBUG_MODE=false
```

说明：
- `ADMIN_USERNAME/ADMIN_PASSWORD`：本地管理员账号
- `ADMIN_API_TOKEN`：用于管理接口 Header 鉴权（`X-Admin-Token`）
- `AUTH_DEBUG_MODE=true` 仅建议本地调试使用

### 2.2 qkit 账号系统

推荐最小配置：

```env
AUTH_BACKEND=qkit
FLASK_SECRET_KEY=请替换为随机密钥
QKIT_ADMIN_USERNAME=平台管理员用户名(不含邮箱后缀)
QKIT_LOCAL_HOST=你的平台访问地址(含端口)
QKIT_LOGIN_HOST=auth2.qkit.nie.netease.com
QKIT_REQUEST_TIMEOUT_SECONDS=5
QKIT_REDMINE_API_URL=http://redmineapi.nie.netease.com/api/user
ENABLE_ADMIN_SECURITY=true
```

常用可选配置：
- `QKIT_PUBLIC_BASE_URL`：反向代理场景下建议设置
- `QKIT_AUTH_CHECK_JWT_API`：自定义 JWT 校验地址
- `QKIT_LOGIN_SERVICE` / `QKIT_LOGOUT_SERVICE`：自定义登录/登出地址
- `QKIT_LOCAL_JWT_CACHE`：是否启用本地 JWT 缓存

兼容旧变量名（可用但不建议新配置继续使用）：
- `LOCAL_HOST`, `LOGIN_HOST`, `AUTH_CHECK_JWT_API`, `LOGIN_SERVICE`, `LOGOUT_SERVICE` 等

## 3. 启动模式说明（DEPLOYMENT_MODE）

```env
DEPLOYMENT_MODE=single
```

支持值：

### 3.1 `single`（默认）
- 平台 Web + 本地后台任务都启动
- 适合单机部署、开发测试

### 3.2 `platform`
- 平台只负责控制面（Web/API/任务编排）
- 不启动本地后台任务
- 实际任务下发给远端 Agent
- 适合生产“平台 + 多 Agent 节点”架构

### 3.3 `agent`
- `python app.py` 时不启动 Flask，直接进入 Agent 循环
- 一般用于同仓一体化调试
- 生产更推荐使用 `agent/` 目录独立运行

## 4. 推荐部署方式

### 4.1 单机模式（最简单）
###### 该模式下，只需要启动一个服务即可使用完整功能（缺点：后续机器性能资源不足，不方便拓展）
1. `.env` 中配置：
   - `DEPLOYMENT_MODE=single`
   - `AUTH_BACKEND=local` 或 `qkit`
2. 启动 `start.sh` / `start.bat`

### 4.2 平台 + Agent 节点（推荐生产环境）
###### 该模式下，启动平台服务的机器只接收和显示Agent机器上报的信息，Diff等逻辑实际在Agent节点机器运行，分布式部署
###### 该模式同样可以提供 Agent 节点到不同项目自行部署（代码、excel仓库在本地服务器导出），适用于保密项目
1. 平台机 `.env`：
   - `DEPLOYMENT_MODE=platform`
   - `AGENT_SHARED_SECRET=同一密钥`
2. 启动平台
3. 在各 Agent 机器部署 `agent/` 独立目录并启动（见第 6 节）

## 5. 如何配置“有项目”或“空项目”启动 Agent

Agent 关键配置在 `agent/.env`：

```env
AGENT_PROJECT_CODES=
AGENT_DEFAULT_ADMIN_USERNAME=admin
```

### 5.1 有项目代号启动
- 给 `AGENT_PROJECT_CODES` 填多个项目代号（逗号分隔）
- Agent 注册时会申请绑定这些项目（不存在时可自动创建）

### 5.2 空项目启动（推荐先上线节点再建项目）
- `AGENT_PROJECT_CODES` 留空即可
- Agent 会正常在线，但不自动创建项目
- 后续可在平台创建项目并绑定到该 Agent

### 5.3 让某用户可在平台创建并绑定到该 Agent
- 设置：

```env
AGENT_DEFAULT_ADMIN_USERNAME=某用户名
```

- 该用户在平台可创建项目并默认绑定到该 Agent（用户会被设置为项目管理员）

## 6. 其他机器启动 Agent 节点

### 6.1 分发 Agent 方式
- 可直接复制 `agent/` 目录，或用：

```bash
python agent/build_zip.py
```

生成 zip 分发。

### 6.2 远端配置 `agent/.env`
至少设置：

```env
PLATFORM_BASE_URL=http://平台地址:8002
AGENT_SHARED_SECRET=必须与平台一致
AGENT_NAME=Remote节点-001
AGENT_HOST=
AGENT_PORT=9010
```

说明：
- `AGENT_HOST` 建议留空自动探测
- `PLATFORM_BASE_URL` 不能写成本机 `127.0.0.1`（除非平台就在同一台机器）
- **`AGENT_LOCAL_TASK_TYPES` 不用配**。这个变量决定节点在本地执行哪些任务类型，
  必做集合（`auto_sync` / `commit_diff` / `excel_diff` / `weekly_sync` /
  `weekly_excel_cache` / `file_content` / `temp_cache_fetch`）无论变量怎么写都会被补上。
  其中 `file_content` 值得单独说一句：平台在 platform/agent 模式下**不 clone 仓库**，
  代码文件的正文只有节点上的工作副本里读得到 —— AI 分析要核对某个代码文件时，
  就是靠这条任务把正文取回去的。少了它的表现不是报错，而是 AI 报告里一直挂着
  「读不到文件正文」的信息缺口。

### 6.3 启动 Agent
- Linux/macOS:

```bash
cd agent
bash start_agent.sh
```

- Windows:

```bat
cd agent
start_agent.bat
```

## 7. Agent 发布与回退

> 下面命令在**平台项目根目录**执行。

### 7.1 发布 Agent 新版本（一键发布，其他链接到平台的 Agent 节点代码会自更新）

```bash
python scripts/publish_agent_release.py
```

常用参数：
- `--version <版本号>`
- `--notes "<发布说明>"`
- `--force`
- `--allow-dirty`（允许脏工作区发布，不建议生产使用）

脚本包装：
- Windows: `scripts\publish_agent_release.bat`
- Linux/macOS: `bash scripts/publish_agent_release.sh`

### 7.2 回滚 Agent 版本

回滚到上一版：

```bash
python scripts/publish_agent_release.py --rollback --rollback-steps 1
```

回滚到指定版本：

```bash
python scripts/publish_agent_release.py --rollback --rollback-target-version <版本号>
```

独立回滚脚本（等效）：

```bash
python scripts/rollback_agent_release.py --steps 1
python scripts/rollback_agent_release.py --target-version <版本号>
```

脚本包装：
- Windows: `scripts\rollback_agent_release.bat`
- Linux/macOS: `bash scripts/rollback_agent_release.sh`

### 7.3 管理接口（管理员）
- `GET /api/agents/releases/admin/list`
- `POST /api/agents/releases/admin/rollback`

可通过登录管理员会话或 `X-Admin-Token` 调用。

## 8. Agent 自更新配置

`agent/.env`：

```env
AGENT_AUTO_UPDATE_ENABLED=true
AGENT_AUTO_UPDATE_CHECK_INTERVAL_SECONDS=300
AGENT_AUTO_UPDATE_REQUEST_TIMEOUT_SECONDS=15
AGENT_AUTO_UPDATE_DOWNLOAD_TIMEOUT_SECONDS=120
AGENT_AUTO_UPDATE_INSTALL_DEPS=true
AGENT_AUTO_UPDATE_PIP_TIMEOUT_SECONDS=900
```

行为说明：
- Agent 定时检查最新 release
- 有新版本时下载、校验 SHA256、覆盖文件、自动重启
- 如开启 `AGENT_AUTO_UPDATE_INSTALL_DEPS`，会先执行 `python -m pip install -r requirements.txt`
  - 这里的 `python` 指“当前运行 Agent 的解释器”（`sys.executable`）
  - 用 venv 启动 Agent：依赖安装到该 venv
  - 用系统 Python 启动 Agent：依赖安装到系统环境（不推荐生产）
- 因此该能力**不只依赖 venv**，两种启动方式都可触发；但强烈建议使用 venv 以避免系统环境污染和权限问题

### 8.1 自更新安全约束（Agent 侧强校验，fail-closed）

> 这一节原先写在 `README.md` 里。它决定了「什么样的发布清单会被拒绝安装」，
> 属于部署与发布时要懂的事，所以挪到这里。

Agent 执行自更新时（`agent/self_update.py`）有三条 fail-closed 规则，
发布清单不满足即**拒绝安装**，原因会写进返回平台的消息与 Agent 日志：

1. **`version` 必须是单一安全路径段**（只允许字母数字与 `.` `_` `-`，且首字符为字母数字）。
   该值会参与临时目录拼接，历史实现直接
   `shutil.rmtree(os.path.join(root, ".agent_update_tmp", version))`，
   `version="../../.."`、绝对路径、Windows 盘符都能删掉任意目录。现在改为
   `realpath` + `commonpath` 的包含性校验，落点必须仍在 Agent 目录内。
2. **下载地址必须与 `PLATFORM_BASE_URL` 同源**（scheme + host + port 全等）。
   下载请求携带 `X-Agent-Token` 与共享凭据，`download_path` 若允许绝对 URL，
   等于把机群凭据发给任意主机。
3. **`package_sha256` 变为必填**，且必须是 64 位十六进制串；缺失、格式非法或
   摘要不匹配一律拒绝安装。历史实现写作 `if expect_sha256:` —— 清单里不写摘要
   就完全不校验，篡改发布清单者只要删掉该字段即可投递任意包。

> 平台侧 `scripts/publish_agent_release.py` 生成的清单已始终包含 `package_sha256`，
> 正常发布流程不受影响。

## 9. 使用要点（建议给用户）

1. `AGENT_SHARED_SECRET` 必须在平台和所有 Agent 完全一致。  
2. 生产建议固定 `DEPLOYMENT_MODE=platform`，Agent 独立部署在业务节点。  
3. 平台和 Agent 机器时间尽量同步（NTP），便于日志、心跳和排障。  
4. 发布前尽量保持 git 工作区干净，发布后先观察一个 Agent 的升级日志再全量放开。  
5. 回滚只会切换 latest 指向，不会删除历史 release 目录。  
6. 若远端 Agent 无法升级，优先检查：
   - 平台地址可达
   - 密钥一致
   - 管理接口可访问
   - 节点磁盘空间与 Python/pip 环境  
7. 建议将平台数据库从默认 SQLite 迁移到 **MySQL**（生产场景）。
   - 平台只支持 `sqlite` 与 `mysql` 两种后端（`utils/db_config.py` 的 `SUPPORTED_BACKENDS`），
     **没有** PostgreSQL 后端，也没有对应依赖；连接驱动固定为 PyMySQL。
   - 配置方式（`DB_BACKEND` / `DATABASE_URL` / 连接池等）与 SQLite 的 WAL 行为见
     `代码架构说明.md` 第 5 节。  
8. 生产环境的 `ALLOW_DESTRUCTIVE_DB_OPS` 必须保持关闭。它是「清库 / `drop_all` /
   `truncate`」这类破坏性数据库操作唯一的放行开关（`utils/db_safety.py`）；
   打开后误操作将不可恢复，详见 `代码架构说明.md` 第 5.5 节。  
9. 升级到本次修复后的版本前，请先读第 12 节：历史提交里被丢掉的文件**不会**被普通增量同步补回来，
   已部署实例需要按第 12.3 节做一次数据补齐。

## 10. 权限模型（接口访问控制）

判定函数集中在 `utils/request_security.py`，由 `services/app_security_bootstrap_service.py`
在 `before_request` 里统一执行。

### 10.1 四个权限级别

| 级别 | 判定函数 | 说明 |
| --- | --- | --- |
| 登录用户 | `_is_logged_in()` | 只要登录即可（`local` 后端默认开放自助注册，新用户角色是 `normal`） |
| 平台管理员 | `_has_admin_access()` | 平台级管理操作 |
| 项目成员 | `_has_project_access(project_id)` | 项目内可见/可写；**平台管理员自动拥有所有项目** |
| 项目管理员 | `_has_project_admin_access(project_id)` | 项目级管理操作；平台管理员自动拥有 |

### 10.2 请求门禁顺序

`ENABLE_ADMIN_SECURITY=true` 时（`enforce_admin_access`）：

1. 命中 `AUTH_EXEMPT_ENDPOINTS` / `AUTH_EXEMPT_PATHS` → 直接放行；
2. 携带正确的 `X-Admin-Token` → 直接放行；
3. 未登录 → 401 / 跳登录页；
4. `request.path` 以 `/admin/` 开头，或 `request.endpoint` 命中 `SENSITIVE_ENDPOINTS` → 必须是平台管理员，否则 403；
5. `request.endpoint` 命中 `WRITE_PROTECTED_ENDPOINTS` 且方法不是 GET/HEAD/OPTIONS → 必须是平台管理员；
   其中 `core_management_routes.projects` 例外，改判 `has_project_create_access()`。

### 10.3 两张门禁表的书写要求（重要）

`SENSITIVE_ENDPOINTS` 与 `WRITE_PROTECTED_ENDPOINTS` 里的名字**必须写全限定形式**
（`<blueprint>.<endpoint>`，例如 `core_management_routes.delete_repository`）。

Flask 注册蓝图路由时总会给 endpoint 加蓝图前缀，**即使显式传了 `endpoint=` 也一样**。
如果写成裸名（`delete_repository`），`request.endpoint in TABLE` **永远不成立**，
整张表会**静默失效**——不报错、不打日志，看起来像是权限已经配好了。

两张表的定位是**第二道防线**（纵深防御）：表中多数 handler 自身已带 `@require_admin`
装饰器（`utils/request_security.py`），万一将来有人漏加装饰器，这里仍然拦得住。

`edit_repository` / `add_git_repository` / `add_svn_repository` 是**项目级**页面，
刻意**不**放进平台管理员表，改由函数体内的项目级判定把关 —— 否则会把项目管理员挡在门外。

### 10.4 已修复的权限缺口（升级须知）

| 接口 | 现状 | 修复前 |
| --- | --- | --- |
| `GET /repositories/<int:repository_id>/edit` | 需要**该仓库所属项目**的访问权限；无权直接 403 | **任何登录用户**都能读取任意项目的仓库连接配置（url / server_url / branch / category / resource_type） |
| `POST /repositories/<int:repository_id>/test` | 需要**平台管理员**（`@require_admin`），并列入 `SENSITIVE_ENDPOINTS` | 任何登录用户都能对任意仓库触发真实同步任务，并读回 git/svn 的错误文本 |
| `GET/POST /projects/<int:project_id>/weekly-version-config/api` | 需要**项目访问权限**；无权返回 `403` | 任何登录用户都能跨项目读取配置，或创建配置并派发同步任务 |
| `GET/PUT/DELETE /projects/<int:project_id>/weekly-version-config/api/<int:config_id>` | 需要**项目访问权限**；无权返回 `403` | 任何登录用户都能改时间范围、删配置及其 Excel 缓存、diff 缓存与后台任务 |

> 注意上表前两个接口的方法：`/repositories/<id>/edit` 仍是 GET，`/repositories/<id>/test` 是 **POST**。
> 周版本配置两个接口的完整路径以 `routes/weekly_version_management_routes.py` 注册的为准
> （`/projects/<project_id>/weekly-version-config/api...`），不是 `/weekly-version-config/<project_id>/api`。

升级影响：如果调用方原先用普通账号访问上述接口（典型场景是用脚本或直链读别的项目的仓库编辑页），
升级后会收到 **403**。请改为使用具备对应项目权限的账号，或改用平台管理员令牌。

## 11. 写接口调用方式与 CSRF

平台对**所有非 GET/HEAD/OPTIONS/TRACE** 的请求做 CSRF 校验
（`services/app_security_bootstrap_service.py::enforce_csrf`）。校验失败返回 400：
`CSRF token invalid or missing.` 或 `Cross-site request blocked.`。

CSRF token 的三种传法（`utils/request_security.py::_csrf_token_from_request`）：

- 请求头 `X-CSRF-Token`（也接受 `X-CSRFToken`）
- 表单字段 `_csrf_token`
- JSON body 里的 `_csrf_token`

同时还要求**同源**：`Origin`（缺失时看 `Referer`）的 host 必须等于 `Host`；两者都没有时视为通过。

以下请求直接跳过 CSRF 校验：

- `/api/agents/` 前缀（Agent 协议，走 `AGENT_SHARED_SECRET` 鉴权）
- 静态资源（`endpoint == "static"`）
- 携带了正确 `X-Admin-Token` 的请求（`ADMIN_API_TOKEN`，见第 2.1 节）

### 11.1 三个接口从 GET 改为 POST（升级须知）

下面三个接口原先用 GET 就**会写库**，而 `enforce_csrf` 对 GET/HEAD/OPTIONS/TRACE 直接放行 ——
等于这批写操作完全落在 CSRF 保护之外（攻击者页面一个顶层导航或 `<img src>` 就能在受害者
登录态下触发）。现已改为 **POST**：

| 接口 | 变更 | 破坏性 |
| --- | --- | --- |
| `POST /api/excel-html-cache/clear`（含 `?force_all=true`） | GET → POST，并补平台管理员校验 | `force_all=true` 会执行 `DELETE FROM excel_html_cache`，**清空全平台 HTML diff 缓存**（下轮访问全部重算） |
| `POST /api/excel-html-cache/regenerate` | GET → POST，并补平台管理员校验 | 删指定缓存行，并对 `repository_id` / `commit_id` / `file_path` 触发重新计算 |
| `POST /update_commit_fields` | GET → POST（该 handler 本就在 `SENSITIVE_ENDPOINTS` 里，需平台管理员） | 遍历并改写 `commits_log` 中所有 `version` / `operation` 为空的记录 |

**运维/调用方适配**：原先用 GET 调这三个接口的脚本必须改成 POST，并满足任一鉴权方式：

```bash
# 方式一（推荐给脚本）：管理员令牌。它同时满足平台管理员校验并跳过 CSRF 校验
curl -X POST -H "X-Admin-Token: $ADMIN_API_TOKEN" \
  "http://<平台地址>:8002/api/excel-html-cache/clear?force_all=true"

# 方式二：会话 Cookie + CSRF Token，且必须是同源请求
curl -X POST -H "X-CSRF-Token: <token>" -b "session=<cookie>" \
  "http://<平台地址>:8002/api/excel-html-cache/regenerate?repository_id=1&commit_id=<sha>&file_path=Config/A.xlsx"
```

方式一需要平台 `.env` 里配了 `ADMIN_API_TOKEN`；方式二的 token 取自登录会话
（`session[csrf_session_key]`），脚本里通常先从页面 meta / 表单里取出来。

平台前端已同步改为 `fetch(..., { method: 'POST' })`（`templates/excel_cache_management.html`），
`templates/base.html` 里的全局 fetch 包装器会自动补 `X-CSRF-Token`，无需手工带。
`/update_commit_fields` 在仓库内没有调用方，改方法无兼容性影响。

## 12. 并发一致性与数据完整性

### 12.1 Agent 任务抢占是原子操作

`POST /api/agents/tasks/claim` 的抢占已改为**带条件的原子 UPDATE**：

```sql
UPDATE agent_tasks
   SET status='processing', assigned_agent_id=?, started_at=?, lease_expires_at=?
 WHERE id = ? AND status = 'pending'
```

只有目标行**仍是 `pending`** 时才更新得到，`rowcount == 1` 才算抢到；抢不到就换下一条继续试
（最多 10 次，`_AGENT_CLAIM_MAX_ATTEMPTS`），而不是直接返回「没有任务」——后者会让 Agent
在争抢时空转一轮。

- 修复前是「SELECT 取第一条 pending → 在 Python 里改属性 → commit」，两个 Agent 同时轮询时
  会**各自读到同一条** pending 任务，于是**同一条任务被两个 Agent 执行**：重复写库、重复拉取缓存、
  重复派发下游任务；而且 `assigned_agent_id` 与实际执行者不一致，出问题无法追责。
- 该写法在 SQLite 与 MySQL 上都可用（SQLite 不支持 `SELECT ... FOR UPDATE`，所以不采用行锁方案）。

`lease_expires_at` 的语义**没有变化**：仍是「续租窗口」，由请求体 `lease_seconds` 决定
（取值被夹在 30~600 秒，缺省 120）。超过租约仍未续租的任务会被重新放回 `pending` 并可被再次抢占。

### 12.2 仓库 ID 分配是原子自增

创建仓库时不再用「读 `global_repository_counter.max_repository_id` → 在 Python 里 +1 → 写回」，
改为原子自增再读回（git / svn 两个入口共用 `services/repository_creation_handlers.py::allocate_repository_id`）：

```sql
UPDATE global_repository_counter
   SET max_repository_id = max_repository_id + 1
 WHERE id = ?
```

修复前是典型的 read-modify-write：并发提交创建表单时两个请求读到同一个 N、都算出 N+1，
后者 `INSERT` 撞 `repository.id` 主键报 `IntegrityError` → **500**。管理员看到「创建失败」
但没有任何可用提示，而且前一条已经建成、后一条的表单内容全部丢失。

### 12.3 一次提交改多个文件：每个文件各占一行（含运维补齐步骤）

`commits_log` 的行标识是三元组 `(repository_id, commit_id, path)`。SVN 与 git 两条同步路径
原先的判重键**漏了 `path`**，只按 `(repository_id, commit_id)` 判重，而两条路径的提交列表
本来就是**一个文件一条**（`commit_id` 相同）：

- `services/svn_service.py::SVNService.sync_repository_commits`
  （`_parse_svn_log` 对 `paths` 里每个 path 各产出一条 `r<revision>`）
- `services/task_worker_service.py::_handle_auto_sync_task_inner`（git 后台同步）
  （`git_service.get_commits` 对每个变更文件各产出一条，`commit_id` 是同一个 hexsha）

于是**同一次提交的第 2 个文件起全部被判为「已存在」而跳过**。实测（修复前，一个 SVN revision
改了 3 个文件）：`parsed entries` 3 条，`rows added: 1`，库里只剩 `/trunk/Config/A.xlsx`。

对「配表 diff 确认平台」来说这是致命的数据丢失：评审者在提交列表里**只看得到第一个文件**，
确认了这条提交就等于确认了**没看过**的改动，而且界面上没有任何异常迹象。

现已统一到 `(commit_id, path)` 口径（`services/agent_management_handlers.py` 的 Agent 回传路径
本来就是对的）。SVN 路径顺带修掉一处 N+1：改为按本批 `commit_id` 批量查询已存在的
`(commit_id, path)` 集合（500 一批），循环内只做集合判断。

> **⚠️ 已部署实例必读：历史缺失的文件不会自动补回来**
>
> 增量同步的起点是 `since_date = max(repository.start_date, commits_log 中最新 commit_time)`
> （`services/task_worker_service.py::_handle_auto_sync_task_inner`；git 侧最终落到
> `services/git_service.py::get_commits(since_date=...)` 的 `since` 参数）。
> 修复前被跳过、**从未落进 `commits_log`** 的历史文件不在这个时间窗口内，
> 因此**再次普通增量同步不会把它们补回来**。
>
> 补齐方式按部署模式区分：
>
> - **Agent 模式**：`agent/handlers/auto_sync.py::_collect_commits` 用 `git log -n<limit>`
>   （SVN 侧是 `svn log -l<limit>`）采集，**不带任何日期过滤**。所以重新派发一次 auto_sync
>   任务就会重新采集这段区间，判重键已含 `path`，之前缺的文件会被补上。
>   注意 `limit` 取自 payload，缺省 **300**、被夹在 50~2000 —— 若缺失发生在更早的历史，
>   需要把 `limit` 调大到覆盖该区间。
> - **单机（single）模式**：同步按 `since_date` 增量拉取，必须让采集回到历史起点：
>   清掉该仓库在 `commits_log` 中的记录（或删除仓库后重新创建并同步），
>   并确认仓库的起始日期（`repository.start_date`）为空或早于需要补齐的历史起点，再触发同步。
> - 平台仓库页的「重试」入口（`services/repository_maintenance_api_service.py::handle_retry_clone_repository`
>   → `should_retry_with_reclone()`）只在下列两种情况选 `force_reclone`，否则选 `force_repair_update`：
>   (a) `clone_status` 是 `pending` / `cloning`；或
>   (b) `clone_status` 是 `failed`，**或** `clone_error` 非空 —— **且**该仓库在 `commits_log` 里
>   一条记录都没有（`has_commits` 为假）。
>   **注意 `force_reclone` 只清理本地工作副本再重新克隆，并不会重置 `since_date`**，
>   因此在单机模式下它本身不足以补齐历史。
>
> 建议升级后逐个核对已启用仓库的提交列表文件数是否与 VCS 一致，确认没有遗漏再放行评审。
