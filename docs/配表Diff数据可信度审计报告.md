## 二、四类问题

### A 类：正文的比对基线 ≠ 页头标注的对比版本（14/100，最严重）

页头「对比版本」由 `resolve_previous_commit(commit)` 解析；正文来自 `DiffCache`。
两边口径不一致时，用户看到的是**与另一个版本比出来的结果**，而页头仍标注着
「对比版本 = 上一版」——界面上完全无法察觉比错了。

实测三个方向：

1. **基线晚于被审提交**（凭空产生变更、真变更被抵消）
   - `6158` `EditorCfgTool/excel/skill/BuffCfg_Buff配置.xlsx`：真值是该文件**新增**
     （父提交里连目录都不存在，应显示「初始版本 / 全部新增行」），平台却报
     `modified 124`。用平台自带引擎复现：
     `process_diff(路径, blob(6ecc9c5a), blob(5263ef18))` 与线上内联数据
     **2967/2967 条 (行, 列, old, new) 逐条一致**，而 `5263ef18` 是 `6ecc9c5a`
     的**后继提交**（08-31 21:29 vs 14:23）。
   - `6773`：平台报「售卖价格/购买价格变化」，而这两个值在两版之间**根本没变**；
     报出的 old 值恰好等于**下一个提交** `bc227b16` 的值（逐格对上）。真变更
     （物品描述 F 列 15 格）整体漏报。
   - `6785`：平台报「宝藏房巡逻列被清空 7 行」，而两版里**都没有这一列**；
     old 值等于**下一个提交** `fffbae0c`（也等于仓库 HEAD 内容）里该列的值。
     真变更（新增 AD/AE/AF 三列 18 格）漏报。
   - 同类还有 `6767`（old 值只存在于后代提交 `b9ae2037`，真变更 `武器!E490` 被抵消）、
     `6764`（报出的删除行只从子提交 `72e49c3d` 起存在，真实 17 行改写被判 0 修改；
     且与同平台 `6630` 记录的 prev 行数自相矛盾）、`6691`、`6684`、`6736`、`6775`。

2. **基线 = 该文件的最新版本**（同样方向反转）
   - `6703`：平台报 `added 1343`，真值只有第 1243 行 11 格。实测基线是最新版本
     `4addc430`（该版本 `游戏内外观模型表` 只剩 9 行、`创角外观模型表` 整表不存在）。
   - `5998`、`6143` 同类（`5998` 的基线是工作副本/HEAD 版本 `c1605a34` 的内容）。

3. **基线 = 空版本**（整份文件被当成新增）
   - `6729`：平台报 `added 51`（两张表都标「新增工作表」），真值是 `触发技能` 表
     新增了第 30 行 6 格。用平台引擎复现 `process_diff(路径, blob(本提交), None)`
     与线上**逐字段一致** —— 即正文是「与空版本比」算出来的。
   - `6719`：平台报 `added 353`（含 `Sheet1 added 0`，空表也标新增），真值 2 格。

**根因（已定位到三个具体成因，本次修了两个写侧 + 一个读侧）**：

| 位置 | 问题 | 状态 |
|---|---|---|
| `services/commit_diff_view_service.py`（页面读缓存） | 读缓存**不传基线**，交给缓存服务自己解析（只查 DB）；解析不出来时基线校验被**整个跳过**（`excel_diff_cache_service._resolve_expected_baseline` → 不校验），于是同一 (提交, 文件) 下任何基线算出来的行都可能被当成这一页的正文。而页头用的 `resolve_previous_commit` 更强（同秒按 id 兜底、库里缺失还能回退 VCS）——两边口径不一致，缓存键等于白加。 | **已修** |
| `services/commit_diff_logic.py::handle_different_files_merge` | 单提交组传 `previous_commit=None`（那句 `file_commits[1] if len(file_commits) > 1 else None` 处在 `len == 1` 分支里，条件恒假）→ 载荷是「整份文件新增」，并以 `previous_commit_id = NULL` 落库。 | **已修** |
| `services/commit_diff_logic.py::handle_consecutive_commits_merge_internal` | 范围 diff 失败时的回退写 `file_commits[1]`，而 `file_commits` 是**升序**排的：两条提交时它就是 `latest_commit` 自己（自己和自己比 → 整段区间算成「无变更」），更多条时基线落在区间内部（只显示区间尾部，页头却声称覆盖整段区间）。 | **已修** |

**仍未定论的部分**：抽样中那 14 条的具体缓存行内容与它记录的 `previous_commit_id`
是否同源，需要线上库/日志才能确认（见第五节）。上述三处修复消除了「错误基线被写入」
与「错误基线被命中」这两条通路，但不能断言它们就是这 14 条的全部成因。

### B 类：删除提交看不到被删掉的内容（6/100）

`6033`、`6078`、`6032`、`6146`（删除文件）、`6055`、`6142`。

页面只显示一句「该文件在此提交中被删除，无法显示差异内容」+ 一个「上一个版本」链接，
而那个链接指向的是**那条提交自己的变更**，不是被删掉的内容。配表整份删除

「有东西没了」，看不到没的是什么。

修复前一律 `rows = 0`（正文空白），修复后 `summary.removed` 与渲染行数逐条一致且带真实单元格值。

### C 类：服务端渲染 HTML 丢单元格内容（影响所有依赖该接口的下游）

`/commits/<id>/excel-diff-data` 的 `html_content` 在抽样中**88/88 份非空载荷里
`<td class="excel-cell">` 出现 0 次** —— 每行只渲染一个行号 `<td>`。

成因两条，均已修（`b04ab27`）：模板读 `row.cells`，而实际流通的行形态是
`data` + `cell_changes`（没有 `cells`）；以及修改行落进 `{% else %}` 输出成
`excel-row-normal`（服务端模板从不输出修改行标记，`22fd173` 补齐）。

这类缺陷不污染用户结论（页面走内联 `diffData`，不调用该接口），但会让归档/截图/
外部评审看到「一串没有内容的行号」，也是上一轮「66% 空结果」误判的来源。

### D 类：变更幅度失真（结论方向对、数字不可信）

- **行匹配吞掉整块变更**：`5988` 平台报 3 行，git 是 1985 格/456 行，且平台报的
  「行 9」把第 10 行与第 21 行的值错配成一条 modified（old 取自第 21 行、new 取自第 10 行）；
  `6626` 平台报 8 行，git 是 322 格/63 行。
- **表头改名被放大**：`6651` git 只有 2 格（含表头单元格 `H1` 改名），平台报 5 行
  modified —— `read_excel(header=0)` 把表头当列名 + `reindex(columns=..., fill_value='')`
  使整列旧值变 `''`，一处改名放大成多行。
- **行号口径**：平台「行号」= Excel 行 − 1（`_dataframe_rows_with_index` 用
  DataFrame 行序 +1，而 df 第 0 行 = Excel 第 2 行），且表头行的变更不可见。
  抽样中所有有变更行的记录都是这个偏移（如 `6035` {6,8,18,19} → {5,7,17,18}）。
- **统计含空行**：整表删除时 `stats.removed = len(previous_df)`（含空行），
  如 `基地常量 136 vs 76 有值行`。

**未修**：这三项都会改变用户看到的行号与计数，属于口径决策而不是 bug 修复，
需要先确定「行号按 Excel 行还是按数据行」「相似度匹配的阈值与位移处理」再动。

## 五、需要线上库/日志才能定论的一件事

A 类里 14 条的具体成因只到「机制」这一层。要定论需要下面任一条证据：

1. `DiffCache` 中涉及这些提交的行：`previous_commit_id`、`created_at`、`diff_version`、
   `cache_status` 与 `diff_data` 里 `stats.total_rows_previous`；
2. `DIFF` 日志里 `📂 当前提交: X | 前一提交: Y`（`services/vcs_content_service.py`）与
   对应请求的页头解析结果是否一致；
3. 该 path 在 `Commits` 表里的 `(id, commit_id, commit_time)` 是否存在 `commit_time` 倒挂
   （补录 / 多来源写入会把「前一提交」解析到更晚的提交）。

在拿到这些证据之前不建议改「基线解析」本身：读路径已经按缓存键过滤，
真正的风险集中在**写侧写入了错误基线**与**非提交级功能复用了同一张缓存表**
（区间/合并 diff、版本对比），改动面比这三处修复大得多。
